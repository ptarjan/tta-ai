THE FIX
-----------------------------------------------------------------------
Model copied, as instructed: `decrease_population`'s existing
`interact::enqueue(state, QueueItem::LosePop{..})` shape (events.rs), and
`interact::offer_plunder_split`/`plunder_split_options` for split
enumeration -- reused DIRECTLY for the loss side (not re-implemented),
since a self-directed loss is capped by the exact same "how much can this
player's own two banks supply" math Plunder already uses for a victim's
banks.

New types (rust/src/state.rs):
- `QueueItem::FoodOrResSplit { player: u8, amount: i16, lose: bool }` --
  enqueued once per targeted player, from `apply_gains_block`
  (rust/src/events.rs), in the SAME clockwise-from-revealer order
  `resolve_count_targets` walks (see "clockwise ordering" below).
- `ChoiceKind::FoodOrResSplit { lose: bool }` -- options are
  `ChoiceOption::Gain(GainOption)`, exactly `PlunderSplit`'s own option
  shape. `lose` distinguishes Raiders' drain direction from Foray's gain
  direction.

Enumeration (rust/src/interact.rs):
- Loss (Raiders): `plunder_split_options(&state.players[player], amount)`
  called DIRECTLY, unmodified -- it already windows the split by what a
  player's own two banks can supply (r_max/r_min against `resources`/
  `food`), which is exactly "respecting what the player can actually pay"
  for a self-directed loss too, not just a victim's. This IS the "player
  who cannot pay the full amount from one pool" requirement: if a player
  has 1 food and needs to cover up to 2 of a loss, the (food:2,
  resources:0) option is never generated, because `r_min = (total -
  food).max(0)` excludes it. Covered by
  `plunder_split_options_omits_a_split_the_players_own_short_pool_cannot_cover`.
- Gain (Foray): new `food_or_res_gain_options`, every split 0..=total with
  NO cap at option-build time -- deliberately matching `PlunderSplit`'s own
  existing attacker-gain precedent (its own doc comment in state.rs): the
  chosen split is capped automatically, per bank, by `economy::gain_food`/
  `economy::gain_resources` AT RESOLUTION, not filtered out of the option
  list. This is not a new gap; it is the same simplification PlunderSplit
  already ships with, called out explicitly rather than inherited silently.

Resolution (rust/src/interact.rs, `resolve_choice`'s new
`ChoiceKind::FoodOrResSplit` arm):
  lose  => player.food/.resources -= chosen amounts, saturating (never negative)
  !lose => economy::gain_food(player, food); economy::gain_resources(player, res)

Clockwise ordering (rust/src/events.rs, `resolve_count_targets`): the
`strongestPlayers`/`weakestPlayers` loops used to iterate `targets`
(strength-sorted, for SELECTING who qualifies) and apply each selected
player's block IN THAT STRENGTH ORDER. Selection is unchanged, but
resolution order now re-walks `order` (already clockwise from the revealer,
`order_from`) filtered down to just the selected players -- so whatever
per-player decision a selected player's own `apply_gains_block` call opens
(chiefly this new choice) resolves clockwise, not by strength-tie-break
order. Verified this cannot change `decrease_population`'s existing
behaviour for any base-game card: `StrongestPlayers`/`WeakestPlayers` is
printed on exactly 4 cards (Raiders, Foray, Crime Wave, Cold War) and all
four print `decrease_population: 0`.

Bot wiring: `interact::pending_moves` (legal.rs's only caller for an open
`Pending::Choice`) already turns ANY choice's options into `Move::Choose{n}`
candidates, ChoiceKind-agnostic -- so the WEIGHTED (learned) bot picks among
these splits with its ordinary board-state evaluation, zero new
special-cased heuristic code, exactly like PlunderSplit already does.
Grepped every exhaustive match over `ChoiceKind`/`QueueItem` in the whole
crate (interact.rs's `resolve_choice` + `run_item`, replay_common.rs's
`categorize_choice` + `resolve_intervening`'s drain match, bots/book.rs's
`choice`) -- confirmed `bots/weighted/*` has NONE, so there is nowhere a
hardcoded preference for the learner could even be smuggled in.
`bots/book.rs` (a SEPARATE, entirely hand-tuned heuristic bot, not the
learner -- every one of its decisions is hand-scored, mirroring Python's
book.py) needed a new arm to stay exhaustive; it reuses the existing
`prod_value`/`PlunderSplit` valuation shape, negated for a loss, same as
that file already does for every other decision it answers.

`events::food_or_resources` (the old fixed-formula function) is DELETED,
not kept dead: its one production call site was switched to enqueue
instead, leaving it with zero callers.

Replayer rewiring (rust/src/replay_common.rs): a PRIOR pass had already
patched the replayer to journal-correct `food_or_resources`'s wrong guess
POST-HOC (apply the deterministic split, then overwrite `p.food`/
`p.resources` against `produces_grants`/`spends_grants`, two FIFOs already
built by a broad, non-event-aware text-shape prescan of the whole journal).
Since the engine no longer applies anything synchronously here -- it opens
a real `Pending::Choice` instead -- that post-hoc correction is now
provably dead code (deltas would always be zero) and was removed.
`resolve_intervening`'s own exhaustive choice-dispatch match gained a
`ChoiceKind::FoodOrResSplit` arm that drains the SAME two FIFOs, but
resolves them by feeding a real `Move::Choose` into `apply::apply` --
matching the live choice's own options -- instead of patching fields
directly. One correctness nuance caught by a pre-existing regression test:
UNLIKE `PlunderSplit`'s own FIFO consumer (which pops-and-discards a
non-matching entry while scanning), these two FIFOs must NOT discard a
miss -- they're filled by text-shape alone, so an entry that isn't this
choice's answer may still belong to a LATER, unrelated real consumer
further down the game. Fixed by scanning with `position()` + `Vec::remove`
(exactly the old post-hoc code's own approach), not `pop_front()` in a
loop; caught because
`foray_skips_a_foreign_non_matching_entry_queued_ahead_of_its_own_real_split`
failed with the pop-and-discard version first, before I'd finished reading
its own assertion.

THINGS I WAS UNSURE ABOUT / CHOSE NOT TO DO -- stated plainly
-----------------------------------------------------------------------
- Foray's gain-side option enumeration has NO cap at option-build time
  (blue tokens only limit what lands at resolution). This is a real,
  acknowledged simplification, not something the rulebook settles either
  way -- it exactly mirrors the PRE-EXISTING `PlunderSplit` choice's own
  attacker-gain arm, so I did not invent a new gap, but I also did not
  independently verify that pre-existing simplification is itself
  optimal-play-correct. If a future pass wants the option list itself
  capped by achievable-given-denomination-consolidation blue-token math,
  that math is nontrivial (`economy::gain`'s own doc: gains are not
  monotonic because of token consolidation) and was out of scope here.
- I widened the `resolve_count_targets` clockwise-ordering fix to BOTH the
  `strongestPlayers` and `weakestPlayers` loops (not just wherever Raiders/
  Foray specifically need it), since the underlying RULES_SPEC.md §5.3 rule
  ("multiple-player decisions resolve clockwise") is general, not specific
  to food-or-resources. I verified this cannot change any EXISTING
  observable behavior (decrease_population is 0 on all 4 cards that use
  these two targeting keys), but I did not get explicit sign-off that
  widening the scope of the ordering fix beyond "just make the RED test
  pass" was wanted -- flagging the judgment call rather than making it
  silently.
- The task's rule text is explicit about ORDER ("clockwise from the
  revealing player") but RULES_SPEC.md itself is silent on the CONTENT
  question (that the split is a genuine per-player choice at all, not just
  its order) -- that half rests entirely on the BGO journal evidence already
  gathered by the prior FOODCHOICE.txt pass, which I read and cross-checked
  against the current code but did not re-derive from a fresh journal read
  this pass (out of scope: no journal access in this task's instructions).
- Did not touch `docs/RULES_SPEC.md` or `sources/` themselves -- read-only
  references for this pass, per the task framing ("cross-reference sources/
  ... to decide"), not files this fix should be editing.
- Left the `climb`/`champion_*.json` trained-weight files untouched. Same
  caveat the prior pass already flagged: any existing trained weights have
  zero learned skill at this NEW decision point (it did not exist in their
  training data) and would benefit from further training exposure -- not
  this task's scope to retrain, and not done.
