Ran via a build.bat (avoids ssh/cmd quoting pain), executed synchronously over ssh
(the connection just stays open until the remote command finishes -- no detachment
trick needed here since climb.rs is fast to build; only needed for the long-lived
arms in step 3).

WHY --bin climb, not a bare `cargo build --release`: rust/src/bin/ has ~29 binaries
(climb, neuraltrain, rankdata, selfplay, humantrain, ...). The package has a lib.rs,
so building one bin still compiles the shared lib once and links only that target,
skipping ~28 binaries we don't need. This is the same LTO=fat, codegen-units=1,
opt-level=3 release profile from Cargo.toml -- no compiler settings were changed, only
which binaries get built. Game logic was NOT touched.

Result: built in 41.42s (cold, no cache) -- far under the 10-25 min estimate from the
task, because that estimate was for the mini's full multi-binary build. Confirmed
target/release/climb.exe exists (1,270,470 bytes) and `climb.exe --help` prints the
expected flag list (--players, --gauntlet, --gauntlet-kind, --gauntlet-search,
--threads, --seed, --pool-k, etc.) matching the mini's binary's interface.

No Windows-specific build errors occurred -- nothing needed fixing.

HOW THEY SURVIVE SSH SESSION END (this took real trial and error -- record it):
  Tried and FAILED:
    - `start /b cmd /c ...bat` over ssh: process never actually started (no cargo/
      climb process, no log file appeared even after waiting).
    - PowerShell `Start-Process -FilePath ... -WindowStyle Hidden` (both inline
      -Command and as a .ps1 file run via `powershell -File`): DID start a process
      (confirmed with -PassThru and a captured PID), but that process died partway
      through a 30-second test job with only partial output flushed -- Windows
      OpenSSH's server places remote-spawned processes in a Job Object tied to the
      ssh session, and closing the session tears down the job, killing children,
      REGARDLESS of Start-Process's own detachment flags.
  What WORKED, verified with a 30-second ping test across three separate fresh ssh
  connections (process alive mid-run, log fully written and process gone cleanly
  after completion, all observed from sessions that did not launch it):
    schtasks /create /tn <name> /tr "<path-to-bat>" /sc once /st 23:59 /f
    schtasks /run /tn <name>
  Task Scheduler launches the process under its own service, outside the ssh
  session's job object entirely, so it is unaffected by the ssh connection closing.

  Applied for real as:
    schtasks /create /tn TTAClimb_2p /tr "C:\Users\micro\tta-desk\climb_2p.bat" /sc once /st 23:59 /f
    schtasks /create /tn TTAClimb_3p /tr "C:\Users\micro\tta-desk\climb_3p.bat" /sc once /st 23:59 /f
    schtasks /create /tn TTAClimb_4p /tr "C:\Users\micro\tta-desk\climb_4p.bat" /sc once /st 23:59 /f
    schtasks /run /tn TTAClimb_2p
    schtasks /run /tn TTAClimb_3p
    schtasks /run /tn TTAClimb_4p
  (/st 23:59 is irrelevant for a task launched with /run -- /run fires immediately
  regardless of the scheduled trigger time; the trigger just has to be syntactically
  valid at creation time.)

Verified survival: same three climb.exe PIDs (163916 = 2p, 164568 = 3p,
164132 = 4p) observed alive across THREE separate, later ssh reconnections, with
growing RSS and growing jsonl log files each time -- not the ssh session that
launched them.
