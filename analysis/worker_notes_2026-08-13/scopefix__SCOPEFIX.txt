THE ONE LEAD ACTUALLY CHECKED: "has a military unit" (WeightKey::HasUnit)
--------------------------------------------------------------------------
Task's brief: "A known lead to check FIRST: 'has a military unit' is
reportedly applied everywhere, when it only actually matters during a live
colony auction."

Status: NOT CONFIRMED, NOT REFUTED -- stopped mid-investigation.

What was found:
- features.rs:576-580 sets `WeightKey::HasUnit` unconditionally on every
  `features()` call, off `unit_workers > 0` (unit_workers is the sweep
  total of staffed military-unit workers, sweep_tableau, features.rs:201-208).
  There is no gating on "is a colony auction currently live" anywhere near
  this line, nor on `dc` (`rivals::deferred_credit`, the module's own
  mechanism for pending-decision facts like `AuctionCommitted`/`AuctionBid`
  a few lines below at 605-606).
- weights.rs's own doc comment on `HasUnit => "has_unit"` (weights.rs
  ~552-563) argues this is INTENTIONAL, not a scope bug: "RULES_SPEC 11.3
  cliff... colonizing requires sacrificing at least one military unit 'even
  if other bonuses would cover the bid', so a player at zero units is
  dropped from every aggression/colony auction before it ever reaches a
  decision, and `unit_workers` (linear) cannot express that unit #1 is
  worth far more than unit #5." That argument, taken at face value, is
  that owning >=1 unit is a PERSISTENT eligibility fact (like HasColony,
  WarImmune, WonderInProgress -- all similarly unconditional cliffs set a
  few lines apart in the same function) that matters for as long as it
  holds, not only in the instant an auction is live -- i.e. it reads as a
  deliberate design choice with the same shape as the other cliff features,
  not the SCOPE defect family this audit is hunting.
- RULES_SPEC.md 11.3 confirms the rule itself ("printed strength of the
  sacrificed military units (>=1 unit mandatory...)") but says nothing
  about eligibility being scoped to only the live-auction turn -- the
  eligibility is a standing property of the board (can this player ever
  colonize/aggress right now), matching weights.rs's framing.
- What was NOT done: reading eval.rs to see exactly how HasUnit's
  weight*feature term is combined into the final score, and specifically
  whether there is a SEPARATE decision-context evaluation path (e.g. an
  auction-bid evaluator that should be the only place this fires) that
  `HasUnit` is ALSO being added into outside of -- which is the concrete
  shape the "applied everywhere" complaint would need to have to be a real
  SCOPE bug rather than a restatement of the by-design cliff pattern. This
  is the exact next step for whoever picks this back up: read eval.rs's
  combination logic and grep it for any auction-specific evaluation
  function separate from the main board `evaluate()`, then check whether
  HasUnit's coefficient is asked to serve both roles at once.
