2. STEP 2 -- WEIGHT-VALUE OR STRUCTURE? TESTED, NOT ASSUMED
-------------------------------------------------------------------------
Working hypothesis going in (the brief's own): early strength value is
spread across four entangled coordinates, so no single-coordinate mutation
(all `climb.rs` ever tries in one generation via its `Scatter`/`Group`/
`Rescale`/`Kick` ops) can move behaviour, and only a coordinated multi-
coordinate move -- which the climb essentially never produces -- would fix
it. TESTED, not assumed:

### 2a. Single-coordinate perturbations (each of the 4 zeroed alone)
Baseline (frozen champion, unmodified): 96.7% military-first (n=300,
`behavcensus --games 300 --players 2 --seed 500 --threads 2`; matches the
brief's 97.8% on a different, larger sample).

  variant (one coordinate zeroed)   first-build = Military
  strength -> 0                      95.3%   (barely moves)
  strength_rel -> 0                   0.0%   (COLLAPSES -- 99.0% Mine/Farm)
  strength_rel_early -> 0            96.3%   (barely moves)
  strength_rel_late -> 0              0.0%   (COLLAPSES -- 99.7% Mine/Farm)
  all four -> 0                       0.0%   (99.2% Mine/Farm)

This DISPROVES the strict form of the working hypothesis: a SINGLE
coordinate (`strength_rel`, or `strength_rel_late` alone) is already
sufficient to flip the opening habit completely. `climb.rs`'s ordinary
`Scatter`/`Group` mutations absolutely CAN and do perturb `strength_rel`
alone; there is no unreachable-search-space story here in the naive sense.

### 2b. But does the single-coordinate fix actually WIN?
`arena --a variants/zero_strength_rel.json --b frozen_champion_2p.json
--games 600 --players 2 --seed 900 --threads 2`:

  win rate     7.4%  +/- 2.0   (null 50.0%)   p = 0.0000
  culture      A 26.2   best other 76.3   lead -50.1 +/- 2.6
  verdict      reject -- decisively worse

Zeroing `strength_rel` fixes the opening and is CATASTROPHIC for overall
play (7.4% vs a 50% null, a -50 culture lead). This is the real mechanism,
and it IS a structure problem, just not the one originally guessed:
`strength_rel`'s BASE coefficient (+17.23 in the frozen champion) is a
SINGLE SHARED number that both (a) prices relative strength in the literal
opening, where it should be near zero, AND (b) prices it in the late game,
where a large positive value is genuinely earned (real combat outcomes).
The existing phase-blend mechanism (`w[base] + (1-L)*w[early] + L*w[late]`,
`eval::evaluate`, `PHASE_KEYS`) was SUPPOSED to let `_early`/`_late` carry
the phase-dependent part -- but the base itself is NEVER phase-scaled, it
applies in full at every lateness, at every point in the game. Concretely,
with the frozen champion's own numbers (strength_rel=17.23, _early=-0.195,
_late=5.606): effective value at L=0 (the literal opening) is
17.23-0.195=17.03; at L=1 it is 17.23+5.606=22.84 -- a narrow band, ALWAYS
big, because the phase pair can only nudge, never zero, an always-on base
that dwarfs it.

This is WHY 42,000 generations never found the single-coordinate fix even
though it demonstrably exists and is individually reachable: reducing
`strength_rel` toward zero helps the (small, rarely-decisive) opening
build-choice but ALSO drags the late-game effective value down by the SAME
amount, because both endpoints share the one coefficient -- and late-game
strength genuinely matters (real war outcomes), so the climb's own
win-rate-vs-champion acceptance test rejects every step in that direction
long before it travels far enough to fix the opening, exactly matching
2b's own -50 culture-lead result. The entanglement is real, but it is
ACROSS PHASES within one coefficient's design, not across the four
coordinates in the way originally guessed. Zeroing `strength_rel_late`
alone also collapses the opening (2a) for the identical reason in reverse:
it is the OTHER half of the SAME shared-coefficient problem (it removes the
"late" endpoint's own boost, so the affine blend's slope changes enough
that even the still-present, always-on base isn't enough to keep early
value clearing the mine's own margin in aggregate self-play, where the
comparison compounds over many decisions, not just the one hand-picked
position in section 1).

VERDICT: STRUCTURE problem, precisely: the phase blend is additive-on-top
of an ungated base, when what this ONE coordinate (unlike `Workers`,
`TechLevels`, `HandValue` -- the other three `PHASE_KEYS`, where an
always-on base really is correct) needs is for the base to itself be
phase-gated. A structural fix (making the blend reach genuinely near-zero
in the opening while leaving late-game value alone) is preferred over
hand-tuning `strength_rel_early` to some large negative number, which
would just be re-creating the same always-on-base defect with an extra
digit and would get climbed away exactly as easily as it was set.


3. STEP 3 -- THE FIX (and a real over-correction found and corrected)
-------------------------------------------------------------------------
Files: `rust/src/bots/weighted/eval.rs` (`evaluate`, `linear_features`),
`rust/src/bots/weighted/rivals.rs` (`strength_marginal`, the identical
concept applied to card pricing -- kept in lock-step deliberately, since
two call sites silently pricing the same thing two different ways is
exactly the shape the `card_board_leader` bug already burned this project
once).

New formula for `StrengthRel` only (the other three `PHASE_KEYS` are
untouched): `eff(L) = (1-L) * strength_rel_early + L * (strength_rel +
strength_rel_late)`. The base folds into the LATE endpoint instead of
applying unconditionally; `strength_rel_early` becomes the WHOLE early-game
coefficient, not a delta on the base. At `L == 1` this is BYTE-IDENTICAL
to the old formula (pinned by a dedicated algebraic test, section 4) --
late-game value, and the champion's own late-game training, is untouched.
At `L == 0` it is exactly `strength_rel_early` alone: -0.195 in the frozen
champion, already small, no retuning needed for the structural change
itself to take effect.

### 3a. First attempt: gated by `lateness()` alone -- MEASURED, REJECTED
Applying the new formula unconditionally (scaled continuously by
`horizon::lateness(state)` for the WHOLE game) measured DECISIVELY WORSE:
27.7% +/- 1.5 (n=3000, p<0.0001) against the unmodified champion. Diagnosed
before accepting or discarding: `lateness()` rises gradually across the
ENTIRE game, not just rounds 1-3 -- at `lateness == 0.5` (a genuine
mid-game moment), the new formula prices `strength_rel` at ~11.3 against
the old formula's ~19.9, a ~43% cut to a coordinate the champion's other
~155 weights were tuned assuming stays near its old value THROUGHOUT the
game, not just in the opening. The MineFirst-forcing experiment that
measured +5.2pp only ever restricted the FIRST build decision, then handed
control straight back to the completely unmodified evaluator for the rest
of the game -- my first attempt at a code fix was a much BROADER
intervention than the thing that was actually validated to work, and it
measured accordingly.

### 3b. Refined: gated to `state.round <= 3`
Matches, precisely, the definition of "the opening" this entire task
(OPENINGS.txt, FORCEOPEN.txt, `opening_force.rs`'s own `OpeningTracker`)
already uses throughout. Outside that window the new formula is not
merely close to the old one, it computes the OLD formula verbatim (an
explicit `if state.round <= 3 { new } else { old }` branch in `evaluate`,
`linear_features`, and `strength_marginal`, kept in sync by construction)
-- so nothing about round-4-onward play changes AT ALL. Re-measured in
section 4/5: win rate recovers from 27.7% to 44.1%, an 18.3pp swing from
narrowing the fix's own scope to match what was actually validated,
without touching a single weight VALUE.

Not chased further (see section 6): a still-narrower gate keyed to "no
build has happened yet THIS game" (rather than "round <= 3") would match
MineFirst's own scope even more exactly, but `evaluate` scores STATES via
1-ply lookahead and has no natural "has a build happened" bookkeeping the
way `opening_force.rs`'s stateful `OpeningTracker` does across decisions;
building that in would be materially more machinery for a fix this pass's
budget did not extend to confirming pays for itself.

### 5c. Which do I trust, and why
Both readings are honest and both are real. They disagree because they are
measuring different things: 5a measures whether the mechanism this task
set out to fix is actually fixed (yes, completely, at every player count).
5b measures whether THIS SPECIFIC frozen champion, whose other ~155
coordinates were hill-climbed for tens of thousands of generations while
this exact defect was present, wins more once one coordinate's pricing is
corrected out from under them. The brief's own precedent from today
(a leader-pricing gate that measured 40.2% and was "still right") is
exactly this shape, and I did not just invoke it as a shield: I actively
tested whether the negative result was a REAL co-adaptation cost or a
fixable scoping mistake on MY part (section 3a's diagnosis, then 3b's
narrower gate, which recovered 18.3pp). Having done that and still landing
significantly negative, the honest remaining explanation is co-adaptation:
this ONE frozen snapshot's other weights (leader valuation, wonder
row-scarcity, worker allocation, and everything else the mining pass
`OPENINGS.txt` and today's `SIGNAUDIT.txt` both independently found
mispriced in this exact vector) were never trained against a version of
this bot that opens with a Mine -- correcting the opening changes the
board trajectory those other ~155 coordinates were tuned against, and
34,000+ generations of climbing never had the chance to re-adapt to it.
That is a real cost of THIS vector's specific training history, not
evidence the fix is wrong -- section 1 and section 2 already independently
established, by direct code read and by a live position, that the old
formula is structurally indefensible (an always-on base swamping a phase
pair that exists specifically to let it vary by phase) regardless of how
any one trained snapshot happens to score against it.

I trust the behavioural read (5a) as the direct evidence the mechanism is
fixed. I trust the win-rate read (5b) as an honest, real cost of deploying
this fix against a champion whose OTHER coordinates have not been
re-climbed since -- not as evidence to discard. The remaining candidate
next step (re-running the hill climb FROM this fixed evaluator, letting
the other ~155 coordinates re-adapt to the corrected opening the way they
never got the chance to) is exactly what the brief's own framing predicts
should recover the +5.2pp-class win this mechanism is capable of, and is
out of this pass's scope (a climb run is hours/many generations, not a
single measurement pass).
