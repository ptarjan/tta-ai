BUG 1: uprising (flat 0/1 penalty pinned at the clamp)
--------------------------------------------------------

DIAGNOSIS
Feature computation, rust/src/bots/weighted/features.rs:511 (pre-fix):

    f.set(WeightKey::Uprising, if discontent > f64::from(p.workers_free) { 1.0 } else { 0.0 });

The feature is a bare 0/1 indicator. Weight (weights.rs:481, unchanged):

    Uprising => "uprising", -12.0;

`eval.rs`'s generic `WeightKey::ALL` loop does `total += w[k] * f[k]` for
Uprising like every other flat key, so the ONLY thing the climb can ever do
is set one number that is the penalty of "an uprising happened" -- with no
way to distinguish a catastrophic mid/late-game uprising (large economy, big
production forfeited) from a nearly-free turn-1 one (tiny economy, almost
nothing forfeited). RULES_SPEC.md:181 (6.3) and :378 (item 9) both spell out
that an uprising is not a fixed-size event: "if discontent workers > unused
workers, skip the entire Production Phase (score/corruption/production/
consumption all skipped)". `economy.rs`'s own `end_of_turn` doc comment
(economy.rs:596-628) lists the same steps skipped: 3a science+culture
scoring, 3b corruption, 3c food production, 3d food consumption, 3e resource
production. Since the feature could never carry the size of that forfeit,
the coefficient had to average the true, size-varying cost across every
board size the league ever saw, and the live log shows the climb doing
exactly what an unrepresentable-magnitude bug looks like: pushed all the way
to the clamp and stuck there (`uprising = -60.000 (clamp 60.0) -- pinned
coordinate`, gen 42804, 2p).

FIX (features.rs, in `pub fn features`, "--- happiness" block)
Scale the indicator by the gross production actually forfeited this turn --
the same four `Stats` fields (`s.science`, `s.culture`, `s.food`,
`s.resources`) `economy::end_of_turn` step 3a/3c/3e would otherwise apply to
the player, already read once per call by this same function
(`effects::compute`, features.rs:286) and already guaranteed non-negative by
"Limits on Ratings" (effects.rs:1440-1448, `.max(0)` on all four). This is a
rulebook fact the ENGINE computes -- not a fitted formula: no coefficient of
any kind appears in the magnitude, only the existing Stats reading.

    let uprising_production_at_stake = f64::from(s.science + s.culture + s.food + s.resources);
    f.set(
        WeightKey::Uprising,
        if discontent > f64::from(p.workers_free) { uprising_production_at_stake } else { 0.0 },
    );

Now the same `WeightKey::Uprising` coefficient means "evaluator-value per
point of production actually at stake" at every position, instead of
"the cost of an uprising" averaged over every board size that has ever
happened. `WeightKey::Uprising` keeps its `NonPositive` sign-intent
classification (weights.rs:1025, unchanged) unmodified and still correct,
since the new magnitude is >= 0 by construction, same as `Discontent`/
`StrengthDeficit` beside it.

BUG 2: row_last_copy (weighted composite fed into a second weight)
--------------------------------------------------------------------

DIAGNOSIS
`row::row_last_copy` (rust/src/bots/weighted/row.rs, pre-fix line 485):

    let val = cards::card_potential(name, w, Some(&base), Some(late), &mut scratch);
    ...
    let gone = 1.0 - counting::lookup(outlook, name, 0.0);
    if gone > 0.0 {
        total += val * gone;
    }

`cards::card_potential(id, w, ...)` (cards.rs:1743-1861) is itself a full
weighted composite: every branch of `card_potential_core` returns SOME
learned WeightKey's coefficient times a sub-valuation (`TechBoardCredit`,
`GovBoardCredit`, `ActionBoardCredit`, `WonderBoardCredit`, `UnitTechCredit`,
`TacticBoardCredit`, `AggressionBoardCredit`, `WarBoardCredit`,
`PactBoardCredit`, `EventBoardCredit`, or the generic
`CardBoardCredit`/`CardRateCredit` fallback via `sum_yields`, which itself
dots every printed card yield against its own WeightKey). `eval::evaluate`
(eval.rs:385-388, unchanged by this fix) then multiplies that ALREADY-priced
composite by a SECOND, independent coefficient:

    let rlc = w.get(WeightKey::RowLastCopy);
    if rlc != 0.0 {
        total += rlc * row::row_last_copy(state, idx, w, ctx);
    }

This exact defect is the one `weights.rs`'s own sign-intent audit flagged
and explicitly declined to touch (rust/src/bots/weighted/weights.rs, pre-fix
lines 1154-1158): "`RowLastCopy` is explicitly out of scope for THIS audit's
fix set ('its defect is units, not sign')" -- SIGNAUDIT.txt:514-516 repeats
the same verdict. Because `card_potential(w)`'s composite moves every time
ANY OTHER weight in `w` moves (not just `rlc`), the fitted `rlc` had no
fixed, position-independent price: doubling e.g. `card_rate_credit` doubles
this reading even though `rlc` itself never changed -- "the coefficient has
no consistent meaning" is exactly this.
(Sibling keys `RowUrgency`/`RowBargainForgone`/`HandPotential`/etc. share
`card_potential(w)`'s bilinearity too, but that is DOCUMENTED, ACCEPTED
architecture for those ten "identity-aware" keys, per
docs/BOT_ARCHITECTURE.md:78-84 and docs/AGREEMENT_FIT.md's own "ten
coordinates ... bilinear in the real evaluate" section -- `RowLastCopy` is
the one weights.rs itself already flagged as a genuine defect rather than
an accepted approximation, which is why it is the one fixed here.)

FIX (row.rs, `row_last_copy`)
`card_potential` is still called -- "does the player want this card at
all" is still the right question, and every other caller in this file
(`row_pressure`) gates on it the same way -- but it is now used ONLY as the
existing `> 0.0` filter, never as a magnitude. What is actually summed is
`gone` itself: a deterministic, rulebook-derived probability
(`counting::civil_outlook`) that does not depend on `w` at all.

    let val = cards::card_potential(name, w, Some(&base), Some(late), &mut scratch);
    if val <= 0.0 {
        continue;
    }
    let gone = 1.0 - counting::lookup(outlook, name, 0.0);
    if gone > 0.0 {
        total += gone;
    }

`eval::evaluate` needed NO change: `rlc * row::row_last_copy(...)` is now
exactly one weight (`rlc`) applied to a state-only, `w`-independent
quantity ("count of wanted, about-to-vanish-forever row slots"), so `rlc`'s
learned value means the same thing -- evaluator-value per about-to-vanish
wanted card -- at every position. `weights.rs`'s stale "out of scope" comment
(lines 1154-1158) is updated to record the fix; `RowLastCopy` keeps its
`Free` sign-intent classification (fixing the units did not establish a
sign any rule cites).

TESTS (row.rs, `mod tests`)

   `row_last_copy_matches_the_one_minus_outlook_formula` (renamed): pins
   `row_last_copy(state, idx, w, None) == gone` (not `val * gone`) for a
   wanted "Colossus" in slot 0, computing `gone` independently via

   every caller in this file already has) asserts `row_last_copy`'s reading
   is UNCHANGED. At least one non-gate-flipping perturbation is required to
   exist (`checked > 0`) so the test cannot pass vacuously.
