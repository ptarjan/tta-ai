2. Built a NEW `trailing_now_resources` oracle (twin of the pre-existing `trailing_now_science`
   diagnostic) plus a `REPLAY_DEBUG`-gated "end-turn resources drift" print, mirroring BGO's own
   "N resources (now M)" End Turn clause the same way the culture/science oracles already do.
   FIRST PASS (ungated) showed an enormous, extremely clean-looking signal: 1747 drift instances
   across the 103 Build-illegal games, 614 of them EXACTLY `delta == -3`, and in game 7521765 ALL
   FOUR players showed `delta == -(that round's own printed production rate)` at the SAME round
   (round 4) -- looked, at first, like a systemic "one round's entire resource production gets
   skipped" engine bug.
   THIS WAS A FALSE POSITIVE / DIAGNOSTIC ARTIFACT, NOT A REAL BUG -- ruled out by hand-tracing
   with `REPLAY_DEBUG_ALL=1`: `economy::end_of_turn` legitimately returns early (does none of its
   own steps 2-5, including resource production) when a `DiscardMilitary` choice is still open
   (exactly the situation the EXISTING `pending_culture_check`/`flush_pending_culture_check`
   machinery already exists to defer around for the culture oracle -- I had not read that
   machinery closely enough before adding my own check right next to the pre-existing
   `trailing_now_science` check, which has the SAME undocumented flaw and always has). My new
   resources check read `r.state.players[actor].resources` at the SAME premature moment, before
   the deferred discard resolves and production actually runs -- so it was comparing the PRE-
   production value against BGO's POST-production truth. FIXED the diagnostic itself (not the
   engine) by gating both the science AND resources drift prints on `!matches!(r.state.pending
   .top(), Some(Pending::Choice(c)) if c.kind == ChoiceKind::DiscardMilitary)`
   (rust/src/replay_common.rs, right before the two `if let Some(want) = trailing_now_...`
   blocks). Re-ran: the real signal dropped from 1747 to 71 instances, with a much smaller, more
   scattered delta distribution (22 at +2, 15 at -1, 11 at -3, 11 at -2, 6 at -4, 5 at +1, 1 at
   -5) -- no single dominant sub-cause, consistent with the earlier, SEPARATE scorediv session's
   own finding for score-divergence ("several distinct small causes, not one shared term").
   LESSON FOR THE NEXT WORKER: `trailing_now_science`'s own doc comment ALREADY warned about this
   exact trap ("this fires BEFORE a deferred resume_end_turn ... a discard-blocked turn reads as
   a false 'drift' here") -- read it before trusting either drift check's raw output. The
   `trailing_now_resources` helper and the now-corrected drift check are left in the tree
   (rust/src/replay_common.rs, ~line 2880 for the helper, ~line 5603 for the check) as permanent,
   correctly-guarded diagnostic tooling for the next pass -- same `REPLAY_DEBUG=1` gate the
   science check already uses, zero cost when unset.

WHAT WAS FIXED
============================================================================
File: rust/src/replay_common.rs, function `convert_trade_food_shortfall` (~line 3120, called from
the Build/WonderStep/Upgrade `ActionClass` arms in `apply_one`, ~lines 6459/6493/6603).

BUG: this function converts Trade Routes Agreement's side-A "1 food as 1 resource" grant
(`Move::TradeFoodAsResource`) to cover a build/upgrade/wonder-stage's cost, but the OLD code only
converted however much a naive affordability check said was a genuine SHORTFALL:
    let shortfall = match stated {
        Some(stated) if stated == true_cost => true_cost - p.resources as i32,
        _ => 0,
    };
This is wrong: a real human may use the pact's conversion even when their PLAIN resources alone
already cover the cost (their own choice, e.g. to conserve resources for something else this
turn). CONFIRMED against real game 7521765, round 5: Orange upgrades Philosophy to Alchemy, true
cost 3, journal says `"Orange spends 2 resources; Orange spends 1 food"`, but Orange had 3 PLAIN
resources on hand at that moment -- MORE than the raw cost, no shortfall by the old formula's own
arithmetic (3 - 3 = 0). The old code skipped the conversion entirely and let `Move::Upgrade`
deduct the full 3 straight from `p.resources` (3 -> 0), when the true outcome (per the journal)
is resources 3->1, food 4->3 (2 resources + a food-substituted 3rd resource, leaving 1 real
resource on hand, not 0). This silently drains exactly 1 resource this binary can never recover,
and the drain does not fail AT this line -- it fails several actions later (the very next line in
this specific game: `Move::Build { Warriors }`, needing 1 net resource this binary no longer has),
far from its real cause, which is exactly the cascading-failure shape `spent_food_after_resource`'s
own doc comment already warns about for a sibling bug class.

FIX: convert exactly the food amount the journal ITSELF states was spent
(`spent_food_after_resource(raw_text)`), not a derived "shortfall" -- still gated on the journal's
stated total matching `true_cost` exactly (the pre-existing safety net: never touches game state
when the cost itself looks mispriced), and still bounded by the same two availability checks
(`trade_food_as_resource_remaining` and `p.food`) so an overstated food clause for some OTHER,
unrelated reason still fails loudly rather than fabricating food from nowhere.

Diff shape (see `git diff rust/src/replay_common.rs` if not yet committed, or the commit itself
once landed):
    let to_convert = match stated {
        Some(stated) if stated == true_cost => spent_food_after_resource(raw_text),
        _ => 0,
    };
    ... to_convert <= trade_food_as_resource_remaining(...) && to_convert <= p.food ...

Also carried in this same file (harmless, permanent, REPLAY_DEBUG-gated diagnostic additions, see
item 2 above): `trailing_now_resources` helper + the corrected "end-turn resources drift" check.
