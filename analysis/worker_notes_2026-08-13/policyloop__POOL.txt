--- Claim 1: Seat has no search field ---
CONFIRMED. src/bots/greedy.rs:835-851 (before my edit):
    #[derive(Clone, Copy, Debug)]
    pub struct Seat {
        pub kind: BotKind,

Exactly two fields. `Weights` is `#[derive(Clone, Copy, Debug, PartialEq)] pub struct Weights([f64; N])`
(src/bots/weighted/weights.rs:1037-1038) -- Copy, so Seat is Copy purely because both its fields are.

--- Claim 2: kindmatch enables the hybrid outside Seat/build_bots ---
CONFIRMED. src/bin/kindmatch.rs:363-393 (play_one): builds `seats: Vec<Seat>` and calls the
generic `build_bots(&seats, seed)` UNCONDITIONALLY first, then for any seat with
`--a-search`/`--b-search` set, OVERWRITES `bots[i]` by hand with
`Bot::human_plan(eval_weights, human_weights, player_seed)` -- a `Bot` variant
(`Bot::HumanPlan`, greedy.rs:667-673) built directly, bypassing `Seat`/`build_bots` entirely,
because `Bot::human_plan` needs TWO `Weights` vectors (the human ranking vector AND a separate
gameplay-evaluator vector for `plan::pick`'s beam) and `Seat` only ever carried one. Confirmed by
the doc comment on `Bot::HumanPlan` itself (greedy.rs:656-666): "Seat carries exactly one Weights
slot per seat, already spent... so there is no second slot here for a human ranking vector to
travel through make_bots's generic per-kind construction. Built by hand... bin/kindmatch.rs's
--a-search/--b-search flags are its one caller."
`eval_weights` in kindmatch = "the OTHER side's own weight vector" (kindmatch.rs:385-389), i.e.
whatever `--b-weights`/`--a-weights` resolved to for the non-searching side -- in the measured
65.62% run this was a frozen champion vector. `human_weights` = `human_policy::vector_from_weights(&s.weights)`
where `s.weights` is the searching seat's OWN weights (loaded via `human_policy::load_weights`,
i.e. the human-imitation fit).

--- Claim 3: climb's gauntlet builds seats only through arena::loader_for / Seat ---
CONFIRMED. src/bin/climb.rs Config::gauntlet is `Vec<(String, Seat)>` (line 671). Every
`--gauntlet` entry is resolved (parse_args, ~866-881) as
`a.cfg.gauntlet.push((label, Seat { kind, weights }))` where `weights = loader_for(kind)(&p)?`
(arena::loader_for, arena.rs:54-70, exhaustive match: Human -> human_policy::load_weights, every
other kind -> the champion loader). `measure_gauntlet` (climb.rs:472-487) and `pool_members`
(climb.rs:516-522) both consume `cfg.gauntlet` as plain `Seat`s and feed them straight into
`measure_against` -> `Match { a, b, .. }` -> `arena::build_bots(&seats, seed)`. There is no path
from `--gauntlet`/`--gauntlet-kind` to `Bot::human_plan`/`Bot::HumanPlan` at all today: a `Seat`
with `kind: BotKind::Human` always becomes a plain searchless `Bot::Human` (greedy.rs build_bots,
`BotKind::Human => Bot::Human(HumanBot::new(&seat.weights))`). So the claim is correct: the
strongest opponent (65.62% hybrid) is structurally unreachable from climb's gauntlet/pool veto as
the code stood at HEAD (d04acfa in the source tree this clone started from).

=== step 2: Seat/Search construct ===

Added `bots::greedy::Search` (Clone/Copy/Debug/PartialEq enum):
    None
    HumanShortlistBeam { eval_weights: weighted::weights::Weights }
`Seat` gained a third field `search: Search`, stays `Copy` (Weights and Search are both
Copy). `build_bots` asserts up front that `HumanShortlistBeam` only ever rides a
`BotKind::Human` seat (panic with a clear message otherwise) -- this is NOT fully
type-unrepresentable (that would need `BotKind` to stop being the fieldless, `Copy`,
`Hash`-able registry key `BotKind::ALL`/`from_str`/`name` all depend on), so it is the same
"checked once at the boundary (the flag parser), trusted after" shape this file already uses
elsewhere (`Match::validate().expect(...)`, kindmatch's own `--a-policy` kind check). Both
flag parsers that can construct a `HumanShortlistBeam` seat (`kindmatch.rs`'s
`--a-search`/`--b-search`, `climb.rs`'s new `--gauntlet-search`) validate the combination
before it is ever assembled.

`kindmatch.rs`'s `--a-search`/`--b-search` now build the seat's `search` field UP FRONT and
call the ordinary `build_bots` -- the old "build every seat plain, then overwrite bots[i] by
hand with Bot::human_plan" loop is GONE. `--a-policy`/`--b-policy` (needs an `Arc<ValueNet>`,
not `Copy`-friendly) is untouched, still its own hand-built path -- out of scope, task only
asked to unify the search-hybrid flags.

`climb.rs` gained `--gauntlet-search PATH`: applies to the NEXT `--gauntlet` member only,
same deferred-resolution shape as `--gauntlet-kind` (a `pending_gauntlet_search: Option<PathBuf>`
alongside `pending_gauntlet_kind`). Rejected at parse time if that member's resolved kind is
not `human`. `eval_weights` is read with the CHAMPION loader (`bots::weighted::eval::load_weights`,
dominance_repair included) -- it is a real gameplay evaluator for `plan::pick`'s beam, not a
human-imitation ranking vector.

=== step 4: pool-veto measurement ===

Question: with the human+search hybrid (`Search::HumanShortlistBeam`, ROOT_SHORTLIST=8,
plan::pick beam, default max_nodes=4000) as a `--gauntlet`/pool member instead of the plain
searchless `HumanBot`, does the pool veto (`Anchor::clearly_worse_than`: disjoint 90% CIs at
`pool_games=60`) reject essentially every mutant candidate, freezing the climb?

Method: a temporary #[ignore]-marked test in climb.rs (`measure_pool_veto_pass_rate_against_
the_human_search_hybrid`, DELETED before landing -- this is a one-off measurement, not a
correctness pin) generated 15 real mutants of a real 2p champion via climb's own `mutate`
function at sigma=0.25 (the climb default initial step), then measured EACH of the SAME 15
mutants (paired, not resampled) plus the champion itself ("incumbent"), each at pool_games=60
(the production default), against three opponent seats in turn: `anchor` (built-in default
weights, cfg.kind=weighted -- what the anchor veto already uses), `plain_human` (the
searchless HumanBot the gauntlet uses today), and `hybrid_search` (the new
Search::HumanShortlistBeam seat, eval_weights = the same champion vector). threads=2 throughout
(box-sharing rule).

Attempt 1 (DISCARDED, see below) used `analysis/frozen/champion_2p.json` as both the
champion-under-test and the hybrid's eval_weights. That file turned out to be the STALE
78-key, gen-220, 2026-07-26-era vector `analysis/frozen/README.md` explicitly warns is not
representative of the current bot ("do not read them as describing the current bot") -- it
lost EVERY SINGLE game (0.000 +/- 0.000, a literal 0/60) to the hybrid, and every one of the
15 mutants also lost 94-100% of their games to it. That is a degenerate floor effect (you
cannot be "clearly worse than" an incumbent that already lost 100% of its games -- 0 vetoes
fired for that opponent for a reason that says nothing about the hybrid, only about the stale
reference vector). This result (lines just below this note in the raw log) should be
disregarded; recorded here only so the mistake and why it was wrong are not silently lost.

Attempt 2 (the real answer) used `analysis/frozen/gauntlet/champion_2p_gen19554_140key_2026-08-08.json`
-- the 140-key, gen-19554, 2026-08-08 "LATE" cut `experiments/rust_league.sh` already feeds
every live arm's own gauntlet (`GAUNTLET_2P_LATE`), and the date that matches this project's
own "measured 2026-08-08" 65.62% hybrid-vs-champion figure this whole task started from --
for both the champion-under-test AND the hybrid's eval_weights. Results (full per-candidate
detail is the second `--- opponent=... ---` block above, appended by the test itself):

    opponent        incumbent win rate      vetoes / 15 candidates
    anchor          75.8% +/- 11.1%         1/15  (6.7%)
    plain_human     87.5% +/- 9.4%          0/15  (0.0%)
    hybrid_search   67.5% +/- 10.7%         1/15  (6.7%)

Findings:
1. The hybrid does NOT reject essentially every mutant. Its veto rate (1/15, one candidate)
   is indistinguishable from the anchor's own rate (1/15) on the SAME 15 candidates, and both
   are well short of "always fires" -- 14/15 candidates PASSED against the hybrid.
2. It is not a floor effect this time either: the champion (a real, current, 140-key,
   gen-19554 vector) wins 67.5% of its games against the hybrid -- a real, live contest, not
   a wipeout in either direction. (The 65.62%-hybrid-wins figure this task cites was measured
   against a DIFFERENT, presumably earlier, champion snapshot on 2026-08-08 -- the live
   champion moves ~9,000 generations between the "early" and "late" 08-06/08-08 gauntlet cuts
   per `analysis/frozen/gauntlet/README.md`'s own account of a nearly identical reversal for
   the 3p arm, so two measurements days or generations apart landing on opposite sides of 50%
   is exactly the kind of drift that README already documents, not a contradiction in this
   measurement.)
3. The ONE candidate the hybrid vetoed (candidate #12: 35.8% vs the champion's 67.5%) is the
   SAME candidate the anchor also vetoed (30.0% vs the champion's 75.8%) -- both opponents
   agree it is a genuinely bad mutation, not two independent false positives from noise. The
   `plain_human` opponent almost caught it too (67.5% vs its own incumbent's 87.5%) but the
   interval was 1.9 points too wide to be disjoint -- consistent with this file's own module
   doc comment on the two-stage veto being generally underpowered at pool_games=60 (that is
   a property of the STATISTICAL TEST at n=60, true for every pool member, not specific to
   the hybrid).
4. n=15 is a pilot, not a large sample -- but the fact that its anchor-vs-hybrid veto rates
   land on the SAME count (1/15 each) on the SAME paired candidates, and that production's own
   already-live anchor veto is independently known to fire "zero times across 2,075 real
   generations" (this file's module doc comment, section 2) -- i.e. rare but nonzero over a
   much bigger sample -- means this pilot's magnitude is not an outlier against known
   production behaviour for an ordinary, already-trusted pool member.

Recommendation: wire `--gauntlet-search` into production (`experiments/rust_league.sh`'s three
`climb` invocations are OUT OF SCOPE for this task/clone -- that file lives outside `rust/` and
the task said centre changes on greedy.rs/arena.rs/climb.rs; recommending the exact flags is as
far as this task goes) as an ADDITIONAL gauntlet member alongside the existing ones, e.g.:

    --gauntlet-kind human --gauntlet-search analysis/frozen/gauntlet/champion_2p_gen19554_140key_2026-08-08.json \
        --gauntlet analysis/frozen/human_weights.json

using the EXISTING, UNCHANGED default thresholds (`--pool-games 60`, `--pool-confirm-games 300`,
`POOL_CONFIRM_TRIGGER = -0.05`, `--accept-z 1.2816`) -- no new threshold or scoring change is
justified by this measurement. The existing two-stage disjoint-CI design already treats the
hybrid the same as every other pool member and produces a comparable, non-freezing veto rate;
inventing a hybrid-specific threshold would be exactly the "silently pick a threshold and ship
it" the task says not to do, and the data does not support one being necessary. Keep the plain
searchless `--gauntlet` human member too (do not replace it) -- the pool veto's whole design
principle is diversity of opponents, and losing the cheap, already-informative searchless
member for the more expensive hybrid buys nothing.

=== summary ===

Verified (step 1): Seat had exactly {kind, weights}, no search field. kindmatch's
--a-search/--b-search bypassed Seat/build_bots entirely via a hand-built Bot::human_plan
