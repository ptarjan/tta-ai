CENTRAL FINDING (2026-08-13, confirmed empirically before writing any new
code): all 17 effects are ALREADY priced by existing machinery. No new rider
functions, no new WeightKeys were needed. Here is why.

  * Every carrier card for all 17 keys is a Leader or a Wonder (never an
    Action/Tech/Government/etc).
  * `effects::compute` (rust/src/effects.rs:1324) calls
    `apply_special(&mut stats, p, sp)` for EVERY `Special` on the player's
    government, tableau, wonders, leader, and colonies -- and
    `apply_special` (effects.rs:980) already has a correct, well-commented
    match arm for every one of the 17 Special variants (CulturePerTheater,
    CulturePerLabEqualToLevel, SciencePerLab, CulturePerLibraryTheaterPair,
    CulturePerHappyFromTemplesTheatersWonders, BestTheaterDoubleCulture,
    SciencePerBestLabOrLibraryLevel, ResourcesPerLabEqualToLevel,
    DoubleBestMine, ExtraHappyPerHappySource, StrengthPerInfantry,
    StrengthPerArtillery, StrengthPerMilitaryUnit, StrengthPerUnitType,
    StrengthPerTempleOrGovernmentHappy, CultureFirstColony,
    CulturePerAdditionalColony) -- each folding straight into
    `Stats.culture`/`.science`/`.strength`/`.resources`/`.happy`.
  * `board_yields::board_yields` (board_yields.rs:778) already runs a
    GENERIC swap diff for any Leader/Government/Wonder: clone the player,
    swap the card in, `effects::compute` the clone, and `delta_triples`
    (board_yields.rs:353) reads `STATS_FEATURES` (culture -> CultureRate,
    science -> ScienceRate, strength -> Strength, resources -> ResourceRate,
    happy -> HappyMargin, ...) before/after. Since `apply_special` already
    wrote the board-scaled contribution into those exact `Stats` fields, the
    diff picks it up with ZERO extra code -- exactly the same path a leader's
    flat printed `effects.culture` goes through.
  * `card_potential_core` (weighted/cards.rs:1730) dispatches Leader cards
    through this generic path when `WeightKey::CardBoardLeader != 0.0`, and
    Wonder cards through the same `board_yields::board_yields` call when
    `WeightKey::WonderBoardCredit != 0.0` (cards.rs:1758-1781). Both credits
    are live coordinates the hill climb already trains.

Bug found and fixed while doing this: disabling StrengthPerMilitaryUnit
initially left alexanders_strength_scales_with_total_military_units GREEN
(a false pass) because the test only asserted `strength_at(&s4) == 2.0 *
strength_at(&s2)` -- with the arm disabled both sides went to 0 and the
tautology "0 == 2*0" passed. Same bug in
napoleons_strength_scales_with_distinct_unit_types, which compared a value
to `.max(0.0)` of ITSELF (always true). Fixed both by adding an explicit
`assert!(... > 0.0, ...)` before the ratio check; re-ran with the arm
disabled again and got the real failure shown above. Committed separately
(6ce8e00) since it was found and fixed after the main commit landed.

Other 12 board-scaled tests were not individually RED-confirmed by
disabling their own apply_special arm (budget), but all assert a strict
scaling relationship (either an exact multiple, or a `>` between two
distinct board configurations, all with an explicit nonzero floor after
the tautology sweep above) against a REAL board-derived value pulled out
of `board_yields()`'s actual return -- not a hand-computed expected
constant that could silently drift from the rule. The tautology bug found
above was specific to the two "> and self-referential" test shapes; the
rest use either an exact `assert_eq!` against an independently-derived
expected value (e.g. `movies.get().production.culture as f64`) or a
strict inequality between two non-identical scenarios, neither of which
can pass on an accidental 0.
