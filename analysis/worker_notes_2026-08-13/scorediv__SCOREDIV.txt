IMPORTANT SIDE FINDING: the grounding-order "recovery" mechanism WORKS CORRECTLY
============================================================================
I initially suspected a structural bug: `finish_game`'s embedded `events::evaluate_final_events`
call can fire while `state.current_events`/`future_events` still hold the FICTIONAL simulated
pile, when BGO's journal logs the true final "End turn" line (which triggers
`game::advance_turn`'s round-wrap -> `finish_game`) BEFORE its own "End of game" marker line (the
line `ground_final_events` reads to correct the pile) -- confirmed this ordering for 8/28
diverging games (7522822, 7522906, 7521790, 7521789, 7522768, 7522813, 7523149, 7523102) via:
  eog_lineno=$(grep -n "End of game" journal | tail -1 | cut -d: -f1)
  lastend_lineno=$(awk -F'\t' '$5 ~ /^End turn/ {print NR}' journal | tail -1)
  # "BEFORE(suspect)" when lastend > eog is false

BUT: rust/src/replay_common.rs's existing `if r.state.game_over { if !completed { ... } }` recovery
block (around line 5355-5410, see its own doc and the
`replay_game_completes_a_journal_whose_duplicated_end_turn_pair_is_logged_before_its_own_end_of_
game_marker` test) is SPECIFICALLY DESIGNED for exactly this case and, on direct trace of game
7522906 (added temporary eprintln! probes, now removed), DOES correctly: (1) undo the wrong
fictional-pile award via a direct `final_event_awards` diff-and-subtract, (2) ground the piles from
the journal's real "End of game" line, (3) re-run `evaluate_final_events` against the corrected
pile. Hand-verified game 7522906's arithmetic end to end: baseline(98) + Bill Gates(+9, applied
once, correctly, during the premature finish_game since it does not depend on the event pile) +
[undo wrong Industry/Agriculture/Competition award] + [redo correct Colonies/Happiness/Balance
award] reproduces the engine's actual output (138) exactly, and the ONLY remaining gap from the
true index value (140) is the SAME "Impact of Happiness" formula bug named above (engine's
Colonies/Happiness/Balance redo computes Happiness as 14 instead of the journal's 16 for that
seat) -- not a grounding-order defect. CONCLUSION: the grounding-order mechanism is not a live bug
and should NOT be touched; my initial hypothesis was wrong and is recorded here so nobody
re-investigates it.

UPDATE: Homer/Ravages root cause CONFIRMED, fix ATTEMPTED, REVERTED (regression)
============================================================================
After the disk-space outage cleared, root-caused the Impact-of-Happiness divergence precisely:
`effects::compute`'s wonder loop (rust/src/effects.rs, the `for &w in p.completed_wonders...`
loop around line 1385) `continue`s past a FLIPPED (Ravages-of-Time'd) wonder BEFORE checking
`if p.homer_wonder == w { stats.happy += 1; }` -- so Homer's own leader ability (hosted on that
wonder, granting +1 happiness) gets silently voided when the wonder is later ravaged, even though
Ravages of Time's own text ("these wonders lose THEIR effects") only voids the WONDER's own
printed effects, not a leader's ability merely hosted there. Separately, `effects::happy_source_
count` (St. Peter's Basilica's own "extra happy per happy source" doubling bonus) counts a
Homer-boosted wonder as a qualifying "happy source" via `card.effects.happy > 0 || p.homer_wonder
== w` -- double-crediting Homer's already-direct +1 into St. Peter's multiplier too.

Hand-verified BOTH fixes' arithmetic against 4 real games bit-for-bit (7522625, 7522277, 7522906,
7522722 -- the last being the Impact-of-Population divergence, which is downstream of the SAME
`s.happy` bug via `economy::discontent`), and a 6-game spot-check after applying both fixes showed
4/6 newly EXACT (7522625, 7522277, 7522906, 7522722), confirming the root cause precisely.

HOWEVER: a full-corpus re-measurement (bash experiments/measure_replaystats.sh) after applying
both fixes showed this is NOT a safe, isolated change:
  - n_completed DROPPED from 289 to 287 (2 games that used to replay to completion no longer do
    -- WORSE than a score divergence, since `effects::compute` is read throughout ordinary play
    (uprising checks, legal-move stats), not just at final scoring, so changing it can change
    which moves the replayer considers legal partway through a game with a flipped Homer wonder).
  - The diverging-ID set gained 3 NEW entries not present in the BEFORE set: 7522221, 7523162,
    7523562 -- a violation of the strict-subset discipline (SCOREDIV_DIVERGING_ID after minus
    SCOREDIV_DIVERGING_ID before must be empty; it was not).
  - 5 games left the diverging set as intended (7522625, 7522277, 7522906, 7522722, and 7521790).

Per this task's own explicit rule ("a fix that improves the mean while breaking a previously-
correct game is a regression and must be reverted"), and the even stronger case of 2 games
regressing from COMPLETING to not completing at all, BOTH edits were REVERTED in full (rust/src/
effects.rs is back to its base0814 original on both the wonder-loop and `happy_source_count`
hunks -- verify with `git diff HEAD~1 -- rust/src/effects.rs`, which should show ONLY a pure-
addition diagnostic dump block, no logic changes). The commit landed (e93f079) contains ONLY the
oracle/tooling additions, which are read-only and carry no regression risk (`cargo test
--profile difftest --lib`: 1353 passed, 0 failed, confirming this).

The 2 newly-non-completing game IDs from the attempted fix were NOT identified before the
coordinator's wrap-up instruction arrived (would have required a second full corpus run with an
"all completed IDs" dump, which was not built) -- see REMAINING.txt's top item for exactly how to
find them without redoing the investigation.

WHY THIS MATTERS FOR THE NEXT PASS: the root cause is very likely correct (the arithmetic matches
4 real games exactly, card-text-grounded), but `effects::compute` is a shared, hot-path function
read by ordinary gameplay legality, not scoring-only -- so a fix there needs the SAME subset-
discipline check applied to REPLAY COMPLETION (not just score-exactness) before it can ship. See
REMAINING.txt for the precise, minimal next step (most likely: the fix is right for FINAL SCORING
specifically, but something about how a flipped-Homer-wonder's happiness feeds into IN-PLAY
`economy::uprising`/legal-move reconstruction for those 2 games conflicts with an existing
replayer approximation elsewhere -- find and reconcile, or scope the happiness fix to only the
`finish_game`-time read if it turns out the mid-game reading was already deliberately different
for a documented reason).
