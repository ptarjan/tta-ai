TOP 3 REASONS BY VOLUME -- dug in, classified (a)/(b)/(c), concrete examples

### 1. IllegalMove, 456 games (57.8%) -- (b) genuine gap in the replayer's/
###    engine's own RULES MODELING, not "replay failed" and not log noise.

Did not re-derive from scratch -- this project's docs/REPLAY.md already has
an extensive, dated trace of the largest sub-bucket (`Build`, 104 games
current count) from a prior pass (docs/REPLAY.md line ~5005). Quoting its
own conclusion rather than re-deriving: of that pass's 102 `Build` games,
62 were `resources_short` (this reconstruction's own `p.resources` is 1-3
short of `build_cost_for(card)`, even though the build's own COST is
correctly computed). Traced end-to-end on game 7522886, cross-checked
against THREE independent numbers (a running "(now N)" total, the
following round's own spend lines, and the event's own journal text): the
root cause is that `events::food_or_resources` (the "strongest/weakest
civilization loses/gains N food and/or resources" event block, e.g.
Raiders/Foray/Crime Wave/Refugees) is coded as a FIXED deterministic
formula ("drain resources first"), but BGO's own journal text says
"<Color> CHOSES first" and the actual per-player resolutions
(e.g. "Orange spends 2 food" [all food] vs "Green spends 1 food; Green
spends 1 resource" [a 1/1 split] for an IDENTICAL "lose 2" block) prove it
is a real, independent PER-PLAYER CHOICE the replayer currently guesses
wrong. Concrete example: game 7522886 (round 6-7, Orange). Extrapolated
(not fully proven per-instance): ~50 of that pass's 62 `resources_short`
games have a Foray/Raiders/Crime Wave/Refugees event in their own journal,
so this ONE mechanism plausibly explains roughly half of the `Build`
sub-bucket alone, and likely leaks into `Upgrade`/`Develop`/`WonderStep`
too (same resource-shortfall shape). NOT fixed by that pass or this one --
a correct fix needs a new `Pending::Choice` kind (self-directed
food/resources split, mirroring the existing `PlunderSplit` machinery),
explicitly documented there as "larger than one pass's remaining budget
could safely implement AND confirm-by-revert-test in one sitting" -- I
agree with that assessment and did not attempt it.

### 2. StuckPending, 228 games (28.9%) -- (b)/(c) mix, ALSO already deeply
###    traced across many prior passes, NOT log noise, NOT expansion content.

Dominant sub-bucket, current count 101: "decider # != expected actor #,
phase Actions, no pending". docs/REPLAY.md (line ~7548 onward) already
root-caused this at length across several passes, not re-derived here:
the MAJORITY shape (originally 199/241 games in that pass's own numbering)
is a downstream SYMPTOM of a hand-military-SIZE undercount at end-of-turn
(the same disease this doc's discard-phase-oracle and military-hand-ledger
sections track elsewhere) -- this reconstruction's own simulated hand is
smaller than the real human's, so no discard `Pending::Choice` ever opens,
the turn silently completes, and the NEXT journal line (the human's real
forced discard) finds `decider()` already moved on to the next seat.
Two concrete, CONFIRMED ENGINE bugs behind slices of this were found and
fixed by prior passes (both already landed in this checkout, which is why
today's count, 101, is lower than the doc's own historical 199/241/220
numbers): a missing military-actions top-up when a pact granting them is
ACCEPTED mid-turn (commit 652c37c, cut the bucket 241->106 corpus-wide),
and `LosePop`'s same-line fast path only recognising "destroys", never
"disbands" (cut 241->220). At least two more confirmed-but-UNFIXED
mechanisms remain, named with game IDs in docs/REPLAY.md: `set_government`'s
peaceful-change formula gives back too few tokens on a DECREASE (RULES_SPEC
Sec8.2's "spent first" isn't honoured -- concrete numbers given on game
7523357 round 10), and a pre-round-13 hand-size drift on game 7523354 not
yet isolated to a specific event. Concrete example for THIS bucket today:
game 7523354 line 251 (round 14, Purple) -- "Purple discards 1 card" stall.
Category: genuine ENGINE/replayer modeling gaps, several already fixed,
more open -- never a property of the log itself.

### 3. TruncatedAfterGameOver, 68 games (8.6%) -- NEW THIS PASS -- (b), a
###    clean, narrow, well-understood gap in replay_common.rs's OWN
###    completion bookkeeping, not a rules bug and not a log-truncation.

Every one of these 68 journals DOES contain a real "End of game" text
marker later in the file -- these are NOT resignations or abandoned games
(the pre-existing code comment guessed "some journals end mid-stream, e.g.
a resignation"; measured, that guess is wrong for all 68). Proven
structurally, not just eyeballed on one example:
  - For all 68 dropped games: the "End of game" line's own line number is
    STRICTLY GREATER than the last "End turn" line's own line number.
  - For all 222 currently-completed games (control group, same measurement):
    the opposite holds in every single case -- "End of game" comes BEFORE
    the last "End turn" line.
  0 exceptions in either direction, either group (measured with grep -n over
  every one of the 1011 journal files, see commands below to reproduce).

    for id in $(cut -f1 /tmp/leaf_dataset.tsv | tail -n +2 | sort -u); do
      f=/tmp/bgo-journals/journals/$id.tsv
      eog=$(grep -n "End of game" "$f" | head -1 | cut -d: -f1)
      let=$(grep -n "End turn" "$f" | tail -1 | cut -d: -f1)
      [ "$eog" -lt "$let" ] || echo "UNEXPECTED: $id"   # prints nothing
    done

Root cause, traced on game 7522663 (2p) with a temporary per-line trace
print (added, used, then reverted -- not shipped, `git diff` confirms
replay_common.rs has zero net changes): BGO logs its final turn's
end-of-turn TWICE (a documented, already-handled quirk -- see
replay_common.rs's own long comment above the "End of game" branch). The
FIRST duplicate "End turn" line genuinely triggers `game::advance_turn`'s
round-wrap check, which calls `finish_game` and flips `r.state.game_over`
to true for real, correctly. `replay_game`'s loop has a guard,
`if r.state.game_over { break; }`, an UNLABELED `break` (so it does not
show up in a `grep "break 'lines"` audit -- I exhaustively checked all 18
labelled `break 'lines` sites and confirmed every one of them sets
`mismatch` first; this one is the ONLY unguarded exit and it is exactly
what fires here) -- placed to stop the SECOND duplicate "End turn" line
from being replayed against an already-finished game. For these 68 games,
that guard fires on the second duplicate line, one line before the file's
own "End of game" marker is ever reached -- so `completed` (which is ONLY
ever set by literally reading that marker's text) stays false, even though
the engine's own authoritative `state.game_over` is already true and
correct. The code's existing big comment (~replay_common.rs line 5256)
explicitly assumes "BGO logs that marker BEFORE the true last turn's own
end-of-turn processing" -- true for 222/222 of the currently-working
games, false for all 68 of these.
Category: (b), a narrow, deterministic gap in this ONE file's own
completion bookkeeping -- not a rules/engine bug (the real game state is
computed correctly), not a parser gap (every line here parses fine), and
definitely not a property of the source log (the log contains a perfectly
good "End of game" line every time, just one line later than this file's
completion check currently tolerates).

THE PRIZE -- HYPOTHESISED, fix NOT applied this pass
--------------------------------------------------------------------------
TruncatedAfterGameOver is, by a wide margin, the cheapest of the three
reasons above to fix: the other two (IllegalMove/Build's food-or-resources
choice, StuckPending's remaining hand-size-undercount mechanisms) are
already-open, multi-pass efforts in docs/REPLAY.md needing new engine
Pending::Choice machinery or further hand-tracking archaeology -- neither
is "small and obviously safe" for one sitting. TruncatedAfterGameOver's fix
IS narrow in scope (touches only the post-loop completion check in
replay_game), but is NOT a one-line flip either, which is why I did not
attempt it:

Naively setting `completed = true` whenever the loop's `game_over` break
fires (mismatch none) would skip `ground_final_events` -- the step that
grounds the SET of Age III events actually scored, read off the "End of
game" line's own text (`parse_real_final_events`), which this file's
existing "Final scores" section (docs/REPLAY.md) already shows is NOT
always a no-op even on the currently-working 222 (202/222 exact score
matches, 20 games off by 1-16 points, some already traced to exactly this
kind of event-set drift). A correct fix needs the game_over break to first
PEEK at the still-unconsumed remainder of the journal for the "End of
game" line (it is always there for these 68, always within 1-2 lines), run
the same grounding that branch already does, THEN set completed=true --
small in scope, but needs its own before/after score cross-check (the same
kind replaystats.rs already runs) before trusting it, which is a full
follow-up pass's worth of verification, not a same-sitting addition.
