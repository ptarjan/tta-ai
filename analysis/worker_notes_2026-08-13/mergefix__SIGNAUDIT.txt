SIGNAUDIT -- weight-sign structural audit
===========================================
Scope: rust/src/bots/weighted/weights.rs (WeightKey, 162 variants before this
audit, 159 after 3 retirements), eval.rs (dominance_repair and its gate
tables), cards.rs (card_potential_core / board_credit_key), bin/climb.rs
(the hillclimb mutation-time guard).

Why this exists: three sign-inversion bugs of the identical shape
(card_board_leader, card_board_wonder's dead gate, hand_value_early) were
found in one day. The project owner asked for a structural fix, not a
fourth patch. Sections below, in order:

  (1) THE HEADLINE NUMBERS
  (2) THE STRUCTURAL FIX (part C of the task)
  (3) INSTANCE 2 FIX -- retiring card_board_wonder/government/action
  (4) INSTANCE 3 FIX -- hand_value_early/late
  (5) TWO NEW BUGS FOUND BY THIS AUDIT (pop_cost, tactic_gain/tactic_short)
  (6) FULL AUDIT TABLE (part A)
  (7) CORPUS DAMAGE -- how many champion snapshots on disk violated each gate
  (8) VERBATIM RED TEST FAILURES
  (9) FULL TEST SUITE RESULT
  (10) WHAT WAS NOT DONE / FOLLOW-UPS


(1) THE HEADLINE NUMBERS
-------------------------
- 162 WeightKey variants audited.
- 31 were ALREADY correctly sign-gated before this audit (from the prior
  card_board_leader fix's tables: BENEFIT_GATES, SHORTFALL_GATES, LOSS_GATES,
  WONDER_DEBT_GATES, PERISHABLE_GATES, REDUNDANCY_NONNEG_GATES,
  STOCK_NONNEG_GATES, WONDER_VALUE_GATES).
- 5 NEW simple sign gates added this audit: TacticGain (NonNegative),
  TacticShort and PopCost (NonPositive), plus HandValue's phase pair joining
  the existing (empty) NET_NONNEG_PHASE composite mechanism.
- 3 WeightKey variants RETIRED (removed from the enum entirely, unrepresentable
  from here on): CardBoardGovernment, CardBoardAction, CardBoardWonder -- each
  was permanently dead code, shadowed by a dedicated pricing function that
  intercepts first.
- 5 keys are Free at the simple-per-key level but constrained by a COMPOSITE
  mechanism (a sum or a phase-net), unaffected in direction by this audit:
  CardBoardLeader, CardBoardBonus (existing), HandValue/HandValueEarly/
  HandValueLate (new, this audit).
- 120 keys are classified Free (a genuine trade-off/preference the league
  prices empirically, or a coordinate this pass could not establish a
  rules-forced direction for -- see section 6 and 10).
- Structural guard: every WeightKey variant now MUST be classified by
  WeightKey::sign_intent(), an exhaustive match with no wildcard arm. Adding
  a 163rd variant without extending that match is a Rust COMPILE ERROR, not
  a silent gap a hand-typed list could leave open.


(2) THE STRUCTURAL FIX (part C)
---------------------------------
File: rust/src/bots/weighted/weights.rs

Added `SignIntent` (an enum: NonNegative(&'static str), NonPositive(&'static
str), Free) and `WeightKey::sign_intent(self) -> SignIntent`, a single
exhaustive `match` over all 159 live WeightKey variants, with NO trailing
`_ =>` arm -- same shape as the pre-existing `WeightKey::group()` (which this
audit used as its literal precedent) and the pre-existing
`DELIBERATELY_UNPRICED`/`PRICED_ELSEWHERE` "every printed card effect is
either priced or explicitly declared unpriced" pattern in cards.rs (the
precedent named in the task brief). The reason string travels WITH the
classification (not a second, parallel lookup table), so direction and
diagnostic text can never drift apart.

Consequence: adding a 163rd WeightKey variant and forgetting to classify it
is a `cargo build` failure -- "non-exhaustive patterns" -- at the exact
line `sign_intent()` lives on, not a silent gap five months and one lost
league run later.

File: rust/src/bots/weighted/eval.rs

The EIGHT hand-typed `&[WeightKey]` lists that used to exist here
(BENEFIT_GATES, SHORTFALL_GATES, LOSS_GATES, REDUNDANCY_NONNEG_GATES,
STOCK_NONNEG_GATES, WONDER_DEBT_GATES, PERISHABLE_GATES, WONDER_VALUE_GATES),
fed into two wrapper tables (NON_POSITIVE_GATES / NON_NEGATIVE_GATES) that
`dominance_repair` and `bin/climb.rs`'s under-mutation guard both iterated,
are DELETED. In their place: two functions,

    pub fn non_positive_gates() -> impl Iterator<Item = (WeightKey, &'static str)>
    pub fn non_negative_gates() -> impl Iterator<Item = (WeightKey, &'static str)>

which simply filter `WeightKey::ALL` through `k.sign_intent()`. There is
exactly ONE place left to edit a key's sign classification (`sign_intent`'s
match in weights.rs); `dominance_repair` and `bin/climb.rs`'s guard both read
these two functions directly, not a copy, so a reclassification is armed at
load time AND mutation time automatically -- confirmed by a NEW climb.rs test
rather than assumed (section 8).

This is exactly the failure this task was opened to close: card_board_leader
was gated in ONE table (BENEFIT_GATES, on card_board_credit) while its actual
effective sign lived in a DIFFERENT, ungated coordinate
(card_board_leader) -- a hand-typed list is a classification a new variant,
or a variant nobody thought to add to the RIGHT list, can silently miss.
There is now exactly one classification per key, checked by the compiler for
completeness, not by a human remembering to update eight lists.

The composite mechanisms (NET_NONNEG_PHASE, the card_board_credit_keys()
per-type-offset sum, DOMINATES orderings) are NOT folded into sign_intent --
they are relational constraints between TWO coordinates, not a single key's
sign, and forcing them into a 3-way per-key enum would either be wrong
(over-constraining a base term that is legally negative as long as the SUM
isn't) or would need a 4th enum variant carrying a second WeightKey, which is
more machinery than the two cases in this codebase justify. Both existing
composite mechanisms are left in place, extended by the addition of a new
member (HandValue) using the EXISTING NET_NONNEG_PHASE array precedent
per the task's own instruction to extend rather than duplicate.


(3) INSTANCE 2 FIX -- retiring card_board_wonder/government/action
----------------------------------------------------------------------
The task named card_board_wonder as unreachable. Auditing `cards.rs`'s
`card_potential_core` dispatch chain found the identical shape applies to
TWO MORE keys the task did not name:

    kind.is_government() -> if gov_board_credit != 0.0 { return gov_value(...) }
    kind.is_action()     -> if action_board_credit != 0.0 { return action_value(...) }
    kind == Wonder        -> if wonder_board_credit != 0.0 { if let Some(swap)=... { return ... } }

`board_credit_key(id)` used to return `Some(CardBoardGovernment)` /
`Some(CardBoardAction)` / `Some(CardBoardWonder)` for these three types, an
OFFSET the generic swap-diff fallback at the bottom of `card_potential_core`
would add to `card_board_credit` -- but that fallback is only ever reached
when the DEDICATED branch above did not already `return`. `gov_board_credit`
and `action_board_credit` default NONZERO (1.0, "measured effective from the
start" per their own weights.rs comment), so `card_board_government` and
`card_board_action` were dead on EVERY trained champion by construction, not
merely by drift -- there was never a champion where the dedicated branch
could have been skipped by accident. `wonder_board_credit` defaults 0.0 but
is climbed away from it in every champion sampled (see section 7), making
`card_board_wonder` dead the same way once trained.

This is the same failure shape the codebase's OWN precedent already
retired a static formula for: `cards.rs::tests::
card_yields_never_reprices_the_action_boards_ring_fenced_coordinates`'s doc
comment records "the fix was to delete the static formula rather than pin
agreement, because it was provably unreachable on every trained champion."

Fix: all three retired --
  - Removed from the WeightKey enum (weights.rs).
  - Added to RETIRED_KEYS ("card_board_government", "card_board_action",
    "card_board_wonder") so old champion JSON files on disk keep loading
    (the field is silently dropped, exactly like the 12 pre-existing
    retirements).
  - `cards::board_credit_key`'s match updated: Government/Action/Wonder move
    from `Some(WeightKey::CardBoard*)` arms into the `None` bucket, alongside
    Farm/Mine/Tactic/etc -- the SAME bucket for the SAME reason ("a dedicated
    board-aware function already owns this type's pricing").
  - `eval::card_board_credit_keys()` needed NO code change: it is DERIVED
    from `board_credit_key` (a pre-existing structural precedent from the
    card_board_leader fix), so it shrank from 5 entries to 2
    (CardBoardLeader, CardBoardBonus -- the two types with no dedicated
    top-level branch) automatically.
  - `cards::swap_slot` (hand-collapsing logic for Leader/Government cards
    in hand) had a genuine BUG surfaced by the retirement: it called
    `board_credit_key(id).expect(...)` for Government, which now panics
    (board_credit_key answers None). Investigation found `swap_slot`'s
    PRE-EXISTING check (`card_board_credit + card_board_government != 0.0`)
    was already the WRONG condition for whether a Government card is priced
    board-aware -- it never looked at `gov_board_credit`, the actual gating
    coefficient for the dedicated branch that fires first on every real
    champion. Rewritten to check `gov_board_credit != 0.0 ||
    card_board_credit != 0.0` for Government (the true routing condition in
    card_potential_core), Leader's check is unchanged. This was a genuine,
    separate latent bug this audit's retirement exposed rather than caused;
    full test suite now green with this fix in place (section 9).

Government/Action's dead weight was WORSE than Wonder's in one sense (100%
dead on trained champions by construction, since the credit defaults
nonzero, vs. Wonder's "dead once climbed away from its 0.0 default") --
see section 7 for the corpus numbers.


(4) INSTANCE 3 FIX -- hand_value_early/late
----------------------------------------------
`features.rs`'s `hand_value` feature is `Σ (level()+1)` over the civil hand
-- always >= 0 (every card contributes at least 1). `evaluate` applies it
through the flat WeightKey::ALL loop (the base `hand_value` coefficient) AND
a SEPARATE PHASE_KEYS loop (`+ (1-lateness)*hand_value_early +
lateness*hand_value_late`), so the EFFECTIVE coefficient on this always-
nonnegative feature is `hand_value + (1-lateness)*hand_value_early +
lateness*hand_value_late` -- an affine blend between the two endpoints
`hand_value + hand_value_early` (round 1) and `hand_value + hand_value_late`
(late game).

Fix: `WeightKey::HandValue` added to `eval::NET_NONNEG_PHASE` (the exact
pre-existing mechanism this audit's task explicitly pointed at: "check
whether it should simply be extended rather than duplicated" -- it was
extended, not duplicated; the array had been empty since 2026-08-04 after
its previous two members' phase pairs were deleted outright). This requires
BOTH `hand_value + hand_value_early >= 0` and `hand_value + hand_value_late
>= 0`; because the blend is a convex combination of the two endpoints, both
endpoints being non-negative guarantees the whole affine curve is.

Two new dedicated tests pin the exact repair (eval.rs,
`a_deeply_negative_hand_value_early_is_repaired_even_though_the_base_is_
legal` and `the_repaired_vector_no_longer_prices_a_full_hand_worse_than_an_
empty_one_in_the_opening`), plus a mutation-survival test in bin/climb.rs
(`no_mutant_ever_leaves_a_net_nonneg_phase_pair_net_negative`) that is the
FIRST test to ever exercise NET_NONNEG_PHASE's mutation-time arming at all
(it was empty until this audit, so nothing had proven the loop actually ran
under `mutate()` rather than only at load).


(5) TWO NEW BUGS FOUND BY THIS AUDIT
---------------------------------------
Neither was named in the task brief. Both were found by systematically
checking every remaining WeightKey's consuming code for a provably
one-signed feature, then cross-checking the corpus for real drift.

pop_cost (NEW NonPositive gate). `economy::pop_food_cost(...)` is the
RULEBOOK's own cost table for the next population increase -- always >= 0
by construction. Exactly the same shape LOSS_GATES already documents for
corruption/consumption (both of which were netted OUT of separate weights
for this identical confound: "a big civilization pays more of a rulebook
cost than a small one, so a strictly-bad coordinate correlates with
strength, and a climb chasing win rate charges the correlation to the
penalty"). `pop_cost` is still a LIVE, separate WeightKey (never netted like
its two siblings), so it still needed the gate they no longer do. Found
POSITIVE (+13.34, authored default -0.4) in
analysis/frozen/gauntlet/champion_4p_gen4034_140key_2026-08-08.json -- a
player paying MORE food to grow was being scored as a large improvement.

tactic_gain / tactic_short (NEW NonNegative / NonPositive gate pair).
`cards::tactic_terms` returns `(gain, short)` from `effects::tactic_
outlook`: `gain = max(0, best_army - army_strength(p))` (an available
army-strength IMPROVEMENT, never negative) and `short` (the per-type
shortfall to the NEXT army, never negative -- the whole-hand analogue of the
already-priced `tactic_shortfall_cost`, whose OWN weights.rs doc comment
already names `tactic_short` as "the same shape"). Both were the MOST
widely wrong-signed coordinates found in this audit: `tactic_gain` negative
in 8 of 10 real champion files (as low as -60.0, `champ_backup/
rust_champion_4p.json`), `tactic_short` positive in 6 of 10 (as high as
+10.8, scratch/champion_2p_frozen.json and scratch/champion_2p_civilnonzero.
json). Both are more thoroughly wrong-signed across the corpus than the
originally-reported card_board_leader bug.

(7) CORPUS DAMAGE -- how many champion snapshots on disk violated each gate
--------------------------------------------------------------------------
27 weight-vector JSON files found under /private/tmp/signaudit (champion
snapshots, gauntlet members, python-era champions, human-fitted weights,
strengthcheck experiments, scratch copies). Scan script: /tmp/corpus_scan.py
(reads pop_cost / tactic_gain / tactic_short / hand_value+early / +late /
card_board_wonder / _government / _action directly out of each file's
"weights" object, no dominance_repair applied -- this is the RAW, unrepaired
corpus).

  pop_cost > 0 (violates new NonPositive gate):            4 / 27
  tactic_gain < 0 (violates new NonNegative gate):          8 / 27
  tactic_short > 0 (violates new NonPositive gate):         7 / 27
  hand_value net < 0 at either phase (NET_NONNEG_PHASE):   20 / 27
  nonzero now-retired card_board_wonder/government/action: 13 / 27

hand_value's NET_NONNEG_PHASE violation is the single most widespread finding
in this audit -- 20 of 27 files on disk currently price a full civil hand
WORSE than an empty one somewhere in the early or late game, exactly the
"bot sits on unused civil actions in the opening" symptom the task's own
instance-3 writeup describes.

Worst single violations found:
  pop_cost:      +13.34  (analysis/frozen/gauntlet/champion_4p_gen4034_140key_2026-08-08.json; authored default -0.4)
  tactic_gain:   -60.00  (champ_backup/rust_champion_4p.json; authored default 0.0)
  tactic_short:  +10.82  (scratch/champion_2p_frozen.json and scratch/champion_2p_civilnonzero.json; authored default 0.0)
  hand_value net: 0.2 + (-27.68) = -27.48 net at round-1 lateness (champ_backup/rust_champion_2p.json)

The 13/27 files carrying a nonzero (now-retired) card_board_wonder/
government/action are not "violations" in the sign sense (Free before
retirement) -- they are evidence of exactly how much of the hill-climb's
search budget was being spent perturbing three coefficients that could never
have affected a single evaluated game, on the specific champions where the
matching dedicated credit (gov_board_credit/action_board_credit/
wonder_board_credit) was simultaneously nonzero. All three sit in the
-42 to +42 range across the corpus, i.e. wandered as far as any live,
functioning coordinate -- pure noise the climb never had a reason to prefer
zero.
