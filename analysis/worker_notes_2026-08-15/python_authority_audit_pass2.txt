--- #1 UNSUPPORTED but CONFIRMED-elsewhere-in-repo -- miscited, not miscoded ---
--- (highest value fix: redirect a future reader off the dead Python file) ---

FILE: rust/src/effects.rs:601-607 (`count_armies_genghis`), called from
`army_strength_units` (effects.rs:711-712).

RULE ASSERTED: Genghis Khan's infantry-may-fill-cavalry-slots substitution is
computed by a brute-force search maximizing the number of complete armies
formable (`k*(need_inf+need_cav) <= avail_inf+avail_cav && k*need_cav <=
avail_inf+avail_cav`), matching Python's nested loop. Comment: "Genghis Khan
... [mirrors] the nested `count_armies` inside Python's `_army_strength_counts`
Genghis branch literally, loop included ... independent bounds in Python's own
formula, not re-derived here (if this ever needs re-justifying against the
rulebook, START FROM `engine/effects.py::_army_strength_counts`, NOT FROM FIRST
PRINCIPLES)." That instruction points a future engineer at a file that no
longer exists.

FUNCTION STATUS: LIVE. `count_armies_genghis` is called from
`army_strength_units` (effects.rs:711-712), which is `pub` and is the function
`army_strength` (effects.rs:656, also `pub`, called from `state_stats`/`compute`,
the main per-turn stats recompute) delegates to whenever a player's leader is
Genghis Khan. Not dead, not test-only.

ORACLE CHECK: Code of Laws errata, Genghis Khan entry (/private/tmp/col.txt
~line 1190-1198): "When forming armies, each infantry unit can be either
cavalry or infantry (but not both) TO MAXIMIZE THE CIVILIZATION'S TOTAL STRENGTH
RATING. The infantry units are still considered infantry for other cards, such
as the Great Wall, regardless of their role in forming armies." This same CoL
page is ALREADY cited correctly elsewhere in this codebase:
docs/RULES_SPEC.md:267 -- "10.6 Composition matching: ... Genghis Khan: infantry
may count as cavalry or infantry [CoL p.12]."

VERDICT: CONFIRMED. Maximizing the count of complete armies IS equivalent to
maximizing total strength rating here, because every army of a given tactic
contributes the same per-army value (fresh vs. outdated is a function of the
army's age relative to the tactic, not of which role an infantry unit is
playing) -- so "most armies" and "highest strength" are the same objective for
this formula, matching the CoL text's stated goal exactly. Not a rule risk. But
the comment's OWN internal pointer ("if this ever needs re-justifying... start
from engine/effects.py") sends a future reader to a deleted file instead of
RULES_SPEC.md:267 / CoL p.12, which already settle it -- worth a one-line
citation fix so nobody goes looking for the Python file this comment names.

--- #2 UNSUPPORTED, but self-disclosed as moot -- same underlying game-rule fact
    covers two separate arithmetic choices (MAX vs SUM) ---

FILE: rust/src/effects.rs:89-91 (`Stats::wonder_stages` doc comment) and
effects.rs:1199-1206 (`apply_special`'s `BuildDiscount` arm), both about
Masonry/Architecture/Engineering (the three tiers of the Construction special
technology).

RULE ASSERTED: when multiple `wonderStagesPerAction`-printing sources are held
at once, the wonder-stages-per-action stat takes the MAX across sources; when
multiple `buildDiscount`-printing sources are held at once, the per-age
resource discount stat SUMS across sources. Two DIFFERENT combination rules for
data that lives on the same three cards. Comment (1199-1206): "matching
`_apply_special`'s `bd[age] = bd.get(age, 0) + d` -- not maxed, which is what
`wonderStagesPerAction` ... does ... Holding two of the three at once is
UNREACHABLE IN THE BASE GAME (§7.6 allows one construction special-tech in
play), so nothing today tells the two rules apart at runtime; Python sums, so
this sums."

ORACLE CHECK: Code of Laws, "Limitation" note (/private/tmp/col.txt ~line 927-
930): "You can never be affected by two special technologies of the SAME TYPE.
If you have two of the same type [a newer replaces the older]." Masonry/
Architecture/Engineering are all `specialType: construction` (verified via
`data/cards_civil.json`: all three, and only these three cards in the whole
civil-card set, print `wonderStagesPerAction`). This CONFIRMS the comment's own
"unreachable in the base game" claim independent of Python -- a player can never
hold two Construction techs simultaneously, so MAX and SUM produce IDENTICAL
results (both degenerate to "the one source's own value") in every real game.

VERDICT: CONFIRMED-moot. The MAX-vs-SUM distinction cited to Python cannot
currently diverge from a CoL-backed correct answer given the game's own
same-type-technology exclusivity rule, which the code's author had evidently
already worked out (hence "unreachable," independently correct) but supported
with a Python citation rather than the CoL rule that actually proves it. Low
risk; recommend citing CoL's "same type" limitation instead of "Python sums, so
this sums" -- if a future card (expansion, house rule, or bugfix elsewhere)
ever let two Construction techs coexist, this comment gives no way to tell
which combination rule would then be correct, whereas the CoL-based reasoning at
least explains why it doesn't matter today.
