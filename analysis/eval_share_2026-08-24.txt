THROUGH THE AGES -- EVAL SHARE: SIZING A PER-KEY CLAMP AGAINST THE DECISION
ITSELF (2026-08-24)
================================================================================
MEASUREMENT ONLY. Answers "how big should SCALE be" for a clamp of the form
`bound(k) = SCALE / p95_spread_when_firing(k)`, by anchoring SCALE on the
size of the decision the clamp protects, rather than picking it by hand.
Picking it by hand failed: at SCALE=70 (analysis/clamp_design_2026-08-24.txt)
the design's own two sanity cases pulled in opposite directions (see
analysis/spread_quantiles_2026-08-24.txt's SANITY CHECKS section: culture_rate
needed bound > 60, food_stock needed bound < 60, and 70/p95 gave 17.74 and
10.00 respectively -- both FAIL/PASS the wrong way for a single flat SCALE to
satisfy both).

================================================================================
METHOD
================================================================================
Extends analysis/spread_quantiles_2026-08-24.txt's own method (itself matching
analysis/feature_audit_2026-08-24.txt's method) with one more quantity measured
at the SAME decisions: the FULL evaluation score spread, not just each
feature's own spread.

At every real self-play decision (`filter_resign`d legal-move count > 1)
reached by WeightedBot::choose under a given player count's FROZEN champion
weights (a COPY of experiments/rust_champion_{2,3,4}p.json, taken at the start
of this run -- the live climb rewrites those files every few minutes and this
measurement never reads them directly), every legal move is applied to a
scratch clone and eval::candidate_features() is read for each resulting state.
Per decision:
  total_spread = max(dot(w, phi)) - min(dot(w, phi))   over the candidate set
  spread(k)    = max(phi[k]) - min(phi[k])              over the candidate set
`dot` and `candidate_features` are read directly from rust/src/bots/weighted/
eval.rs (`candidate_features` returns one Vec<f64> per candidate, aligned to
WeightKey::ALL -- the same array `dot` sums against, so `total_spread` and
each key's `spread` come from the identical per-candidate vectors, no
re-derivation). The move actually walked is chosen separately by
WeightedBot::choose on the same state (not re-derived from these scores), so
self-play visits the same decisions the champion actually reaches.

TOOLING: wrote rust/src/bin/evalshare.rs inside this task's own isolated
clone (/private/tmp/evalshare, deleted at the end of this run), reusing
eval::candidate_features/dot and WeightedBot::choose exactly as the prior
spread report's featspread.rs did, adding the total_spread accumulation
alongside the existing per-key fire_rate/mean_spread/mean_spread_when_firing/
p95_spread/max_spread. Ran single-threaded (no --threads flag needed, unlike
the prior run's featspread) specifically so as not to compete with the three
climb arms live on this machine.

COMMAND RUN (from rust/, in the isolated clone):
  cargo build --profile difftest --bin evalshare
  ./target/difftest/evalshare
(games/seed/player counts are compiled in: 40 games/count, seed 0, 2p/3p/4p,
matching the prior spread report's own choice and rationale for both.)

Percentiles are nearest-rank, same convention as the prior report.

SAMPLE SIZE: 40 self-play games per player count (120 games total), producing
10,136 (2p) + 15,255 (3p) + 25,155 (4p) = 50,546 real decision points, each
with its full legal-move candidate set scored -- effectively the same
population as the prior spread_quantiles run (50,818 decisions, same 40/seed-0
protocol; the small per-count differences, e.g. 10,136 vs 10,101 at 2p, come
from the live champion having moved between the two runs' freezes, which
changes WeightedBot::choose's actual path through each game).

eval_share(k, players) = abs(champion_weight(k)) * p95_spread_when_firing(k)
                          / p95(total_spread at that player count)
-- "what fraction of a typical decision's whole score range this one
coordinate commands," using the SAME p95_spread_when_firing the earlier
report already computed as "how bad does it get when it fires" (that report's
own LIMITATIONS #2 applies here identically: the rarest-firing keys' p95
rests on a few hundred firing samples, so single-digit-percent movement is
expected on a re-run).

================================================================================
SECTION C -- SCALE implied by "no coordinate should command more than T times
the p95 total spread", T in {0.5, 1.0, 2.0}
================================================================================
SCALE = T * p95_total_spread(count); bound(k, count) = SCALE(count) /
p95_spread_when_firing(k, count); a champion (key, count) pair VIOLATES if
abs(champ_weight(k, count)) > bound(k, count). SCALE differs per player count
(p95_total_spread differs by count, see Section A) -- each key's bound is
checked against SCALE for ITS OWN player count, never a cross-count SCALE.
Keys that never fired anywhere in this run (p95_spread_when_firing = 0) are
excluded from the violation count -- their bound is undefined, matching the
prior spread report's own footnote-only "floor=500" treatment rather than
silently admitting a divide-by-zero.

================================================================================
CAVEATS
================================================================================
1. Sample size matches the prior spread report's own choice and inherits its
   LIMITATIONS #2 verbatim: p95 for the rarest-firing keys (e.g. auction_bid,
   fire_rate ~0.02-0.03) rests on roughly 200-450 firing decisions per count,
   so a re-run with a different seed could move THOSE keys' p95 (and hence
   their eval_share / violation status) by double-digit percent. The keys
   Section B/C's headline numbers turn on -- event_scoring_margin,
   attack_target_weakness, auction_bid -- fire on 2-26% of decisions, giving
   them between ~250 and several thousand firing samples; less shaky than the
   rarest keys but not as solid as the always-firing majority.

2. Champion weights were frozen at run start (see METHOD); the live climb
   moves them continuously, so a live weight for e.g. event_scoring_margin
   could already differ from the 30.07/34.65/31.88 (2p/3p/4p) used here by
   the time this file is read. The SCALE figures (which depend only on
   candidate-set geometry, not on any one weight) are far more stable across
   time than the specific violation lists in Section C, which depend on both.

3. total_spread and each key's spread are read from the SAME per-candidate
   Vec<f64> in one pass (see METHOD) -- there is no risk of the two numbers
   coming from different champion snapshots or different decision samples
   within this run, unlike a comparison across two separately-run files.

4. This is a measurement, not a landed clamp. No change to
   rust/src/bots/weighted/weights.rs or any live champion file was made.
