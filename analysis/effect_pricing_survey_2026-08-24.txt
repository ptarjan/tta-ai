EFFECT-PRICING SURVEY -- 2026-08-24
Read-only investigation of rust/src for the "per-card effect pricing" mechanism.
Scope: /Users/pt/tta-ai, no edits made, no git/cargo commands run.

TOP-LINE FINDING (contradicts the task's premise as stated):
There is no single dead-code "effect pricing" mechanism sitting inert in the
current build. There is a well-documented PATTERN of ~20 "*_credit" WeightKeys
that each gate a dedicated, board-aware, per-CARD (not per-type) pricing
function -- action_value/tech_value/gov_value/tactic_value/aggression_value in
rust/src/bots/weighted/cards.rs -- around the generic per-type static table
(card_yields). Every one of these credits defaults to 0.0 in DEFAULT_WEIGHTS,
but by 2026-08-24 every single one of them has been climbed away from 0.0 in
ALL THREE live champion JSONs except for a handful pinned at exactly 0.0 in
the 4p champion only (free_action_credit, restricted_resource_credit,
tactic_board_credit). So "inert" is real, but champion-scoped, not global.
docs/OPEN_ITEMS.md item 29 describes a case (card_board_credit/wonder_potential
gating wonder-completion-culture pricing) that WAS globally inert on 3p/4p
when written, but is STALE now -- both keys are nonzero on all three current
champions, so that inertness has since been resolved by training.

Q2: WHY is it inert (where it is)?
===========================================================================
Mechanism: a dedicated WeightKey ("*Credit"/"*BoardCredit") gates the call.
Concrete example, the FreeCivilAction path:
  rust/src/bots/weighted/weights.rs:728   FreeActionCredit => "free_action_credit", 0.0;
  rust/src/bots/weighted/weights.rs:1673  WeightKey::FreeActionCredit => [0.000000, 0.000000, 0.000000],
  rust/src/bots/weighted/cards.rs:1160-1163:
        if card.special.iter().any(|sp| matches!(sp, Special::FreeCivilAction(_))) {
            let fc = w.get(WeightKey::FreeActionCredit);
            if fc != 0.0 {
                total += fc * rivals::feature_marginal(WeightKey::CivilActions, ...);
  So: default weight is exactly 0.0 -> the `if fc != 0.0` branch never fires ->
  the per-card FreeCivilAction bonus prices at nothing, UNLESS training (hill
  climbing) has moved free_action_credit off 0.0 for a given champion.
  This is "a weight authored at 0.0" gating "a branch never taken", exactly
  the task's third bullet -- but it is a TRAINABLE parameter, not a
  structurally-dead branch: nothing prevents it from being nonzero, and in
  fact it already is nonzero in 2 of 3 live champions (see Q3).

Same shape repeats for every other *_value()/*BoardCredit pair (action_board_
credit gates action_value entirely at cards.rs:1815-1818; tech_board_credit/
gov_board_credit/wonder_board_credit/tactic_board_credit/aggression_board_
credit/... the same). tech_value's own doc comment says it plainly:
  rust/src/bots/weighted/cards.rs:1180 "... a `max`, not a sum:
    `build_fresh_credit` gates it, default 0.0, so this is inert until the
    league is told to look."
docs/OPEN_ITEMS.md:642-650 (item 29) documents the historically-inert
wonder case: card_board_credit and wonder_potential both default 0.0 and,
as of that doc's writing, were 0.0 on 3p/4p (only 2p had climbed them:
0.361 / 0.115) -- STALE as of today, see Q3.

Q4: What would turning it on change, and is there a double-count risk?
===========================================================================
Call path (FreeCivilAction example, most concrete one):
  eval.rs/row.rs -> card_potential() (cards.rs:1781)
    -> card_potential_core() (cards.rs:1792), CardType::is_action() branch
       (cards.rs ~1815-1818): gated by ActionBoardCredit (nonzero on all 3
       champions already, so action_value() IS being called today)
    -> action_value() (cards.rs:1108) -> the FreeCivilAction special case
       (cards.rs:1160-1166), gated by FreeActionCredit.
Turning FreeActionCredit on (nonzero) for the 4p champion specifically would
only affect the ~18 base-game cards carrying Special::FreeCivilAction (e.g.
Rich Land) when action_value() is reached for them at 4p -- a narrow, already-
wired path.

Double-count check: NO, not for this specific key today. There used to be a
double-count bug -- the static card_yields table AND action_value both
attempted to price ResourceDiscount/RestrictedResources/FreeCivilAction, and
they measurably disagreed (comment at cards.rs:3376-3390: "0.0 static vs 1.82
board-aware pricing Rich Land (A)'s resourceDiscount at the live 2p Rust
champion's weights"). The fix DELETED the static formula for those three
WeightKeys rather than trying to keep them in sync, and it is now pinned by a
regression test:
  rust/src/bots/weighted/cards.rs:3391 fn card_yields_never_reprices_the_
    action_boards_ring_fenced_coordinates() -- walks every card, asserts
    card_yields() never emits WeightKey::ResourceDiscount |
    WeightKey::RestrictedResources | WeightKey::FreeCivilAction.
So the FreeCivilAction/ResourceDiscount/RestrictedResources triple has
exactly ONE live pricing path (action_value, gated by ActionBoardCredit +
FreeActionCredit), not two. Turning on the currently-0.0 keys (at 4p) is a
pure activation of an already-single-path mechanism, not a risk of double
counting.

Caveat: this "single path, safe to turn on" property is true because a prior
lane already excised the duplicate. It does NOT generalize automatically to
every *_credit gate without checking each one's own history the same way
(e.g. board_yields.rs:42-49's doc comment on wonder_completion_culture single-
implementation guard, tests/test_card_pricing.py:TestOneImplementation on the
Python side, is the analogous guard for the OnBuildCulture path).

===========================================================================
OPINION
===========================================================================
Turning "it" on is a SMALL, safe change for the one candidate that actually
matches "wired but currently reads as literally 0" today (FreeActionCredit /
Special::FreeCivilAction, restricted_resource_credit, tactic_board_credit --
all three exactly 0.0 in the 4p champion only): flip the weight, rerun
training/eval for 4p, done -- the call path is single, tested, and the
double-count hazard was already closed by a prior lane (cards.rs:3391).
It is NOT a small change in the sense the task's premise implies (flip one
switch and unlock a whole unused subsystem): the "subsystem" is already live
in production on 2p and 3p, and on most of its 20 credit keys at 4p too. The
real, currently-true gap is narrow: three credits pinned at exactly 0.0 on
one arm (4p), plus docs/OPEN_ITEMS.md item 31's build_fresh_credit, which was
tested and found to be a genuine regression, not an oversight -- turning that
one on is not free and should not be done without redoing that A/B.
