STEP 1 -- WHAT featspread ALREADY MEASURED, AND WHAT WAS ADDED
================================================================================
Read rust/src/bin/featspread.rs (all four existing modes: default, `emit`)
and rust/src/bin/takeprobe.rs (as the worked example of enumerating legal
moves via eval::candidate_features and re-deriving the argmax via eval::dot,
per the task's instruction to imitate its approach).

featspread's existing `play_count` ALREADY measures the correct quantity in
principle: for every real decision (`candidates.len() > 1`, exactly
eval::candidate_features' post-filter_resign output), per WeightKey k,
spread(k) = max(candidate value) - min(candidate value) OVER THE CANDIDATE
SET AT THAT DECISION POINT -- not a cross-game/cross-state magnitude
normalisation. `P95_TOTAL_SPREAD`/`total_spread` there is ALSO a
per-decision, per-candidate-set quantity (max dot - min dot over the same
candidate set), not a cross-game statistic either. So featspread was
already answering the right KIND of question (candidate-set spread, which
decides an argmax), not the wrong one (cross-game spread, a magnitude
normalisation). No code needed to change to fix a category error, because
there wasn't one.

What featspread's existing modes did NOT compute, and this task's METHOD
REQUIREMENTS section needs:
  1. A MEDIAN of the non-zero-spread distribution (existing modes report
     mean_spread_when_firing and p95_spread_firing only, no median).
  2. The feature's mean absolute LEVEL (mean |candidate value|, independent
     of spread) -- needed to distinguish an inert-but-alive key (zero
     spread, large level) from a dead/never-populated one (zero spread,
     zero level) per the task's own METHOD REQUIREMENTS point 1. Neither
     existing mode computes this at all.
  3. The DECISIVE quantity itself: |w_k| * spread_k compared, PER DECISION,
     against that SAME decision's actual winning margin (best candidate's
     dot(w,phi) minus the RUNNER-UP's). featspread's existing `eval_share`
     divides by `p95_total_spread`, which is max-minus-min over the WHOLE
     candidate set (every candidate, not just the top two) -- a different,
     looser quantity than "the margin the actual winner needed to beat the
     actual runner-up". A key can have `eval_share < 1` under the existing
     metric while still never actually being tested against the real
     competitive margin at any single decision, and vice versa.

Per the task's own instruction ("If it does the second [candidate-set
spread], use it as-is... If [it lacks needed stats], add a NEW mode... then
run the FORCED GATE"): added ONE new mode, `decisive` (4th CLI arg
"decisive", alongside the existing "emit"), restricted to 3p only (the
count this task asks about), reusing the exact same champion_dir +
`rust_champion_3p.json` join every other mode already uses -- no new
file-naming convention. Every existing mode (default report, `emit`) is
byte-identical: `decisive` is checked first in `main` and returns before
touching any of the old code paths. New code: `play_decisive`/
`DecisiveKeyAgg`/`DecisiveResult`/`print_decisive_report` in
rust/src/bin/featspread.rs. The FORCED GATE (clippy -D warnings, full
`cargo test`, release build) all exited 0 -- see /private/tmp/spread_notes.txt
for the exact EXIT lines. One clippy false-positive was fixed along the way:
a doc-comment line starting "* spread_k >= margin" was parsed by rustdoc as
a markdown bullet marker, breaking `doc_lazy_continuation`'s indentation
tracking for the rest of that list item -- reworded to prose, not silenced
with `#[allow]`.

`decisive` mode's method, per decision (candidates.len() > 1, same gate as
every other mode): for every WeightKey k,
  spread_k = max(candidate value) - min(candidate value)     [same as play_count]
  level_k  = mean(|candidate value|) over the candidate set  [NEW]
  swing_k  = |champ_w(k)| * spread_k                          [max score swing k alone can cause]
  margin   = best candidate's dot(w,phi) - runner-up's dot(w,phi)   [NEW, ALL keys' weights included]
capable_frac(k) = fraction of ALL 85,404 decisions where swing_k >= margin,
i.e. k ALONE was structurally capable of having been the deciding factor,
at the CHAMPION's own |w(k)| (spread_k is fixed by the game state and the
legal moves; only |w(k)| is a free dial, so capable_frac is monotonic in
|w(k)| and this reports the number at the champion's actual weight, per the
task's "at the champion's own weight" framing -- not a hypothetical one).

STEP 3 -- FLAT VERDICT
================================================================================
BestMine is structurally incapable of deciding anything at the champion's
current weight, in this sample: its spread is exactly zero at every one of
85,404 decisions, its mean level is exactly zero (dead, not just constant),
and its capable_frac sits at the tie-only floor. A feature that never
varies AND never takes a nonzero value cannot have moved a single argmax
this sample reached, at ANY weight the champion could have put on it
(spread fixed at zero means |w|*spread == 0 regardless of |w|). This
directly explains, via an INDEPENDENT mechanism (candidate-set feature
variation, not the take-mechanism census), why the champion takes zero
higher-tier Mines: the feature that is supposed to reward mine-taking is
never in a position to distinguish a mine-take candidate from any other
candidate, because best.mine never departs from its floor value across
these 220 games.

BestFarm is ALSO structurally incapable in this sample, but for a subtly
different reason: it is not dead (it fires on 0.08% of decisions, with a
real nonzero level when it does), but its capable_frac is IDENTICAL to
BestMine's -- exactly the tie floor. Every one of its ~68 firing
occurrences produced a swing too small to beat the actual winning margin.
So BestFarm is "occasionally alive, never decisive" rather than "always
dead" -- a finer-grained version of the same underlying failure mode the
task's headline hypothesis describes.

Beyond these two named suspects, 59 OTHER keys (61 total, 38% of the
160-key vector) sit at the exact same tie-only floor -- the majority of
them (35 of the 38 permanently-zero-spread keys) are dead/unused rather
than merely inert, meaning most of this group is not even the interesting
"large, correctly-signed, completely inert" case the task describes -- it
is simply an unused coordinate. A handful (best_farm, best_library,
best_unit, best_arena, rival_hand_civil, urban_limit, gov_level,
civil_actions, colonize_bonus, war_immune, special_techs and others in the
0.90-1.00 zero_frac band) DO fire occasionally but never decisively --
exactly BestFarm's pattern, not BestMine's.

FoodRate, Workers, FreeWorkers and FoodStock are NOT structurally
incapable, and must not be lumped in with BestMine/BestFarm:
  - FoodStock is clearly decisive (0.3321, top-11 of 160).
  - Workers is clearly decisive (0.2723, well above the tie floor).
  - FreeWorkers is weakly decisive (0.1151) -- above the floor but well
    below the "clearly decisive" tier; an intermediate case, not inert.
  - FoodRate is the one near-miss: it varies constantly (fires on 46.8% of
    decisions, more often than all but a handful of keys) yet is barely
    above the tie floor (0.0989) because the champion's own weight on it
    (0.0666) is too small, not because the feature is structurally
    constant. This is a DIFFERENT failure mode from BestMine/BestFarm
    (a pricing problem, not a candidate-invariance problem) and this
    measurement cannot tell those two failure modes apart from
    capable_frac alone -- see CAVEATS.

Do not overclaim beyond what this table shows: capable_frac measures
whether a key ALONE could have flipped a decision, not whether it actually
did, and it says nothing about whether RAISING a key's weight would help --
that is a weight-tuning question, explicitly out of scope (task's own
instruction: diagnosis only, no weight change proposed or tested here).

================================================================================
CAVEATS
================================================================================
1. TIE-FLOOR ARTIFACT (important, read this before trusting any
   capable_frac number): capable_frac(k) counts a decision as "capable"
   whenever swing_k >= margin. When margin == 0 (an EXACT tie for the top
   candidate score -- which happens on 9.24% of the 85,404 decisions in
   this sample, judging by the floor every zero-spread key shares), EVERY
   key trivially satisfies swing_k (0) >= margin (0), even a key that never
   fires at all. This produces the 0.0924 floor observed for 61 keys. The
   RANKING across keys is still meaningful (a key with capable_frac well
   above 0.0924 really is more decisive than one sitting exactly on it),
   but the raw capable_frac number for any key should be read as
   "0.0924 + true decisive rate", not as the true decisive rate itself. A
   tighter version of this measurement would exclude margin == 0 decisions
   from the denominator; this run did not, and the report leans on the
   RANK/floor-comparison rather than the raw fraction for that reason.

2. mean_abs_level distinguishes dead-vs-alive only within the SAMPLE this
   run actually reached. A key could be alive in principle (a legitimate,
   non-buggy feature) but simply never reach a nonzero state across 220
   games at this seed -- best_mine's zero level is consistent with either
   "the code path is unreachable/buggy" or "220 games of this champion's
   own policy structurally never develops a mine", and this measurement
   cannot distinguish those two causes by itself (though the mine_take_probe
   census's independent SEEN/LEGAL/SCORED funnel, cited in the task
   background, is strong evidence for the latter: mines are seen and legal
   constantly, just never taken).

3. RATE_KEYS scaling: per eval::linear_features' own doc comment, every
   RATE-tagged WeightKey (FoodRate, ResourceRate, ScienceRate, CultureRate,
   plus the four inside horizon::RATE_KEYS) is scaled by
   horizon::rate_multiplier(state, freeze, live_count), with freeze pinned
   to the SAME champion vector these candidates are scored with -- exactly
   matching real self-play (WeightedBot::choose/rank_moves never recompute
   this per candidate weight either). This means every number in this
   report for a RATE-tagged key already reflects the champion's own horizon
   scaling; it is not a raw, unscaled feature read. This does not change
   the zero/nonzero-spread verdict for any key (the scaling is a per-
   decision scalar applied uniformly to that decision's candidates when the
   underlying raw feature is candidate-invariant, and multiplicatively to a
   candidate-varying raw feature otherwise) but should be kept in mind when
   comparing a RATE key's absolute mean_abs_level against a non-RATE key's.

4. Single seed (12345), single run, 3p only, 220 games / 85,404 decisions.
   Task asked for 200+ games at 3p; this satisfies that but is not a
   multi-seed replication. The eleven WeightKeys eval::linear_features'
   own doc comment documents as bilinear-in-w (HandPotential,
   WonderPotential, WonderPromise, HandMilPotential, RivalHandPotential,
   RowUrgency, RowBargainForgone, RowLastCopy, MyEventThreat, plus
   RateHorizon's own scaling of the four RATE_KEYS) are priced by freezing
   their internal sub-computations at the champion vector, exactly as every
   other real caller does -- their spread/level/swing numbers here are
   faithful to what the champion bot itself would have seen, not a
   different linearization.

5. "Decisions" here means every point where WeightedBot::choose faced 2+
   scored candidates, across the WHOLE game -- not specifically Mine-take
   or Farm-build decisions. BestMine/BestFarm's near-zero capable_frac is
   therefore a statement about their decisiveness ACROSS THE WHOLE GAME,
   which is the correct scope for "can this feature ever decide anything",
   not a narrower claim restricted to the specific decision types the prior
   probes (mine_take_probe, farm_build_probe) already covered in more
   depth -- this measurement is complementary to those, not a replacement.

6. This is diagnosis only. No weight change was proposed, tested, or run
   here, per the task's own instruction; the corpus/climb/champion files
   were not touched.
