====================================================================
1. WHAT WAS ADDED TO THE DUMP
====================================================================

phidump grew an extra block AFTER the phi block. MAGIC UNCHANGED (`TPHI`),
VERSION BUMPED 1 -> 2, and the header's fourth word -- which v1 always wrote
as a hard zero -- now carries the extra width. So the phi block's layout is
byte-identical to v1 and any reader that takes the width from the header
reads both versions; a v1 file simply declares extra = 0. A reader that
hard-asserted version == 1 does not, which is why the bump is visible rather
than silent. analysis/phifit.py was updated to the same rule.

Column names go in a second sidecar <out>.extra_keys, matching the contract
<out>.keys already has for phi.

The columns are computed in rust/src/feature_screen.rs. THE EVALUATOR IS
UNTOUCHED: no WeightKey was added, nothing in eval.rs changed, and nothing
here is reachable from evaluate / rank_moves / pick.

Provenance guard. candidate_features returns (move, phi) and not the
post-move state phi was priced on, so feature_screen rebuilds that trial
state (clone, determinize_current_events at plan_rng, apply unless EndTurn)
to read the extra columns off it -- while still taking phi itself from
candidate_features, which is never re-derived. The test
feature_screen::tests::trial_matches_candidate_features asserts that
linear_features over the rebuilt trial reproduces candidate_features' vector
EXACTLY over 400+ real self-play decisions, so the extra columns cannot
silently start describing a different position than the phi beside them.

Legality. Every column reads only the ACTING seat's own hand
(players[idx].hand_civil / hand_military), its own hidden-card counts, its
own science and actions, and public board state. No rival hand identity, no
deck order, no label. Nothing here is information the bot does not already
legally have at that decision point.


====================================================================
2. THE HAND-COMPOSITION ENCODING, AND WHY
====================================================================

The standing claim under test is that taking a card is nearly invisible to
the board features because the card goes to HAND, and the only thing pricing
a hand is the eval-only HandPotential block. phi already carries the hand
SIZES and two aggregate values (HandCivil, HandValue, HandValueLate,
HandPotential, HandPerishable, HandMilitary, HandMilValue, HandMilPotential,
HandOverCapacity, HandSwapExtra, HandLimit). What it has no feature for is
the COMPOSITION -- which cards those are. So the 34 columns are a set of
DECOMPOSITIONS of the same hand, each partitioning or summarising it a
different way, and the screen asks which cut of the hand carries outcome
signal the aggregates do not:

  (A) by type family, 7 cols -- production / urban / units / government /
      leader / action / specialtech. Partitions the civil hand. The coarsest
      "what kind of thing am I holding" question.
  (B) by age, 7 cols -- counts at age A/I/II/III, plus stale (age below the
      current civil age), ahead, and the mean age gap. Absolute age and age
      RELATIVE to the board are different questions and both are cheap.
  (C) playable now, 5 cols -- affordable by printed science cost, affordable
      AND a civil action left, total and minimum science shortfall,
      unaffordable count. "Can I actually use this" as distinct from "do I
      have it".
  (D) cost mass, 4 cols -- total and max printed science cost, total
      resource cost, and science / total-cost coverage (scale-free, so it is
      not just hand size again).
  (E) military hand, 7 cols -- tactic / aggression / war / pact /
      bonus+territory counts, count playable against military actions left,
      total MA cost. The military hand is a separate deck with a separate
      action currency.
  (F) hidden counts, 2 cols -- hidden_civil / hidden_military.
  (G) redundancy controls, 2 cols -- ctrl_hand_civil_size and
      ctrl_hand_military_size, which ARE already in phi. They are here as an
      internal check that the screen returns ~0 for something the base set
      already has.

Printed costs are used throughout, never costs::tech_cost / build_cost_for.
Those are discount- and pact-aware, and a column that folded the rest of the
board into a hand measurement would score for the wrong reason.

3. POSITIVE CONTROL -- CAN THE SCREEN DETECT ANYTHING?
====================================================================

Run BEFORE any candidate column was read.

Probes are the 8 phi columns with the largest |champion weight| x column sd:
the bot demonstrably scores with them (non-zero weight) and the term actually
moves the score (non-trivial spread). Each is DROPPED from the base set and
then offered back as a candidate.

"spanned" is the R2 of rebuilding the dropped column by least squares from
the other 173. It is the number that makes a zero recovery readable.

RECOVERY: +0.003732 R2 for CultureRate -- 622x the noise floor below.
Second recovery: +0.001327 for AttackTargetWeakness, 221x the floor.

THE SCREEN CAN DETECT A FEATURE THE EVALUATOR ALREADY USES. It is not broken
and the numbers below are not automatically noise.

BUT READ THE "spanned" COLUMN. Five of the eight probes recover ~0, and every
one of them is a column the remaining 173 reconstruct at spanned >= 0.74,
three of them exactly (1.0000). This is not a failure of the screen, it is
the definition of what it measures: removing a column that the rest of phi
reproduces exactly removes NOTHING, so handing it back can add nothing.

So the screen measures UNIQUE signal, not importance. A candidate scoring
zero here means "phi can already reconstruct this", not "this does not matter
to the game". Two columns with equal gain are equally NEW; neither number
says anything about how much either would move a bot that has to act on it.

Base R2 note. The base ridge here is 0.4400, against the 0.4931 previously
recorded by phifit.py. The method is not the difference: the same
cross-product solver reproduces sklearn's Ridge to four decimals, and
reproduces 0.4931 EXACTLY on the old 600-game v1 dump under phifit's own
single 80/20 protocol. The difference is sample size. Running phifit's
protocol on five disjoint 600-game subsets of this dump gives 0.4071, 0.4087,
0.4099, 0.4487, 0.4704 -- a 0.06 spread, because a single 80/20 split of 600
games scores on only 120 held-out games. 0.4931 was a high draw of a noisy
estimator. The 3000-game pooled 5-fold figure is the tighter estimate.

6. ROBUSTNESS
====================================================================

Ridge penalty. At 720k training rows an alpha of 1 or 100 is effectively no
regularization; the sweep is flat until shrinkage actually bites.

    alpha      base R2   pos control      floor     family   hand_gov_count
        1     0.439962     +0.003732   0.000006  +0.002732        +0.000378
      100     0.439961     +0.003733   0.000006  +0.002734        +0.000378
    10000     0.439312     +0.003662   0.000006  +0.002568        +0.000382
  1000000     0.376990     +0.003296   0.001301  +0.001209        +0.000186

  At alpha 1e6 the fit itself is destroyed (base R2 0.377) and the noise
  floor rises 200x to 0.0013 -- that is a degenerate regime, listed only to
  show where the screen stops working. Everywhere the base fit is intact,
  the ordering and magnitudes are unchanged.

Fold split. The whole screen re-run under three different grouped 5-fold
splits (fold seeds 0, 1, 2):

  seed   base R2   pos control    floor     family
     0  0.439962    +0.003732  0.000006  +0.002732
     1  0.440744    +0.003633  0.000004  +0.002750
     2  0.440211    +0.003624  0.000003  +0.002545

  The top-6 candidate SET is identical under all three seeds, and the order
  is identical except that ranks 4 and 5 (handmil_tactic_count,
  hand_science_cost_total) swap under seed 1.

Method check. The cross-product ridge solver used throughout was verified
against sklearn's Ridge on both this dump and the old 600-game v1 dump under
an identical single 80/20 game split: 0.4395 vs 0.4395, and 0.4931 vs 0.4931.


====================================================================
7. LIMITS OF THIS SCREEN -- READ BEFORE RANKING ANYTHING
====================================================================

1. It measures UNIQUE PREDICTIVE signal at one frozen weight vector, not
   decision value. Section 3 shows five columns the evaluator leans on hard
   scoring exactly zero because the rest of phi already spans them.

2. It predicts the final margin from a position. It does not measure whether
   a bot given the column would CHOOSE better; a feature can predict the
   outcome without being actionable at the decision.

3. The rows come from the champion playing itself. Positions the champion
   never reaches are not in the sample, so a column that only matters off
   this policy's trajectory cannot show up.

4. phi depends on w. Every number here is priced at gen 133131 and would
   have to be re-measured at a different champion.

5. Rank 13 down to rank 7 sit between 2x and 9x the noise floor with mixed
   fold signs. They are above the floor as measured and that is all.
