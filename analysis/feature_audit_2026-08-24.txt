THROUGH THE AGES -- LINEAR LEAF-EVALUATION FEATURE AUDIT (2026-08-24)
========================================================================

HEADLINE: 160 WeightKeys classified -- RETIRE 56 (of which 37 are EXACT null: mean spread identically 0.0 across all 253,906 sampled decisions in all 3 player counts, 19 near-zero), CHANGE 5, KEEP 99.

========================================================================
METHODOLOGY
========================================================================

Firing rate is NOT the metric (military_actions and civil_actions both fire
on 100% of positions and only one was corrupted -- see this task's own brief).
The metric is CANDIDATE-SET SPREAD: the bot picks a move by evaluating the
RESULTING STATE of every legal move and taking the argmax, so a feature only
influences a decision to the extent it VARIES ACROSS THE CANDIDATE MOVES at
that decision. A feature identical in every candidate cancels out of the
argmax exactly, no matter how large its weight, and a hill-climber random-
walks that coordinate forever.

At every real self-play decision point (>1 legal move) reached by
WeightedBot::choose under the LIVE CHAMPION weights (own file per player
count), every legal move was applied to a scratch clone of the state and
eval::candidate_features() was read for each resulting state --
candidate_features() IS linear_features() run once per candidate, the exact
per-WeightKey vector `evaluate` dots against a weight vector (pinned by
eval.rs's own test
linear_features_dotted_with_a_weight_vector_reproduces_evaluate_exactly).
Per WeightKey, per decision: spread = max(candidate values) - min(candidate
values). Aggregated as MEAN, MEDIAN and ZERO-FRACTION (share of decisions
where spread was exactly 0.0) over every decision sampled, separately for
2p/3p/4p self-play under that player count's own champion.

TOOLING -- what was found, what was built, and why:
Searched rust/src/bin/ (behavcensus.rs, botcensus.rs, dump_selfplay.rs,
orderprobe.rs, dumpweights.rs), git log --all for "blind"/"coordinate"/
"argmax", and docs/ for a prior candidate-spread sweep. The closest prior
art is docs/COVERAGE_AUDIT.md's tools/feature_variance.py (varying/
mean_range/flip columns -- literally this same methodology), built for the
OLD PYTHON engine's own feature vocabulary. That engine, and
tools/feature_variance.py with it, was DELETED 2026-08-15
(rust/CLAUDE.md: "do not resurrect it"), so it is gone and not reusable.
No Rust binary in rust/src/bin/ computes candidate-set spread.
dumpweights.rs is the closest Rust precedent (per-WeightKey contribution to
evaluate()'s delta between two FIXED moves at one FIXED hardcoded position
-- a single-fixture diagnostic, not a self-play sweep) but does not sample
real decisions or aggregate across many of them.
eval::candidate_features (rust/src/bots/weighted/eval.rs:699), already used
by bin/agreefit.rs's human-agreement fit, computes EXACTLY the per-candidate
linear_features vector this audit needs, sharing the same root/RivalContext
construction WeightedBot::choose itself uses -- REUSED DIRECTLY, no scoring
logic re-derived. Wrote ONE NEW small binary, rust/src/bin/featspread.rs,
whose only job is to drive real self-play with WeightedBot::choose (so
sampled decisions are the ones the champion actually reaches, not synthetic
positions) and call candidate_features() once per decision, then aggregate.

COMMANDS RUN (from rust/, in the isolated clone):
  cargo build --profile difftest --bin featspread
  ./target/difftest/featspread \
      --weights-2p ../experiments/rust_champion_2p.json \
      --weights-3p ../experiments/rust_champion_3p.json \
      --weights-4p ../experiments/rust_champion_4p.json \
      --games 200 --seed 0 --threads 6 --out featspread_full.txt
  (a 10-games-per-count smoke test preceded this at --seed 0 --threads 4,
  used only to sanity-check the tool before committing to the full run)

Champion files: cp'd into an isolated `cp -Rc` clone BEFORE this ever ran
(the live /Users/pt/tta-ai/experiments/rust_champion_*.json are rewritten by
the (paused) climb every few minutes; this audit never reads them).

SAMPLE SIZE: 200 self-play games per player count (600 games total),
producing 50,524 (2p) + 77,546 (3p) + 125,836 (4p) = 253,906 real decision
points (>1 legal move), each with its full legal-move candidate set scored.
Run took 146.1s wall on 6 threads.

for well-evidenced shape cases):
  RETIRE: mean spread < 0.02 in EVERY player count AND zero-fraction >=
          0.95 in EVERY player count. (Within RETIRE, "EXACT null" marks the

  KEEP:   everything else -- real, nonzero candidate-set spread.
This is a threshold, not a proof, for the boundary cases (mean 0.01-0.03,
zero_frac 0.95-0.99) -- see LIMITATIONS at the end.

WHY roughly a third of the exact-null group is exact-null BY CONSTRUCTION:
rival_desire, rival_take_share, rival_science_rate, rival_wonders,
rival_free_ca (and, in the near-zero group, rival_free_workers,
rival_building_wonder, rival_colonies, rival_culture_rate, rival_mil_actions,
rival_strength) are all sourced from RivalContext, which eval.rs's own
WeightedBot::choose/candidate_features doc comments say is computed ONCE AT
THE ROOT, on the unmoved board, and reused for every candidate ("an
information leak, not just an optimisation, if recomputed per candidate").
Every candidate at a decision therefore gets the IDENTICAL value for any
rival_* feature sourced purely from that frozen context -- a structural
certainty, not a training artifact. This is the Rust-era re-discovery of
exactly the same root-freeze mechanism docs/COVERAGE_AUDIT.md section 5.1
already documented for the OLD Python engine's rival_strength/
rival_science_rate (also root-frozen, also exact nulls there). The rival_*
features that DO show real spread here (rival_culture, rival_mean_culture,
rival_food_stock, rival_resource_stock, rival_science_stock, rival_yellow_bank,
rival_hand_civil, rival_hand_potential) all re-read the TRIAL state per
candidate rather than the frozen ctx object -- exactly the distinction
COVERAGE_AUDIT already drew for the Python engine's rival_culture/
rival_mean_culture.

The `_board_credit` family (action_board_credit, aggression_board_credit,
card_board_credit, event_board_credit, gov_board_credit, pact_board_credit,
tactic_board_credit, tech_board_credit, war_board_credit, card_board_bonus,
card_board_leader) and the sibling `_credit` gates (bonus_card_credit,
build_fresh_credit, card_rate_credit, free_action_credit,
restricted_resource_credit, tactic_reach_credit, tactic_shortfall_cost,
territory_credit, unit_strength_credit, unit_tech_credit,
tech_redundancy_discount) are exact nulls for a DIFFERENT reason: several
of these are 0.0 in every champion (see the table below), and the raw
feature they gate is itself proportional to `w.get(that same gate)` inside
cards.rs/row.rs -- so with freeze==champion, a 0.0 champion weight makes the
RAW FEATURE 0.0 too, independent of which candidate is scored. This is not
drift -- these are deliberately-off gates awaiting a league measurement
(weights.rs's own comments: "trust nothing until the league finds it") --
but it does mean this audit CANNOT tell whether the underlying mechanism
has real spread once turned on; see LIMITATIONS.

========================================================================
LIMITATIONS / WHAT WAS NOT MEASURED
========================================================================

1. Gated (0.0-weight) identity-aware channels: for the ten keys
   linear_features() prices through a `freeze`-priced sub-function
   (hand_potential, wonder_potential, hand_mil_potential,
   rival_hand_potential, row_urgency, row_bargain_forgone, row_last_copy,
   my_event_threat, plus rate_horizon's own RATE_KEYS scaling), spread was
   measured with freeze == that player count's OWN champion, matching
   `evaluate`'s real behaviour exactly (by construction, pinned by
   eval.rs's own dotted-reproduces-evaluate-exactly test). Where a GATE
   weight feeding one of these is 0.0 in the champion, the measured
   near-null spread reflects the gate being off, not a proof the underlying
   mechanism is inert -- see the `_board_credit`/`_credit` note above.

2. Single-legal-move decisions are excluded from every measurement (the
   whole exercise is about CANDIDATE spread; a forced move has none). Some
   RETIRE verdicts here -- `colonies` and `has_colony` most notably, both
   RETIRE despite real board weight (colonies up to 24.4 at 3p) and an
   extensive weights.rs comment on why HasColony's cliff shape should
   matter -- are consistent with colonizing being a MULTI-STEP action whose
   `.colonies` count does not change on the SAME ply that offers the
   colonize move as a candidate; if so, this is a real 1-ply-search
   blindness (the same shape docs/COVERAGE_AUDIT.md called "search-blind"
   for the Python engine's wonder-stage decisions), not evidence that
   colonizing is rare. This audit measures what the LINEAR BASIS can see
   at 1 ply, which is the question asked; it does not attribute the cause.

3. 200 games/player count (253,906 decisions) is a large sample by the
   standard this repo already uses elsewhere (docs/COVERAGE_AUDIT.md used
   40 games/cell, ~2,300-5,500 decisions per cell) but boundary verdicts
   (mean spread 0.01-0.03, zero_frac 0.95-0.99 -- the "near-zero" RETIRE
   subgroup, plus a handful of low-margin KEEPs) could flip with more
   samples, particularly for leader-ability gates (war_immune,
   attack_cost_doubled, no_aggression) that depend on a specific leader
   being in play, which is itself rare in any single game.

4. `sign_intent()` cross-check, clamp-pinning and the 13-key cross-count
   sign-agreement list were NOT re-derived here -- reused verbatim from
   analysis/champion_audit_2026-08-24.txt (frozen from the same 3 champion
   files this audit also used), per this task's brief.

5. This audit did not re-verify every CHANGE candidate's shape by reading
   its full features.rs/cards.rs implementation; the 5 listed are the ones
   with either a PINNED TEST (wonder_progress/wonder_potential -- see
   cards.rs::tests::two_wonders_with_different_powers_score_identically_
   at_the_moment_they_are_taken) or an explicit features.rs/weights.rs
   architecture comment naming the SAME feature as both a raw LEVEL and
   the subject of an already-built DIFFERENCE hinge (food_stock,
   resource_stock) or an explicit "linear cannot express" comment
   (unit_workers). Other keys may share these shapes without a comment
   flagging them; a full audit of all 99 KEEP keys' feature definitions
   was out of scope for the tool-call budget here.
