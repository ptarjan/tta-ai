================================================================================
MULTIPLIER-KEY COUNTERFACTUAL ARGMAX-FLIP MEASUREMENT, 3P -- 2026-08-24
================================================================================

HEADLINE: the candidate-set SPREAD scan (analysis/feature_decisiveness_3p_2026-08-24.txt)
flagged 38 of 160 WeightKeys as "candidate-invariant" and about to be pruned. 32 of
those 38 are structurally invisible to that instrument -- they never occupy a slot
in the linear feature vector phi at all; they are MULTIPLIERS read via w.get(key)
inside other features' computation (example: rust/src/bots/weighted/cards.rs
~line 1873, `tb * tech_value(...)` where `tb = w.get(WeightKey::TechBoardCredit)`).
A key used that way has candidate-set spread exactly 0.0 by construction, at every
decision, regardless of how much it moves real move ranking. "Spread is zero" is
not evidence of uselessness for this family; a COUNTERFACTUAL ARGMAX FLIP is the
right instrument, and this file reports that measurement for all 32 of them.

RESULT: this family is NOT inert. tech_board_credit (champion value -25.4575,
NEGATIVE) flips the actual chosen move on 13.8% of all real 3p decisions just by
zeroing it, and on 27.9% of decisions when only its SIGN is corrected (magnitude
held fixed at |−25.4575| = 25.4575) -- the single largest effect measured, and a
direct confirmation of the task's own hypothesis that a negative multiplier on a
signed value function inverts good and bad cards rather than merely scaling them.
card_board_credit (positive, 0.5837) flips 16.6% of decisions just by zeroing it;
action_board_credit flips 10.0%. Eight of the 32 keys never touched a single
candidate's score across all 31,088 sampled decisions (see CAVEATS) -- six of
those carry live, nonzero champion weights, so either they are unreachable at 3p
specifically or genuinely dead code; this file does not adjudicate which.

================================================================================
METHOD
================================================================================
Binary: rust/src/bin/multcheck.rs (new; copies bin/featspread.rs's self-play /
candidate_features / decision-gate structure rather than inventing one).

Step 1 -- deriving the 32-key set, entirely at runtime, with NO WeightKey variant
name ever typed as a string literal anywhere in the new source file (the repo's
own registry.rs test forbids it):
  (a) features.rs's own source text is embedded via `include_str!` (a file path,
      not a key name). For every WeightKey::ALL member k, the needle
      `format!("f.set(WeightKey::{k:?}")` is built from Debug at runtime and
      checked as a substring -- keys that never appear there: 54 of 160.
  (b) 54 is too many: eleven "identity-aware, freeze-priced gates" plus
      StrengthRel are written directly by eval::linear_features via
      `out[WeightKey::X as usize] = ...`, five more (StrengthRelEarly/Late,
      WorkersLate, TechLevelsLate, HandValueLate) are reached only via the
      `.early()`/`.late()` phase-suffix indirection (registry.rs's own
      PHASE_SUFFIXED_NO_LITERAL_READER ratchet -- these have NO literal call site
      either, so a pure text scan cannot separate them from a true multiplier),
      and EndTurnBias is set in candidate_features itself. All 22 of these DO get
      real, nonzero candidate-set spread; a true multiplier-only key's phi slot is
      never written by ANY code path, so its spread is deterministically 0.0 at
      EVERY decision, forever. A small classification self-play pass (60 games,
      23,241 decisions, 22.1s) confirms this by measuring spread the same way
      featspread does: 32 of the 54 stayed at spread == 0.0 at every single sampled
      decision. That is the final multiplier-only set, matching the task's
      expected count exactly.

Step 2 -- the main measurement (3p only, champion frozen at
/private/tmp/opencensus/champ3p.json, NOT modified):
  80 self-play games, base seed 1001, 5 threads (games split across threads by a
  shared atomic counter, same pattern as bin/selfplay.rs), yielding 31,088 real
  decisions (candidates.len() > 1 after filter_resign, same gate featspread uses).
  At each decision, the baseline candidate set is scored once under the champion
  weights via eval::candidate_features/eval::dot (first-candidate-wins argmax,
  matching WeightedBot::choose's own tie-break exactly). Then, per key and per
  perturbation:
    ZERO: a COPY of the champion weights with that one key set to 0.0
    ABS:  a COPY of the champion weights with that one key set to |champion value|
  is used as BOTH the `freeze` argument to a fresh candidate_features call over
  the SAME state and legal-move list (determinization is a pure function of
  `state`, never of `freeze` -- see candidate_features's own doc comment, so this
  really is the same candidate set the champion faced, just re-priced) AND the
  vector `dot` is taken against, matching how a bot actually built with that one
  weight changed would score and choose. flip_rate_zero / flip_rate_abs = fraction
  of the 31,088 decisions where the resulting argmax MOVE differs from the
  champion's own chosen move. term_nonzero_rate/term_nonzero_n (computed once, off
  the ZERO perturbation) = fraction/count of decisions where at least one
  candidate's score actually changed when the key was zeroed -- i.e. the quantity
  it multiplies was nonzero SOMEWHERE in that decision's candidate set at all,
  independent of whether it went on to flip the argmax.
  Main pass wall time: 267.3s (80 games, 5 threads).

  Sanity check built into the method itself: every key with a POSITIVE champion
  value has flip_rate_abs == 0.0 exactly, because abs(positive) == that same
  value, so the ABS perturbation is a no-op weight vector identical to the
  champion's -- visible in every row below and confirms the harness is not
  spuriously flipping on floating-point noise.

Commands run:
  export PATH="$HOME/.cargo/bin:$PATH"
  cd /Users/pt/tta-ai/rust
  touch src/bin/multcheck.rs
  cargo clippy --all-targets -- -D warnings          # EXIT clippy=0
  cargo test                                          # EXIT test=0 (all targets, incl. new multcheck unit tests)
  cargo build --release --bin multcheck               # EXIT build=0
  ./target/release/multcheck 80 1001 5 /private/tmp/opencensus/champ3p.json

================================================================================
READING THE TABLE
================================================================================
- 24 of the 32 keys have flip_rate_zero > 0: this family is genuinely live, not
  inert, contrary to what a spread-only scan would have concluded (spread == 0.0
  for every one of them, at every player count, by construction).
- tech_board_credit is the standout: NOT just "used", but SIGN-WRONG in a way that
  costs almost twice as many decisions as simply turning it off would (27.9% vs
  13.8%). Its champion value is -25.4575; flipping the sign (to +25.4575, same
  magnitude) changes the chosen move on more than one in four real decisions. This
  is exactly the "negative multiplier on a signed value function inverts good and
  bad cards" failure mode named in the task brief, not a marginal effect.
- card_board_credit, action_board_credit are the next-largest by raw flip rate,
  both from ZERO alone (both keys are positive, so ABS is a no-op for them by
  construction -- see the sanity check under METHOD).
- event_board_credit (-1.9751) and war_board_credit (-0.4611), the two other
  named-negative examples from the task brief, both show ABS > ZERO (0.095 > 0.061
  and 0.040 > 0.017 respectively) -- consistent with, though far less dramatic
  than, tech_board_credit's sign problem.
- 8 keys never fired at all (term_nonzero_n = 0) -- see CAVEATS.

================================================================================
CAVEATS
================================================================================
1. 3P ONLY. The task scoped this to 3p; no 2p/4p measurement was run. The eight
   keys that never fired here (below) may be reachable, and possibly decisive, at
   2p or 4p -- this file makes no claim either way for other player counts.

2. EIGHT KEYS NEVER TOUCHED A SINGLE CANDIDATE'S SCORE across all 31,088
   decisions (term_nonzero_n = 0): defense_bonus, gov_action_cost,
   card_board_bonus, card_rate_credit, unit_strength_credit, wonder_board_credit,
   bonus_card_credit, tactic_shortfall_cost. Two of these (defense_bonus,
   tactic_shortfall_cost) already carry champion weight 0.0, so their ZERO
   perturbation is a no-op by construction and this is uninformative for them.
   The other six carry live, nonzero champion weights (card_rate_credit -11.2057,
   bonus_card_credit 3.5085, gov_action_cost -2.0240, wonder_board_credit 0.5253,
   card_board_bonus 0.0653, unit_strength_credit 0.0095) yet the quantity each
   multiplies was zero in every single sampled 3p decision. This measurement does
   not distinguish "dead code" from "gated on a condition genuinely rare or
   unreachable at 3p" -- that would require reading each key's call site in
   cards.rs/events.rs/etc., which was out of scope here (see the task's own
   framing: report the finding, do not chase it further).

3. GAME COUNT / DECISION COUNT: 80 games, 31,088 decisions, comfortably inside the
   task's 20,000-40,000 target. A larger sample would tighten the low-flip-rate
   tail (several keys sit on single-digit or low-double-digit flip counts) but is
   very unlikely to change the ranking of the top 5-6 keys, whose flip counts are
   in the hundreds to thousands.

4. THE CLASSIFICATION PASS uses a SEPARATE, smaller self-play sample (60 games,
   23,241 decisions, same champion, same base seed 1001) purely to confirm which
   of the 54 features.rs-absent keys have deterministically zero candidate-set
   spread. This is a structural fact (a key's phi slot is either written by some
   code path or it never is), not a statistical one, so a different sample size
   would not change which 32 keys are selected -- but this was not proven by
   exhaustion, only by a large, varied sample across 60 full games.

5. TIE-BREAK: both baseline and perturbed argmax use first-candidate-wins on
   exact score ties (matching WeightedBot::choose's own `val > bv` strict
   inequality). A perturbation that produces an exact tie with the original
   winner is not counted as a flip, matching what the real bot would actually do.

6. flip_rate_zero and flip_rate_abs answer two different questions and are not
   directly comparable in magnitude for keys whose champion value is small
   (e.g. unit_strength_credit at 0.0095): ZERO removes a small-but-real
   contribution, ABS on an already-near-zero value barely perturbs it either way,
   so a near-zero flip rate for such a key says little either way.

7. FILES TOUCHED: rust/src/bin/multcheck.rs is new. No existing file under
   rust/src/bots/ was modified -- both eval::candidate_features and eval::dot were
   already `pub fn`, so no visibility change was needed anywhere.

================================================================================
KEY DERIVATION DETAIL (for reproducibility)
================================================================================
160 total WeightKey variants. 106 appear as `f.set(WeightKey::X` in features.rs.
54 do not. Of those 54, 22 get a phi slot some other way (11 identity-aware
freeze-priced gates + StrengthRel, written directly in eval::linear_features; 5
phase-suffixed keys reached only via .early()/.late(); EndTurnBias, set in
candidate_features itself) and were excluded by the runtime classification pass.
The remaining 32 are the multiplier-only family this file measures.
