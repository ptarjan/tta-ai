TACTIC BLACKOUT DIAGNOSIS -- TacticShortfallCost / TacticReachCredit read exactly zero
term_nonzero over 130,180 real self-play decisions (2p/3p/4p), per
analysis/multiplier_flips_2026-08-25.txt section 4.3, while their sibling
TacticBoardCredit flips 6.47% of 3p decisions.

BOTTOM LINE
===========
Neither read is unreachable code. Both execute constantly -- in a 5-game
counterfactual sweep at 3p alone, the line at cards.rs:1410 (TacticShortfallCost) fired
86,480 times and the line at cards.rs:1446 (TacticReachCredit) fired 537,755 times.
The zero comes from upstream of the code entirely: at 2p and 4p the enclosing function
is never CALLED because a sibling gate (TacticBoardCredit) is exactly 0.0 in those two
champions; at 3p, where the function IS called, each weight's own runtime value has
independently been neutralized to exactly 0.0 before the game ever starts -- one by
the hill-climb itself, the other by the engine's own load-time sign-repair. Verdict
per key below. Neither is (a)/(b)/(c)/(d) cleanly; both are closest to (c) ("multiplies
by a quantity that is always 0"), except the zero quantity is the WEIGHT ITSELF, fixed
before self-play begins, not a state-derived multiplicand computed during play.


SECTION 1 -- THE TWO DEAD READS: ENCLOSING FUNCTION AND GUARD CHAIN
=====================================================================

Both reads sit in the same function, rust/src/bots/weighted/cards.rs:1396-1448:

  pub fn tactic_value(id: CardId, state: &GameState, idx: u8, w: &Weights) -> f64 {
      let p = &state.players[idx as usize];
      let (val, armies, short_by_type) = effects::tactic_shortfall(p, id);   // 1398
      let current = effects::army_strength(p);                              // 1399
      let gain = (val - current).max(0) as f64;                             // 1400
      if gain > 0.0 {                                                       // 1401
          let strength_m = yield_marginal(WeightKey::Strength, ...);        // 1408
          let short: i32 = short_by_type.iter().sum();                      // 1409
          let shortfall_w = w.get(WeightKey::TacticShortfallCost);          // 1410 <-- READ 1
          return (gain * strength_m - f64::from(short) * shortfall_w).max(0.0); // 1411
      }
      if armies > 0 { return 0.0; }                                         // 1413-1419
      let card = id.get();
      let potential = (i32::from(card.effects.strength) - current).max(0);  // 1434
      if potential == 0 { return 0.0; }                                     // 1435-1436
      let mut cost = 0.0;
      for (i, &kind) in effects::UNIT_SLOT_TYPES.iter().enumerate() {
          match unit_type_reach_cost(state, p, kind, short_by_type[i], w) {
              Some(c) => cost += c,
              None => return 0.0, // no visible route to this unit type       // 1442
          }
      }
      let strength_m = yield_marginal(WeightKey::Strength, ...);
      let reach_credit = w.get(WeightKey::TacticReachCredit);                // 1446 <-- READ 2
      (reach_credit * (f64::from(potential) * strength_m - cost)).max(0.0)   // 1447
  }

Full guard chain from function entry to each read:
  * line 1401 `if gain > 0.0` -- the ONLY guard between entry and READ 1 (line 1410).
    True means: playing this specific hand-tactic card, using units the player already
    owns, would beat the army currently in play.
  * line 1413 `if armies > 0` -- returns 0.0 before READ 2 if the candidate is
    formable now but not an improvement (handled already by the branch above).
  * line 1435 `if potential == 0` -- returns 0.0 before READ 2 if the card's printed
    strength does not exceed the current army at all.
  * lines 1439-1444 -- a loop over up to 3 unit types (composition never needs Air,
    per cards.rs:591-593 comment); ANY missing visible route (`unit_type_reach_cost`
    returns `None`) short-circuits to `return 0.0` before READ 2 is ever reached.
  * READ 2 (line 1446) is reached only if gain<=0, armies==0, potential>0, AND every
    composition unit type has a visible route (owned tech, or a matching card
    currently sitting in the CIVIL row -- see Section 4).

in principle, but because both the trained value and the test's zero ARE the same
number, always, at 3p.

At 2p and 4p, a separate, simpler mechanism applies and IS answer (a): see Section 2.

SECTION 3 -- THE CONTRAST WITH TacticBoardCredit (THE KEY THAT FIRES)
========================================================================

All three keys -- TacticBoardCredit, TacticShortfallCost, TacticReachCredit -- are
classified `NonNegative` in `sign_intent` (weights.rs:1184, 1190, and 1595-1597
respectively). `NonNegative` is enforced by `dominance_repair`
(rust/src/bots/weighted/eval.rs:923), which runs on every champion load
(`parse_weights` ends with `Ok(dominance_repair(&w).0)`, eval.rs:1099) -- so
`multcheck`, `climb`, and every real bot all see the REPAIRED vector, never the raw
JSON. The clamp itself, eval.rs:988-998:

      for (k, why) in non_negative_gates() {
          let v = out.get(k);
          if v < -1e-12 {
              viol.push(Violation { weight: k, value: v, ... });
              out.set(k, 0.0);
          }
      }

Raw (as-saved-in-JSON) vs. actual-runtime (post-`dominance_repair`) value, all three
frozen champions:

                     tactic_board_credit   tactic_shortfall_cost   tactic_reach_credit
  2p  raw:                 0.0000                 0.004455              -0.411641
      runtime:             0.0000                 0.004455               0.000000 (repaired)
  3p  raw:                 0.041454               0.000000              -0.071109
      runtime:             0.041454               0.000000               0.000000 (repaired)
  4p  raw:                 0.0000                 0.000000               0.197084
      runtime:             0.0000                 0.000000               0.197084

  (2p/4p runtime values for shortfall/reach are moot: tactic_value is never called
  there at all, per Section 2, regardless of what these weights individually equal.
  4p's reach_credit is positive and genuinely un-repaired, but irrelevant for the
  same reason.)

The concrete, one-sentence contrast: TacticBoardCredit is the outermost of the three
gates (cards.rs:1948, `if tc != 0.0`) and at 3p the hill-climb happened to leave it
POSITIVE, so it survives its own `NonNegative` repair with no clamp and nothing
downstream of it is masked; TacticShortfallCost is a genuinely trained-to-exactly-0.0
value at 3p (not repaired -- it was never negative, the climb just parked it there),
and TacticReachCredit is a genuinely NEGATIVE trained value at 3p (and at 2p) that
`dominance_repair`'s own `NonNegative` gate silently overwrites to exactly 0.0 on
every load, before any game runs -- confirmed directly: 537,755 runtime reads of
`WeightKey::TacticReachCredit` in the 3p sweep, one hundred percent of them 0.0,
against a raw file value of -0.07110897586662696.


SECTION 4 -- WHAT GAME STATE WOULD MAKE THE DEAD LINES EXECUTE, AND IS IT REACHABLE
=======================================================================================

This is the one part of the finding that is NOT about unreachable code: both lines
already execute, copiously, in real self-play (Section 1). The "state" question is
really "what would make the CHAMPION carry the weight all the way through to the
scoreboard instead of the load-time repair or the climb's own convergence erasing
it first":

  * TacticShortfallCost (3p): needs the hill-climb to walk this weight away from
    0.0. Nothing in the code prevents it; the climb simply has not (or has walked it
    back to 0.0, e.g. because the term rarely helped -- `short` was 2 in every
    sampled hit, so the term is being computed against real, nonzero shortfalls; the
    climb had genuine signal available and chose ~0 anyway). This is a training
    outcome, not a code-reachability question, and the state that would change it
    (a different, better-tuned champion) is fully reachable -- it just is not the
    state on disk right now.

  * TacticReachCredit (2p and 3p): needs a NON-NEGATIVE trained value to survive
    `dominance_repair`. The current champions have both walked it negative (2p:
    -0.4116, 3p: -0.0711). Nothing about game state gates this -- it is purely
    "what sign did the optimizer converge to", and it is caught by a repair rule
    whose own doc comment (weights.rs:1551-1554) says a negative reach credit would
    otherwise "let a reach-cost-exceeds-benefit tactic ... read as a fabricated
    positive", i.e. the clamp is protecting against a real inversion bug, not an
    accident -- so the fix is not "let the negative value through", it is "the
    weight needs to retrain positive, or this term is structurally worth removing/
    renaming".

  For TacticBoardCredit itself to matter (which it already does, at 3p only): needs
  ANY hand_military Tactic card to be held while both hand_mil_potential and
  tactic_board_credit are nonzero in the acting player's own trained vector -- an
  entirely ordinary mid-game state (holding an un-played tactic card), reachable in
  a real 2015-base-game game trivially and often (confirmed: 1.27M calls in 5
  games).

  Confirmation that CardType::Tactic never reaches `card_potential_core` through
  the ROW path (only the HAND path matters here): `state.card_row` is declared at
  state.rs:1496 with the doc comment at state.rs:15, "SS2.1 -- the civil card row is
  thirteen slots" -- it is explicitly the CIVIL row only; Tactic/Aggression/War/
  Pact/Event cards never sit in it. This is why `hand_total`/`hand_potential`/
  row.rs's row-pricing functions (all of which read `hand_civil`/`state.card_row`)
  never see a Tactic card at all, and only `hand_mil_potential` (reading
  `hand_military`) can reach `card_potential_core`'s Tactic branch.
