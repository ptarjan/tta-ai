1. THE FIVE KEYS
====================================================================

All five are `WeightGroup::Cards`, all authored default 0.0, all
`SignIntent::Free`. JSON names are the screening rig's own column names
(`feature_screen.rs`'s `EXTRA_KEYS`), so the screen reports and a champion file
can be read against each other with no translation step.

  WeightKey                   JSON name                      screen spread
  ----------------------------------------------------------------------
  HandActionCount             hand_action_count                    0.5321
  HandSpecialTechCount        hand_specialtech_count               1.8039
  HandScienceCostTotal        hand_science_cost_total              0.7739
  HandScienceShortfallTotal   hand_science_shortfall_total         0.5400
  HandResourceCostTotal       hand_resource_cost_total             1.5291

Formulas, all over `p.hand_civil` and all in phi's own units:

  HandActionCount            count of `CardType::Action`
  HandSpecialTechCount       count of `CardType::SpecialTech`
  HandScienceCostTotal       Σ science_price(c)
  HandScienceShortfallTotal  Σ max(0, science_price(c) - my science)
  HandResourceCostTotal      Σ printed `resource_cost`, over EVERY card

`science_price` is the existing hand classifier: printed `science_cost` for a
levelled/tech type, `peaceful_cost` for a Government, nothing at all for a
Leader or an Action card. `HandResourceCostTotal` sums over every card and not
only the priced ones, because a card that costs no science to develop can still
cost resources to build (RULES_SPEC 7.2) -- and because that is what the
screened column did.

WHY THE GROUP IS `Cards`. It is the group `HandCivil` uses, and the same group
`HandPerishable` and `HandOverCapacity` use with a stated reason: both are
"properties OF the civil hand computed in the same pass over it". All five of
these are exactly that, and they are accumulated in literally that same single
loop in `features.rs` -- so a `Group` mutation that reprices "what is in my
hand" moves all of it together.


--------------------------------------------------------------------
1a. SIGN_INTENT -- Free, all five, argued not defaulted
--------------------------------------------------------------------

[[tta-sign-gate-snaps-to-zero]]: a sign_intent is a hard constraint enforced on
every load and every mutation, and a wrong one destroys the key's accumulated
magnitude every time. The bar is a rules citation. None of the five clears it,
and each fails it for its own reason:

  *Count keys   `HandActionCount`/`HandSpecialTechCount` are RESIDUALS in
                exactly the sense `sign_intent`'s existing `HandCivil` arm
                gives: the per-type counts PARTITION `hand_civil`, so each is a
                component of a total already classified `Free` and may
                legitimately price as a negative correction against it.

  *Cost keys    `HandScienceCostTotal`/`HandResourceCostTotal` look like costs
                and are not. The `HandMilValue` arm already says why: a card
                sitting in hand is never a rules-level cost, because §2.5's
                hand limit is enforced by `costs::can_take` making the TAKE
                illegal -- a full hand is a legality constraint and can never
                surface as an evaluation penalty. Worse for a gate, printed
                price is CONFOUNDED WITH CARD POWER: an Age III card costs more
                because it does more (RULES_SPEC 7.1/7.2 price it that way), so
                an expensive hand is simultaneously a strong one.

  *Shortfall    This is the one with a tempting gate. `SHORTFALL_GATES` and
                `TacticShort` both price a marginal-need shortfall
                `NonPositive`, and "short of science for my hand is bad" reads
                the same way. IT DOES NOT TRANSFER, because this column's ZERO
                POINT IS AMBIGUOUS: it reads exactly 0.0 both when every card
                in hand is affordable (good) and when the hand is EMPTY (bad --
                the state `HandCivil` exists to price). A gate is a claim about
                the sign of a coefficient measured against that zero, and a
                zero that means two opposite things cannot support one.

Unlike 78acfbc, no arena was run here, so this report offers NO empirical
directional hint either. There is nothing to promote to a gate and nothing
being withheld from one.

1c. WHY ONLY TWO OF THE SEVEN TYPE-FAMILY COUNTS
--------------------------------------------------------------------

The screen carries seven civil-hand type counts (prod, urban, unit, gov,
leader, action, specialtech). Only two are promoted, and that is deliberate for
the reason 78acfbc gives for dropping the far/level rate buckets: the seven
counts PARTITION `hand_civil`, so all seven plus `HandCivil` would be eight
columns over a seven-way partition summing to a column phi already has, adding
a flat direction to the weight space. Two of seven cannot do that -- there is no
linear combination of `HandActionCount`, `HandSpecialTechCount` and `HandCivil`
that is identically constant, because the other five families are free to vary.
Promoting the two the screen actually ranked keeps the space honest.

2. ONE DEFINITIONAL DEVIATION FROM THE SCREEN'S ARITHMETIC, AND
   FOUR PLACES THERE IS NONE
====================================================================

The screening rig compares each card's science price against `p.science`, the
RAW stored value. `features.rs` does not have a raw science: its
`WeightKey::Science` is `p.science + g(GainFeature::Science)`, the
deferred-credit-adjusted number, and it is set a few lines above this loop.

`HandScienceShortfallTotal` is hinged against phi's OWN `Science`, not
re-derived from `p.science`. Reason, and it is 78acfbc's reason restated: a phi
coordinate that disagreed with the `Science` value sitting in the same function
would be a second, quieter definition of what this player can pay. Section 4
measures the cost of that choice and it is +0.06%.

THE OTHER FOUR HAVE NO DEVIATION AT ALL, and section 4 confirms it to the sixth
decimal place. Counts of a card type and sums of a printed cost field read
nothing but the cards in hand; there is no rate, no deferred credit and no pact
adjustment anywhere in them, so the promoted key and the screened column are the
same arithmetic on the same list. This is a real contrast with 78acfbc, where
all seven promoted keys sat ~1% off their screened columns.

ONE CLASSIFIER, NOT TWO. `hand_card_affordable` (which feeds the existing
`HandOverCapacity`) and the two new science keys now both read a single new
function, `hand_science_price`, which returns a three-way
`Science(u8)`/`Free`/`NotInCivilHand` rather than an `Option`. The third variant
exists so "free to play" and "cannot be in this hand at all" stay
distinguishable: they contribute the same 0.0 to a cost sum but are opposite
answers to affordability, and collapsing them would have silently changed
`HandOverCapacity`. `hand_card_affordable`'s behaviour is unchanged -- it is now
a three-arm match over that enum, and section 7's existing tests for it still
pass untouched.

NOT SPANNED, AND CHECKED. 78acfbc dropped a planned column on an exact-redundancy
proof, so the same question was asked of all five:

  * `HandResourceCostTotal` -- phi carried NO resource-cost reading of the hand
    whatsoever. `HandValue` sums printed levels, `HandPotential` prices yields,
    and neither reads `resource_cost`. Science buys the develop and resources
    buy the build; only the first half was represented.
  * `HandScienceCostTotal` -- correlated with `HandValue` (= Σ level+1) but NOT
    a linear function of it: two cards of the same level in different lanes
    print different science costs, so no fixed coefficient maps one sum to the
    other.
  * `HandScienceShortfallTotal` -- `HandOverCapacity` COUNTS the cards over the
    affordability line; this SUMS how far over. A count is not a linear function
    of the magnitudes it counts.
  * the two type counts -- phi has no per-type civil-hand count at all.

None is in the span of existing columns, so unlike 78acfbc nothing had to be
dropped.

THE NEW GUARD TEST

    linear_features_reproduces_evaluate_on_played_forward_positions_with_the_
      hand_inventory_keys_live

Modelled on 78acfbc's `..._at_a_nondefault_vector`, with ONE deliberate
strengthening: THE PREMISE IS ASSERTED PER KEY, NOT IN AGGREGATE. The sibling
test counts "the new coordinates were nonzero somewhere" across all seven of its
keys together, which passes even if one of them is structurally zero at every
position -- and that is precisely the failure that matters, because a coordinate
that never leaves 0.0 in phi contributes nothing at any weight and the climb
would price it forever against a column of zeros.

Real self-play driven to depth at 2p/3p/4p, sampling every 5th move past move
10, asserting dot(w, candidate_features) == `rank_moves`' own score for every
candidate, at a weight vector giving every key a distinct non-zero value (and a
different ramp from the sibling test, so the two are not one arithmetic
coincidence checked twice). It then requires each of the five individually to
have been non-zero on a floor of sampled candidates -- 1000 for the two cost
sums, 200 for the shortfall and the action count, and 50 for
`HandSpecialTechCount`, which gets the lowest bar on purpose because the screen
measured it all-zero on 67.5% of decisions. Rare is not unreachable, and the
floors are set to fail on the second without failing on the first.

It passes, and it does not read `sources/`, so it runs in a fresh checkout
without the private corpus symlink.
