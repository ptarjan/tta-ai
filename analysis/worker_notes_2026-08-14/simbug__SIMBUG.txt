BOTTOM LINE
-----------
FIX LANDED, zero regressions, 2 wins, unit-tested RED then GREEN. Root
cause: `Replayer::resolve_political_decision` (rust/src/replay_common.rs)
is the ONE remaining call site in the whole file that applies a `Move` by
calling `apply::apply` DIRECTLY instead of through `Self::try_apply` --
every other caller gets a free, automatic `military_hand_deficit` repay
whenever `apply::apply` grows a seat's `hand_military` (`try_apply`'s own
post-apply loop, see that function's doc). `resolve_political_decision`
never got that hook, so any deficit owed by ANY seat -- including a fresh
one THIS SAME call just incurred for the decider one line above, in its own
"no disposable filler" branch -- can never be repaid by a card drawn as
part of the revealed political card's own IMMEDIATE effect (an `AllPlayers`/
`StrongestPlayer`/etc. `drawMilitaryCards` block: Development of Politics'
"Each player draws 3 military cards.", Politics of Strength, ...), because
that draw happens synchronously inside the SAME `apply::apply` call this
function issues directly. The debt then sits on the books forever while the
drawn card(s) stay uncompensated in hand: a permanent phantom card. This is
the exact shape 81 of the 103 `SimulatorBug`/`PrepareEvent` rows show
(simulator excess = journal excess + 1, the classic unpaid-deficit
signature) -- not a per-game hand-tracing question, a structural gap in
which call sites get the repay hook and which don't.

THE FIX
-------
`resolve_political_decision`, right around its own `apply::apply(&mut
self.state, mv)` call (rust/src/replay_common.rs, ~line 1918): snapshot
every seat's `hand_military.len()` immediately before the call, then after
it, call `self.repay_military_hand_deficit(seat, growth)` for every seat
whose hand grew -- byte-for-byte the same loop `try_apply` already runs
right after its own `apply::apply` call. No new mechanism, no new field: it
just gives this one remaining caller the SAME hook every other caller
already has. 22 lines of doc comment (the "why" -- this class of bug is
easy to reintroduce at a NEW `apply::apply` call site if a future edit adds
one without realizing `try_apply` is what makes the repay automatic) + 8
lines of code.

WHY THIS IS DIFFERENT FROM THE THREE EARLIER PHANTOM-CARD FIXES
------------------------------------------------------------------
The three sites fixed earlier today (`resolve_political_decision`'s own
"no filler to sacrifice a PREPARED card" branch, `ground_for_consumption`,
`ground_auction_winner_hand`) all fixed the INCUR side: recording a debt
instead of silently washing a push-then-remove to net zero. This fix is on
the REPAY side: even with the debt correctly recorded, one call site (this
same `resolve_political_decision`, ironically) could never pay it back
when the repaying growth happened to be a side effect of its OWN apply
call rather than a later, separately-dispatched `Move`. The two problems
share a symptom (a permanent phantom card) but are opposite halves of the
same ledger.

RULED OUT / NOT RE-ATTEMPTED
-----------------------------
- Checkpoint-TIMING artifact (the task's own named risk: "a deferred
  cascade meant our live value was simply behind, not wrong"): ruled out
  for this specific mechanism because the fix changes real, permanent
  `hand_military` CONTENTS and `military_hand_deficit` STATE inside one
  `apply::apply` call, not merely which checkpoint a value gets attributed
  to -- confirmed by the corpus's own completion-count and exact-score
  movement (648->650 completed, 604->605 exact), which a pure timing/
  attribution artifact could not produce.
- `resolve_political_decision`'s PrepareEvent-cost eviction restricted to
  CardType::Event/Territory victims: `decider3__DECIDER3.txt` already
  measured this at 139 regressions on the full corpus and closed it. Not
  re-attempted here.
- `handfix__HANDFIX.txt`'s own warning that the `SimulatorBug`/
  `PrepareEvent` bucket may be a PROXIMITY artifact ("whichever ledger-
  tracked action most recently preceded the checkpoint", not necessarily
  causal): true in general, but this session's mechanism does not depend
  on that framing at all -- it is a structural code-path gap (one call
  site missing a hook every sibling call site has), independently
  verified by direct code reading (`resolve_political_decision` vs.
  `try_apply`) and confirmed by a deterministic, hand-traced repro
  (`7522697`), not inferred from the bucket's own label.
- Did NOT attempt the 17-row "simulator short by one" sub-shape
  (`decider3__DECIDER3.txt`'s eviction-collision mechanism) or the other
  six `SimulatorBug` categories (Discard 56, Draw 54, ConsumingPlay 50,
  ColonizeConsume 9, DefenseConsume 4, ColumbusConsume 3) -- out of this
  session's budget. See HANDOFF below for whether this same missing-hook
  shape could explain any of them.
