ONE GENUINE BUG FOUND IN PASSING, DOES NOT EXPLAIN THIS GAME'S SHORTFALL:
Round 13, Orange plays "Crime Wave" ("The two weakest civilizations lose 3
culture and return 1 blue token to the box.; Purple loses 3 culture and 1
blue token"). Confirmed via the added debug print that this fires through
`events::apply_gains_block`'s bare `blueTokens` key handling
(`events.rs`, the block starting "// blueTokens (events.py:91-93)"):
`p.blue_total = (p.blue_total as i32 + sign * eff.blue_tokens as i32)...`
-- this ONLY decrements the abstract `blue_total` counter. It does NOT
remove a worker from any tableau card, and does NOT touch `workers_free` or
`yellow_bank` at all. Observed directly: `TMPDEBUG_P1` (workers_free,
yellow_bank, blue_total) goes from `(0, 8, 16)` to `(0, 8, 15)` across this
event -- yellow_bank UNCHANGED.

This looks wrong against RULES_SPEC.md line 185 (§6.5) and FAQ p.15's
"Lose 1 population" rule ("unused worker -> yellow bank; if none, a worker
off a card, owner's choice") -- Crime Wave's card text differs subtly
("return 1 blue token to the BOX", not "to the yellow bank"), which is
consistent with yellow_bank staying unchanged (permanent removal, not a
returned-to-bank grant), BUT the token still has to come from SOMEWHERE
physical: either an unused worker (decrementing `workers_free`) or a
worker on a specific card (decrementing that card's `.workers` and
requiring a player/engine choice of which card), per the same "owner's
choice" mechanism `Special::DecreasePopulation`/`QueueItem::LosePop`
already implements correctly for Barbarians. `apply_gains_block`'s generic
`blueTokens` key is a DIFFERENT, much weaker code path (a bare counter
decrement) that was apparently written for cards where "blue tokens" means
capacity/scoring bookkeeping, not this card's actual "you lose a placed
population token" effect.

In THIS specific firing, Purple had `workers_free=0` already, so BOTH the
current behavior and a corrected LosePop-based behavior would need to take
the token off a card either way -- meaning this specific instance is a
wash for `workers_free` bookkeeping and does NOT explain 7523640's round-17
shortfall (confirmed: `workers_free` truly does not change across this
event in the trace either way). Left UNFIXED this pass: (a) it doesn't
explain either of this pass's two negatives, so fixing it blind is scope
creep without a corpus win to point at; (b) properly routing it through
`QueueItem::LosePop` would, in SOME other game where Crime Wave fires while
the target actually HAS a free worker, correctly DECREASE `workers_free`
compared to today's no-op-on-workers_free behavior -- the opposite
direction from what either of this pass's shortfalls needs, and an
unverified behavior change that could easily regress a currently-passing
game that happens to depend on today's (wrong but happens to net out)
no-op. Flagged for a future pass with dedicated budget to trace it properly
and add a corpus-measured RED/GREEN fix -- see HANDOFF.
