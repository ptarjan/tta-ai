Journal (/private/tmp/bgo-journals/journals/7523354.tsv):

    line 251: "Purple discards 1 card"
    line 252: "Orange plays event ..." (next player's turn)

`REPLAY_DEBUG_ALL=1 ./target/difftest/replay ... 7523354` shows, right at
this point:

    DEBUG draw_military_step: idx=1 round=14 military_actions_unused=3 n_drawn=3

        phase Actions upcoming=(Discard, None) pending_top=None
    -> StuckPending("decider 0 != expected actor 1, phase Actions, no pending")

The engine computes hand_military_len=4, limit=4 at the pre-draw discard
check (interact.rs::discard_excess_military, RULES_SPEC.md 6.7's "military
hand limit = military action total, checked ONLY at end-of-turn step 1"), so
it opens no discard pending, draws 3 cards, and immediately hands the turn to
Orange with nothing pending. The journal's very next line is a discard the
engine has no mechanism left to satisfy: decider is already Orange (0),
expected_actor (whoever the next real journal action names) is Purple (1),
phase is Actions (post-EndTurn->PolPass), pending is empty. Classic shape for
this whole bucket.

Cross-checked against this file's OWN existing "military hand ledger" oracle
(`prescan_military_hand_ledger` / `GameResult::hand_ledger_verdict`,
replay_common.rs ~3794-3902): a SEPARATE bookkeeping built purely by parsing
journal text deltas (draws/discards/consuming-plays/etc.), independent of the
forward simulator's own `hand_military` Vec. For this exact game/line it
reports:
    DUMP 7523354 line 250 (round 14 age III, Purple): journal excess 1,
    simulator excess 0, ledger excess 1 (ledger's own last event:
    Some((ConsumingPlay, 233)))
The ledger (built from journal text alone) AGREES with the journal that a
discard was owed (excess 1); the forward simulator's own hand array says
excess 0. This is the `HandLedgerVerdict::SimulatorBug` classification --
the project's own diagnostic language for "the simulator's bookkeeping is
provably wrong, not just under-modelled." So the root cause is NOT a missing
rule -- it's the reconstructed `hand_military` Vec being 1 card short of
truth by the time this checkpoint is reached.

I fully verified the arithmetic of the "last event" the ledger points to
(ConsumingPlay at lineno 233, Purple playing "Aggression: Raid" against
Orange) by hand:
  - Pre-turn hand (after round 13's draw of 2, itself verified correct):
    5 cards: [Aggression: Infiltrate, Developed Territory (II),
    Wealthy Territory (II), + 2 new draws from round 13].
  - `ground_for_consumption` (replay_common.rs ~2230) finds "Aggression:
    Raid (I)" not already in hand, pops a disposable victim
    ("Developed Territory (II)", not needed later per DiscardSolver) (-1),
    pushes "Aggression: Raid (I)" (+1) -- net 0, still 5 cards.
  - `try_apply(Move::Aggression{...})` removes the played card (-1) -- 4
    cards left: [Aggression: Infiltrate, Wealthy Territory (II), + 2 new
    draws], which EXACTLY matches the debug-printed hand at the round-14
    discard check. This arithmetic is CORRECT -- the ConsumingPlay event is
    not itself where the missing card went missing. It is simply the most
    RECENT hand-touching event before the checkpoint, not the cause (see
    "RULED OUT" section -- this file's own `LedgerEventKind::ColumbusConsume`
    doc comment, replay_common.rs ~3845-3867, explicitly warns that
    "last event" is often exactly this kind of red herring from a PRIOR
    session's own investigation of the identical symptom).

SEPARATELY, while tracing this: the card BGO actually calls "Raid" here is
misresolved to the wrong age-sibling. `corpus::build_card_index` maps the
bare "Raid" name BGO always prints to an ARBITRARY sibling (its own doc
comment, corpus.rs ~107-117) -- for TakeCard this gets corrected via
`best_age_sibling` (replay_common.rs ~6287) and, more precisely where
evidence allows, via `resolve_named_card_by_effect` (~3447, called only from
`free_civil_action_move`'s "using X" parse, ~6155). Aggression/DeclareWar/
ProposePact/PlayTactic plays go through `consume_named_military_card` /
`ground_for_consumption` instead (~2258), which does NO age-sibling
correction at all -- `resolve_named_card_by_effect`'s own match has a
`Move::Aggression { .. } => None` arm (~3463) that is simply dead code today
(nothing ever calls it with `wanted = Move::Aggression`).
Confirmed on this exact line: BGO logs "Purple plays Raid against Orange
Destroy up to 2 of your rival's urban buildings: one of age II or older and
one of age I or older... Purple uses 2 military action" -- RULES_SPEC.md 5.5
identifies this AGE II TEXT ("...2 urban buildings: one of Age II or older
and one of Age I or older...", 2 MA) exactly, not Age I's ("destroy a level
0-1 building", 1 MA). `card_index` nonetheless resolves the bare "Raid" to
"Aggression: Raid (I)" (card_table.rs ~2274, military_action_cost: 1), so
the engine only deducts 1 of Purple's 4 military actions instead of 2,
leaving `military_actions` (the per-turn remaining budget) 1 too high for
the rest of the turn -- which is exactly why `n = military_actions.clamp(0,3)`
computed 3 unused actions and drew 3 cards where the journal says 2.
THIS IS A REAL, SEPARATE BUG (wrong MA deduction, wrong draw count,
eventually wrong hand contents/scores) but I confirmed by hand (see above)
that it does NOT explain the missing discard at line 251 -- the hand-COUNT
arithmetic around this exact consumption is correct regardless of which
age-sibling gets picked (a play always removes exactly 1 hand card, whichever
identity). Left unfixed: fixing it properly needs (a) an
`resolve_named_card_by_effect`-style `Move::Aggression` arm keyed off the
"uses N military action" clause (mirroring `trailing_gets_civil_action`,
replay_common.rs ~3427, matching against `family_siblings(named)`'s
`military_action_cost` field, which is unique per age for Raid/Infiltrate/
Annex but NOT for Plunder, whose 3 ages all cost 1 MA -- would need to stay a
no-op there), and (b) fixing the multi-building-destroy choice shape for
Raid II/III (their `special` list needs 2 `DestroyUrbanBuildings` entries,
not 1) plus the "half of DOUBLE cost" resource-gain formula. Out of scope
for THIS bucket; flagged for a future session/bucket.

MECHANISMS I RULED OUT FOR THE SIMULATORBUG CAUSE
----------------------------------------------------
1. `resolve_political_decision`'s PrepareEvent "no disposable filler exists"
   deficit path (replay_common.rs ~1780-1810, `military_hand_deficit`) --
   ALREADY has a self-documented, intentional, imperfect fallback: when no
   disposable victim exists at PrepareEvent-claim time, it records a signed
   deficit instead of silently netting to zero, repaid later by
   `repay_military_hand_deficit` (~2277) the next time hand_military grows
   for real, but "does not claim to close it in every case" (own doc). I
   added `REPLAY_DEBUG_ALL`-gated eprintln!s at BOTH the deficit-incurred
   site and the deficit-repay-stalled site (this is the diagnostic half of
   the shipped patch) and reran all 4 hand-traced games:
       NO deficit was ever incurred or stalled in ANY of the 4 games.
   This mechanism is exonerated for these 4 games specifically (it may still
   be the correct explanation for OTHER games in the 78, unverified).

2. `ground_for_consumption`'s victim-swap-then-consume arithmetic (used by
   Aggression/DeclareWar/ProposePact/PlayTactic) -- hand-verified card-by-card
   for 7523354's Raid consumption (see STEP 1 above): nets to -1 correctly
   whether or not a victim is found, UNLIKE what I initially suspected (if no
   victim is found it still pushes the named card, and the immediately
   following `try_apply` still removes it, netting 0 -- WRONG DIRECTION to
   explain an undercount anyway: that failure mode would make the simulator
   OVER-count, not under-count, so it could never explain "simulator excess
   0 < journal excess 1"). Not the cause.

NONDETERMINISM (tangential finding, flagged for whoever owns replay/replaystats)
-----------------------------------------------------------------------------------
While reconciling my own before-sweep against the coordinator's central
baseline I found `replay` gives a DIFFERENT per-game verdict for at least
one game (7521561: my run says COMPLETE, the coordinator's independently-
generated `/private/tmp/full_baseline_0814.txt` -- same commit 3fc32b5, same
binary -- says STOPPED) despite matching action counts and discard counts
("chosen=26 forced_collision=0" -- i.e. ALL 26 discards for this game are
resolved by ARBITRARY tie-breaking among candidates). This strongly suggests
the "arbitrary" tie-break in the discard solver (or similar) is not stable
across process runs (likely HashMap/HashSet iteration order, which is
randomly seeded per-process in Rust's default hasher) -- meaning per-game
COMPLETE/STOPPED verdicts for games with `chosen > 0` are not fully
reproducible run-to-run even with zero code changes. This did not block my
own investigation (the coordinator's guard files are authoritative and I
used those for the final check) but is worth a dedicated look: any bucket
whose repro game has `chosen > 0` discards should be treated with a bit of
suspicion if a "before" and "after" run disagree by exactly one game with no
apparent cause.
