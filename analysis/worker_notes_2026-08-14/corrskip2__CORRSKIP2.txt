===========================================================================
THE MODEL BUILT (all three of the owner's live corrections, in order)
===========================================================================
1. Tokens are bound to the specific denomination they were placed at and
   NEVER move to a higher one (RULES_SPEC S6.4 / CoL p.11, restated by the
   owner in person: "if you develop a new farm all the tokens stay on the
   old farm... blue tokens are bound to their card, when you put a new card
   down you don't move the tokens, they just stay put and you can spend
   them"). This kills the Develop-vs-Upgrade distinction CORRSKIP chased --
   there isn't one; both just never retroactively move existing stock up.
2. PRODUCTION (S6.6 step 3c/3e) places exactly one NEW token per producing
   WORKER, at that worker's own card's denomination -- not a scalar amount
   re-packed for minimal token count afterward. Owner's words: "during
   production you produce wherever your yellow tokens are."
3. Non-production gains (event/card/tactic effects with no worker attached,
   e.g. "gain N resources") are NOT pinned down by RULES_SPEC/CoL/the FAQ as
   to which card the new tokens land on. ASSUMPTION (ordered by the owner
   explicitly: "if you genuinely cannot determine it, pick the
   count-minimizing option, state the assumption prominently... and move
   on"): this engine places non-production gains on the highest available
   denomination, greedily -- the same representation `tokens_for`'s own
   affordability search already assumed. THIS ASSUMPTION IS THE PRIME
   SUSPECT for the 5 regressions below -- see "WHY IT DOES NOT LAND".
4. SPEND (paying corruption, builds, upgrades, wonder stages, trade,
   consumption) removes tokens LOWEST denomination first, "making change"
   (breaking exactly the one token that must be broken, re-representing the
   unspent remainder at smaller denominations) only when the low tokens
   alone fall short. Owner's words: "when you spend resources you can
   choose to spend from whatever farm you want (you usually want to spend
   from the lower ones). You can also make change when you spend."

Per-DENOMINATION counts, not per-card identity -- the owner confirmed cards
sharing a printed value are interchangeable for corruption purposes and nothing
in the rules caps tokens per card, so a `[u8; 8]`-shaped bank (mirroring
`economy::Denoms`'s own fixed-capacity shape) is sufficient state, no `Vec`,
no per-card tracking (`state.rs::TechSlot::stored` stays the pre-existing dead
field it already was -- checked, never written anywhere in the codebase except
one unrelated `Tableau` unit test -- and is NOT what this fix uses).

WHY IT DOES NOT LAND -- what was traced, and the strongest remaining lead
===========================================================================
All 5 regressions share the IDENTICAL shape: the game plays cleanly for many
rounds, then LATE in a long game (round 18-20, every one of them Age IV)
stops on an `IllegalMove` for a `Build`/`WonderStep` whose printed resource
cost the engine now believes the player cannot afford, when the human
journal shows them affording it fine. This is a resources SHORTFALL, not a
corruption-band edge case narrowly -- and it only ever shows up after a long
accumulation, which points at a small systematic per-turn effect compounding
over ~20 rounds rather than a single sharp logic bug.

Hand-traced 7523072 in full (round 10, the FIRST point its own resource
total diverges from the journal's implied true value -- 5 vs a manually
reconstructed true 4, tracked action-by-action against the journal text from
round 9's confirmed-correct end value). The proximate cause at round 10
itself is CONFOUNDED by a pre-existing, unrelated bug this pass did not
introduce and did not touch: `interact.rs`'s `ChoiceKind::Raid` handler
(line ~447-474, untouched by this patch) calls `economy::gain_resources`
ONCE PER DESTROYED CARD using that card's OWN halved-and-rounded cost
(`printed.div_ceil(2)`), not once for the printed card text's actual rule
("gain resources equal to half their TOTAL cost, rounded up") -- and in this
game's case, the SECOND of two same-turn Raid casualties silently no-ops
(`techs.get_mut(id)` fails because the same card was already destroyed once,
see the `if !ok { return; }` guard three lines into that match arm), so only
ONE of the two casualties' loot is ever credited. This pre-dates this patch
entirely (confirmed: the exact same code path is untouched, and this game
IS in the pristine 731-game baseline, i.e. it completes fine WITHOUT any of
this pass's changes) -- but the resulting scalar resource total, once wrong,
then interacts with the NEW, stricter corruption accounting (which correctly
refuses to let 5 old denom-1 resource tokens retroactively "become" denom-2
Iron tokens just because Iron was discovered later that same turn) to charge
2 corruption the journal's own text does not show at all. Whether the TRUE
corruption really was 0 there (meaning assumption #3 above -- "non-production
gains use the highest available denomination, greedily" -- or some other
part of the SPEND/change-making model is still wrong) or whether the TRUE
resource total the human had was different from both this engine's number
AND my manual reconstruction (because the Raid-loot bug's true effect is
itself unknown without fixing it first) could not be disentangled with the
budget remaining on this pass.

The other 4 regressions (7521459, 7522402, 7522796, 7523510) were NOT
traced to this same depth, but their identical late-game "Build/WonderStep
now unaffordable" shape strongly suggests the SAME systematic small
resource-accounting drift, not four unrelated causes -- worth checking
first, before assuming each needs its own investigation.
