2. FIX #1 (Upgrade bucket): Revolution never fires Leonardo da
   Vinci's / Albert Einstein's develop-triggered leader ability
=====================================================================

FILE: rust/src/apply.rs, fn h_revolution (Move::Revolution handler)

ROOT CAUSE:
h_revolution() hand-rolled ONLY Isaac Newton's leader trigger inline
(civil_actions += 1 on revolution) instead of calling the shared
on_develop() helper that h_develop()'s PEACEFUL government-change path
already calls unconditionally at the end of every develop (including
Government-kind cards, via set_government). on_develop() is the single
place that fires Leonardo da Vinci's "+1 resource" and Albert Einstein's
"+3 culture" triggers -- h_revolution() never called it, so a player
using violent Revolution (not peaceful Develop) to seize a government
never got Leonardo's or Einstein's bonus.

docs/RULES_SPEC.md line 232 confirms this is one mechanic: "Newton:
regain 1 CA after a revolution (revolution counts as developing a
technology)" -- the citation is about Newton specifically but the
underlying fact ("revolution counts as developing a technology") is
general, and on_develop() already treats all three leaders uniformly
for the peaceful path.

TRACE (game 7522665, round 11):
Journal line 164: "Orange revolutions Change government to Constitutional
Monarchy; 6 science points spent; Orange loses 6 science; Leonardo Da
Vinci gives 1 resource" -- Orange's leader is Leonardo da Vinci, and BGO's
own line explicitly names the leader trigger firing. Our engine silently
dropped it. This 1-resource deficit is PERMANENT and UNCORRECTED for the
rest of the game (there is no per-turn resource oracle correction the way
science/culture get REPLAY_DEBUG drift checks -- see "false starts"
below) -- confirmed by diffing every subsequent "(now N)" resource total
in the journal against our engine's own end_of_turn POST value: both
sequences matched EXACTLY for 10 consecutive end-of-turn checkpoints,
then diverged by exactly -1 starting at the revolution's own end-of-turn
line and stayed at -1 for every following checkpoint I checked. 7 rounds
later (line 218, round 14) the accumulated 1-resource deficit finally
starves an Upgrade: "Orange upgrades Religion to Organized Religion
Orange spends 4 resources" -- our engine had exactly 3 resources at that
point (upgrade_cost computed correctly as 4; the shortfall is entirely
upstream in the missing +1 from round 11).

FIX: replace the Newton-only inline block in h_revolution with a call to
the shared on_develop(state, idx), mirroring h_develop's own peaceful
path exactly (same computation for Newton, now ALSO firing for Leonardo/
Einstein).

3. FIX #2 (Take bucket): replayer trusted "whichever move is legal"
   over BGO's own "Ocean Liner Service used" text
=====================================================================

FILE: rust/src/replay_common.rs, fn apply_one, ActionClass::IncreasePopulation arm

ROOT CAUSE:
When BGO logs "<Color> increases population Ocean Liner Service used",
this is the wonder's once-per-turn FREE population increase
(Move::PopFree / h_pop_free, no CA spent). The dispatcher used to try
Move::Pop FIRST whenever it happened to be legal (spare CA + enough
food), only falling back to Move::PopFree if Pop was illegal. When BOTH
were simultaneously legal (a player who still had a spare civil action
AND their once-per-turn free Ocean Liners increase available), the code
silently chose the PAID Move::Pop even though the journal explicitly
says the FREE option was used. This overcharges p.civil_actions by 1 for
the rest of that turn.

TRACE (game 7523341, round 14):
Line 458-461: Orange takes Eiffel Tower (3 CA), upgrades Bronze to Coal
(1 CA -- via the Upgrade branch, non-unit), "Orange increases population
Ocean Liner Service used" (should be free), takes Urban Growth (1 CA).
Constitutional Monarchy's ca_total is 6; 3+1+1 = 5 real CA spent, leaving
1 spare -- but the buggy Pop dispatch consumed a 6th, phantom CA on the
"Ocean Liner Service used" line, so by the time "Orange takes Military
Theory in hand Orange uses 1 civil action" (line 462) is reached,
civil_actions=0 instead of 1 and the take is rejected (reason=Budget,
gate_have=0). Confirmed via REPLAY_DEBUG that the IDENTICAL text
"Orange increases population Ocean Liner Service used" correctly
resolved to Move::PopFree EARLIER in the SAME game (round 13, where
Move::Pop happened not to be legal) -- proving the dispatcher is
move-legality-order-dependent, not text-aware, which is the bug.

FIX: apply_one's IncreasePopulation arm now checks
raw_text.contains("Ocean Liner Service used") FIRST and takes
Move::PopFree whenever that's true and PopFree is legal, falling back to
the old "whichever is legal" logic only when the text does not name the
free source.

TEST: replay_common.rs,
a_pop_line_naming_ocean_liner_service_used_takes_the_free_move_even_when_a_paid_pop_is_also_legal

5. FALSE STARTS / DEAD ENDS
=====================================================================

- Initially suspected the Raiders event's FoodOrResSplit resolution
  (`spends_grants` FIFO matching in replay_common.rs ~line 1150-1200) was
  the source of game 7522665's resource shortfall, since that mechanism
  is genuinely subtle (a prior worker's own doc comments flag it as a
  repeat source of bugs). Traced it in full via REPLAY_DEBUG and
  REPLAY_DEBUG_ALL and confirmed it resolved CORRECTLY (matched the
  journal's own "Orange spends 2 resources" resolution exactly,
  7 -> 5). Not the bug -- just adjacent to it in the same turn.

- Considered that `costs::take_gate`'s `>=` comparison might be
  involved in the Take bucket bug -- per the task's own hard rule this
  was NOT touched, and in the end the Take bucket's root cause was
  entirely upstream (a CA phantom-charge from the Pop/PopFree dispatch
  bug), never reaching take_gate's own comparison logic at all.

- There is no per-turn RESOURCE drift oracle (REPLAY_DEBUG has one for
  science -- `trailing_now_science`/"DEBUG end-turn science drift" -- and
  a structural one for culture, but none for food or resources). Diagnosing
  fix #1 required manually cross-referencing the journal's own "(now N)"
  resource total against `grep "end_of_turn POST: idx=0"` from
  REPLAY_DEBUG_ALL output turn-by-turn to find exactly which end-of-turn
  the drift started at. A `trailing_now_resources` parser + drift
  eprintln (mirroring `trailing_now_science`) would make this class of
  bug much faster to localize next time; I did not add it since it's
  tooling, not a bug fix, and the task scoped me to landing fixes with
  tests, not diagnostics -- but it is a natural next addition for
  whoever picks up the remaining Upgrade games below.
