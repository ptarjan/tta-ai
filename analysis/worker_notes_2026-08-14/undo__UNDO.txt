PRECEDENT READ FIRST (commit 5ed0f20, same file, landed earlier the same day)
"Pair a PutBack with the take it actually refunds, not the latest one" --
fixed prescan_putback_skips's PutBack arm to match by refund amount instead
of blindly popping "most recent," because a multi-copy action card (count
other than [1,1,1], e.g. Frugality/Reserves at [2,2,2]) can have TWO open
takes for the same actor at once. That fix left the OTHER arm of the same
function untouched -- the one that pops an open take when the actor commits
the card some other way (Build/Play/Develop/Elect/...). This turned out to
have the exact same shape of bug.

THE BUCKET SPLIT (before any fix; 17 games, quoted journal lines)

GROUP A -- 12 games, the retain-all bug (FIXED)
  Reserves (count [2,2,2]/[2,2,2]/[3,3,3] by age): 7522613, 7523030,
    7521858, 7522189, 7522975, 7523164, 7522782, 7523147 (8 games)
  Frugality (count [2,2,2]): 7523397, 7522301 (2 games)
  Engineering Genius (count [1,2,2]... multi-copy in later ages): 7521158
  Revolutionary Idea (multi-copy): 7521855

  Shared symptom: actor has TWO open takes of the same-named multi-copy
  card (one carried over from an earlier turn, one just taken this turn),
  then a Play/Build/etc. line commits ONE of them. prescan_putback_skips's
  non-PutBack arm did:
      stack.retain(|&(_, a, _)| a != actor);
  which drops EVERY open entry for that actor on that card, not just the
  one the commit line actually resolved. With both entries wiped, the
  later legitimate PutBack finds an EMPTY stack -> "unpaired," not merely
  a wrong pairing (which is what the precedent's PutBack-side bug produced;
  this one is strictly worse because it discards the evidence outright).

  Representative quote, game 7522613 (rust/src/replay_common.rs's new test
  mirrors this exactly):
    line 177 (round 6): Green takes Reserves in hand Green uses 2 civil action
    line 216 (round 7): Green takes Reserves in hand Green uses 1 civil action
    line 217 (round 7): Green plays Reserves Green produces 2 resources
    line 219 (round 7): Green puts Reserves back in the row Green gets 1 civil action
  The refund (1 CA) is direct evidence the round-7 take (also 1 CA) is what
  got put back, so the "plays" line at 217 must have consumed the round-6
  take (2 CA) instead. retain-all wiped both, so line 219 found nothing.

  FIX (rust/src/replay_common.rs, prescan_putback_skips, the non-PutBack
  match arm): pop only the OLDEST open entry for that actor (FIFO -- the
  first pushed, since TakeCard pushes are already in chronological order),
  not every entry:
      if let Some(pos) = stack.iter().position(|&(_, a, _)| a == actor) {
          stack.remove(pos);
      }
  This is a no-op change for the overwhelmingly common single-open-entry
  case (removing the one entry either way), and for tied-cost pairs (where
  it doesn't matter mechanically which of two equal-cost takes is "the one"
  committed) -- it only changes behaviour when costs differ, which is
  exactly the case that was broken. FIFO order was picked because it is the
  only choice consistent with the observed refund evidence in 7522613 (LIFO
  would have left the wrong-cost entry open and either mis-paired the
  putback via the existing cost-match/fallback logic, or still failed to
  pair it).

  Two tests added (both inside `#[cfg(test)] mod tests` in
  rust/src/replay_common.rs, confirmed RED by reverting the fix and
  re-running):
    prescan_putback_skips_lets_a_commit_consume_only_the_oldest_open_take_not_every_open_take
      -- reproduces game 7522613's exact 4 lines; asserts the round-7 take
      and the putback pair, and the round-6 take stays a real applied move.
    prescan_putback_skips_still_drops_a_lone_take_on_commit
      -- confirms the single-open-entry case still degrades to "nothing
      left to pair," i.e. no regression on the common case.

A CROSS-AGE RESOLUTION ISSUE FOUND BUT NOT FIXED (out of scope, flagged for
whoever picks this up next)
  While tracing Group A, two of the eight Reserves games (7522975 line 249,
  7523147 line 477) turned out to complete successfully after the FIFO fix
  even though my manual trace flagged a possible SECOND issue: the "plays
  Reserves ... produces N resources/food" line's printed N sometimes matches
  a DIFFERENT age's table amount than the game's current age at that line
  (Reserves (I)/(II)/(III) print GainFoodOrResources 2/3/4 respectively --
  e.g. 7522975 line 247 is "III 14" context but prints "produces 3
  resources," which is Reserves (II)'s amount, not (III)'s 4). This suggests
  classify()'s bare-name-to-CardId resolution uses the CURRENT game age
  (Line.age) rather than tracking which specific age-variant copy is
  actually in the actor's hand, which could misattribute a play/putback to
  the wrong CardId when a card taken in one age is used after the age
  advances. In practice this did NOT block completion for either game (both
  are in the WINS list below), so I did not chase or fix it -- flagging only
  because the FIFO fix's correctness for these two games might be
  coincidental (equal-refund/no-conflict luck) rather than because the
  cross-age concern is actually a non-issue. Left alone; not in scope for
  this bucket's mandate (it would be a different, likely much larger,
  card_index/classify change).
