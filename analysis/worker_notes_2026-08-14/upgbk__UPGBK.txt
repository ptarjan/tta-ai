     journal's "Sacrificed Units:" clause names a bonus card only generically

     `Replayer::drain_colonize` falls back to `approximate_colonize`, which
     greedily takes whatever `legal_moves` offers first -- including

     narrower, colonize-specific gap in an area (`replay_common.rs`'s
     colonize machinery) with documented regression history
     (`colofix__COLOFIX.txt`, landed cleanly earlier today) and is not
     re-attempted here given the risk/reward and the remaining budget.

  C. A separate CULTURE-tracking drift (not resources), which explains the
     "closely related" score-divergence signal named in the brief -- see
     section 4. Already partially root-caused and fixed at an earlier base
     by a THIRD specialist worker today (`culturedrift`, a Michelangelo/
     Kremlin unhappy-face-cancels-happy-face bug) -- that fix IS present in
     our base commit already, and is confirmed NOT the cause of either
     score-divergence example game (neither actor has Michelangelo). The
     residual culture drift these two example games show is a different,
     still-unexplained instance of the same class of bug.

ANSWER to "are illegal-move Upgrade and the UpgradeProduction/UpgradeUnit

not because anything in Upgrade's own cost/legality/application code is wrong.

5. THE SCORE-DIVERGENCE SIGNAL (UpgradeProduction/UpgradeUnit, mechanism C)
===========================================================================
Checked whether the "4 games diverge right after UpgradeProduction" / "3
after UpgradeUnit" signal is the SAME bug as the illegal-move bucket.

First: `COLONIZE_FALLBACK_DUMP=1` on the two named examples (7522703,
7523159) fires ZERO times in both -- mechanism B is not involved.

Second, and more importantly: "journal says (now 111), this binary computes
106" (7522703) and "(now 128)/(now 129)" (7523159) are `end-turn CULTURE
drift` lines, not resources -- confirmed by re-running with `REPLAY_DEBUG=1`
and reading the actual debug tag (`DEBUG end-turn culture drift: ...`). The
task brief's framing ("an upgrade priced wrong would produce both") does not
hold: these are culture-production mismatches, and `costs::upgrade_cost`
only ever touches `p.resources`. Confirmed the cited journal line numbers
(327 for 7522703, 367 for 7523159) are each the End-Turn line immediately
AFTER the named upgrade, not the upgrade's own line -- the divergence is
first VISIBLE there because that is where the oracle checkpoints, not
because the upgrade caused it.

Checked whether this is the already-known Michelangelo/Kremlin
`CulturePerHappyFromTemplesTheatersWonders` bug `culturedrift__CULTUREDRIFT.txt`
found and fixed at an earlier base (13019ca): the fix
(`happy += w.get().effects.happy.max(0) as i32;`, `effects.rs:1119`) IS
already present in our base 9860400. Neither drifting actor has Michelangelo
in play in either example game (7522703 Purple's leader is Leonardo Da
Vinci; 7523159 Purple never elects Michelangelo -- only Orange does, and
Orange is not the drifting actor). So this is a DIFFERENT, still-open
instance of culture drift, not this already-fixed one.

CONCLUSION: the illegal-move bucket (mechanism A, resource/population drift)
and the score-divergence signal (mechanism C, culture drift) are TWO
DIFFERENT pre-existing bugs, neither one caused by Upgrade pricing, and they
are not "one bug" in any sense stronger than "both are engine-wide production
drifts that happen to surface at Upgrade-adjacent checkpoints because
Upgrades are common actions." Fixing Upgrade code cannot fix either.
