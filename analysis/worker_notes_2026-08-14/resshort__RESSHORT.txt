HAND-TRACE 1: game 7523124, "Purple builds Cannon Purple spends 5 resources", line
357, round 18 -- CORRUPTION vs BLUE-TOKEN CAPACITY, dead end
===========================================================================

`REPLAY_DEBUG=1 REPLAY_DEBUG_ALL=1 replay ... 7523124` -> engine fails with
`resources=4 < cost 5` for Cannon at round 18. Legal_moves at the failure includes
`Build{Knights}`/`Build{Swordsmen}`/`Build{Warriors}` -- confirms the resource-
shortfall shape (other, cheaper builds remain legal).

Checkpoint: journal's round-17 "End turn" line (326) reads "11 resources (now 17)".
The engine's OWN `REPLAY_DEBUG`-gated drift check (`end-turn resources drift`) fires
HERE for the first and only time in this game: "journal says (now 17), this binary
computes 15 (delta -2)". Every EARLIER end-turn checkpoint in this game matched
exactly (no drift line before this one) -- the -2 gap opens during THIS turn's own
production, not earlier.

Traced `economy::end_of_turn`'s internal `pre-corruption`/`blue_used` debug lines
(temporarily run with `REPLAY_DEBUG_ALL=1`, not committed) for Purple (idx=1) at this
exact checkpoint:
  resources=6 food=1 blue_total=16 blue_used=7 corr=2 s.resources=11 s.food=6
`blue_used=7` = `food_tokens(1,[5,1])=1` + `mine_tokens(6,[1])=6` (Purple's ONLY mine
tech the entire game is Bronze, denom 1 -- confirmed via `REPLAY_DEBUG_TECHS=1` at
every checkpoint, never upgraded). `blue_available = 16-7 = 9`, landing in
`RULES_SPEC.md` §6.2's `10-6 -> corruption 2` band. Paying that 2 from resources
(6->4) is EXACTLY the -2 delta: with corr=0 the turn would net to 6+11=17, matching
the journal precisely.

BUT the journal's line 326 has NO "CORRUPTION!" marker -- and this same journal DOES
print that marker verbatim elsewhere ("CORRUPTION! Orange loses 2 resources", line
247, round 14), which THIS ENGINE reproduces exactly at the matching checkpoint
(idx=0, blue_used=6, blue_available=10, corr=2 -- same band, confirmed by trace).
So the corruption MECHANISM is validated correct on a real in-game example, in the
SAME game, yet still disagrees for Purple round 17.

Exhaustively ruled out as the cause of the -2 (each independently confirmed against
the trace, `card_table.rs`, or `docs/RULES_SPEC.md` before moving to the next):
  - `blue_total=16` is correct: Purple gained +1 blue/+1 yellow from colonizing
    "Developed Territory (I)" (round 9, `blue_tokens:1` in `card_table.rs`) and lost
    it back exactly when "Independence Declaration" stripped that colony (round 12,
    `Special::WeakestPlayer` -- Purple WAS the weakest that round, this part is
    right) -- the 16->17->16 fluctuation in the trace is this pair, not a bug.
  - Purple's denominations (`Denoms::of`) are forced: Bronze (mine, denom 1) is their
    ONLY mine card ever; Agriculture(1)+Mechanized Agriculture(5) legitimately
    coexist as TWO separate farm cards mid-upgrade (upgrade moves ONE worker per CoL
    p.5's "Upgrade a Farm/Mine" action -- Agriculture had 2 workers, only 1 moved
    this turn, matching the SAME upgrade repeating next turn in the journal, line
    355).
  - No leader/wonder/government Purple has (Michelangelo -> Napoleon Bonaparte ->
    Bill Gates leaders; Library of Alexandria + St. Peter's Basilica wonders) prints
    `blue_tokens` in `card_table.rs`.
  - `economy::corruption`'s own band table matches `RULES_SPEC.md` §6.2's printed
    table exactly, cross-checked against the CoL rulebook screenshot text directly
    (`sources/cge_code_of_laws.pdf`, p.6: "the leftmost square in each section...
    if all these numbers are covered by blue tokens, you have no corruption").
  - Ruled out re-opening the CLOSED production-cap theory (per task instructions):
    the -2 gap is fully explained by `corr` alone WITHOUT touching
    `gain_resources`/`gain_food`'s capacity math -- but further tracing (see next
    paragraph) shows the two are NOT actually separable in this engine's model.

Why this was NOT shipped as a fix: recomputing "what if corr=0" is NOT simply
"+2 to the final total" -- blue token CAPACITY (`blue_available`) is shared between
what corruption charges and what THIS SAME TURN'S production/`gain_resources` can
still store. Recomputing the whole turn with corr forced to 0 by hand (pre-corruption
resources stay 6 instead of dropping to 4) actually reproduces 15 again, NOT 17 --
because keeping more resources stored leaves LESS capacity for the subsequent
Bill-Gates-sourced `gain_resources` bonus (`Special::ResourcesPerLabEqualToLevel`,
routed as a general CoL p.11 "gain" through the SAME blue-token pool `corruption`
reads). This entangles any "corruption shouldn't have fired" fix with exactly the
capacity-limited `gain_resources`/`gain_food` machinery the task explicitly marks
CLOSED (fixed at 613ff6c, "do not re-open... for a production-cap theory"). Given
that entanglement, and that this mechanism validates correctly elsewhere in the SAME
game, no fix was attempted here -- shipping one blind would risk exactly the
"manufactured win" the task forbids.

line 206, round 9 -- EVENT "strongest civilization" targeting, TWO THEORIES BOTH

===========================================================================

`REPLAY_DEBUG=1 REPLAY_DEBUG_ALL=1 replay ... 7522914` -> engine fails: Purple has
`resources=6` at the Journalism build (cost 8), `workers_free=2` and other, cheaper
`Build{...}` moves ARE legal (confirms the shape). Journal math: round-8 end-turn
checkpoint reads "3 resources (now 6)" (validated exact, no drift). Round 9's only
resource-relevant line before the build is line 202: "Purple plays event... Border
Conflict; The weakest civilization must destroy...; The strongest civilization gains
3 resources.; Purple produces 3 resources; Orange must destroy a mine, farm or
urban building" -- i.e. the journal explicitly names PURPLE as "strongest" and grants
Purple +3 (6->9, comfortably covering the cost-8 Journalism build).

The engine's own trace of this exact event resolution (`events::apply_single_target`,
`RankStat::Strength`, `Special::StrongestPlayer`/`Special::WeakestPlayer` from
`card_table.rs`'s "Border Conflict" entry):
  apply_single_target: order=[1, 2, 0] stat=Strength best=true ranked=[2, 1, 0]
    values=[7, 9, 7]     (Purple=7, Green=9, Orange=7)
  apply_gains_block: idx=2 (GREEN) ... resources_before=4 -> Green gets the +3, not
    Purple.
  apply_single_target: ... stat=Strength best=false ranked=[0, 1, 2] values=[7,9,7]
    -> Orange picked weakest, MATCHES the journal ("Orange destroys Bronze").

So only the STRONGEST half disagrees with the journal; WEAKEST is right. This is the
SAME general class of bug `analysis/worker_notes_2026-08-14/build2__BUILD2.txt`
flagged as an unresolved lead from a DIFFERENT game (7523082, `WeakestPlayer`/"Reign
of Terror") -- there, the engine's live combat-strength computation (tactic army
bonus via Genghis Khan + a leader's temple/happy bonus) picked a different "weakest"
player than the journal. Two independent games, two different specific mechanisms,
same general symptom: `events::rank_stat_value`'s `RankStat::Strength` arm
(`effects::state_stats(state, p).strength`, the FULL combat-strength number including
army/tactic bonus and every flat leader/wonder/special-tech `effects.strength` grant)
disagrees with whatever BGO's own client uses for "strongest/weakest civilization"
event comparisons.

THEORY A (tested, FALSIFIED): "strength rating" for event-targeting purposes should
be RAW UNIT STRENGTH ONLY (workers on Infantry/Cavalry/Artillery/Air tech cards times
that card's own `effects.strength`), excluding both the current tactic's army-
formation bonus (`effects::army_strength`) AND flat non-unit `effects.strength`
grants (wonders like Colossus [Green completed it round 4, `blue_tokens`-style flat
`strength:2` in `card_table.rs`], leaders, special techs). Motivated by
`RULES_SPEC.md` §11.3's own list of "strength-rating modifiers" EXCLUDED from
colonization force (Alexander, Napoleon, Great Wall, Warfare, wonders, leaders,
special techs) -- reasoned this same exclusion list might belong on the event-
targeting stat too, even though §11.3's own wording implies these ARE normally part
of the general "strength rating" (a direct tension with the two corpus games above).

IMPLEMENTED as a new `effects::raw_unit_strength(p)` function, wired into
`events::rank_stat_value`'s `RankStat::Strength` arm ONLY (scoped: does not touch
`state_stats`/`compute`, used at 83 other call sites per that function's own doc
comment, so combat/colonization/production are untouched). Rebuilt, re-ran game
7522914 under the same trace:
  apply_single_target: order=[1, 2, 0] stat=Strength best=true ranked=[0, 1, 2]
    values=[3, 2, 4]     (Purple=3, Green=2, ORANGE=4)
Orange is now ranked strongest -- NOT Purple, NOT a tie. The theory predicted a
3-way tie at 7 (broken toward Purple, the revealer); the actual raw-unit numbers
are NOT equal at all (Purple=3, Green=2, Orange=4), so Theory A is falsified by
direct measurement, not merely unconfirmed. `apply_gains_block: idx=0` (Orange)
confirms the wrong player still gets the resources, just a DIFFERENT wrong player
than before. REVERTED immediately (`git checkout -- rust/src/effects.rs
rust/src/events.rs`), confirmed clean by `git diff --stat` empty. Did not run the
full guard on this candidate since it does not even fix its own target case --
running the corpus-wide guard on a fix already known to be wrong would only
consume budget without adding information.

THEORY B (considered, not implemented): raw units + `army_strength` (tactic bonus)
INCLUDED, only flat non-unit `effects.strength` (wonder/leader/special-tech)
excluded. Ruled out by the SAME raw-value evidence before implementing: Orange
already leads on raw units alone (4 vs Purple's 3) with no tactic bonus added yet
(Orange's own tactic, Phalanx, would only WIDEN the gap if it forms an army, never
narrow it) -- adding any army bonus cannot flip a 4-vs-3 gap in Purple's favor, so
this candidate cannot reproduce "Purple strongest" either. Not implemented; not
guessed into the tree.

Net conclusion on the strength-ranking lead: the full `state_stats(...).strength`
computation (Purple=7, Green=9, Orange=7 -- Green wins) is WRONG per the journal
(Purple should win), but "strip the bonuses back to raw units" is ALSO wrong (Orange
wins instead). Something in between, or something entirely different from a
modifier-subtraction theory, must be the real rule -- e.g. BGO's client may use a
narrower "military strength" concept this codebase does not have a name for yet, or
the true bug is not in `RankStat::Strength` at all and both games are coincidental.
Two clean, falsifiable subtraction theories are now closed off for the next worker;
