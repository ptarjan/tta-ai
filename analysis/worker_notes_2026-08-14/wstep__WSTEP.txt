STEP 2: hand-trace 3 games against RULES_SPEC / CoL / FAQ
============================================================

Game 7521364, line 23: "Orange builds 1 stage of Colossus Orange spends 3
resources" (round 2, single stage, NOT a multi-stage-cap case).
REPLAY_DEBUG=1 ./target/difftest/replay ... 7521364 shows:
  DEBUG cost detail: wonder_stage_cost(steps=1)=3 wonder=Colossus wonder_steps=0
  resources=2 (in the try_apply-fail dump)
So the engine's own cost formula (3) is right; the reconstruction's own
resources (2) are one short. Looking at the raw journal one line earlier:
  line 22: "GAME DATA UPDATED Orange Bronze: 2 -> 6"
This is BGO's own admin-correction line shape (already handled for
`culture` -- see `parse_game_data_updated_culture`'s doc, added in an
earlier pass for game 7523809). `corpus::classify` files EVERY
"GAME DATA UPDATED" line as Bookkeeping regardless of which stat it names,
so this "Bronze: 2 -> 6" correction was silently dropped -- the
reconstruction's own resources stayed at 2 forever, one short of the
WonderStep's cost of 3.

"Bronze" is BGO's own internal label for the player's RESOURCE stockpile,
not a reference to the Bronze tech card: confirmed by scanning every
"GAME DATA UPDATED" line in the full 1,011-game corpus
(`grep -h "GAME DATA UPDATED" journals/*.tsv | sed ... | sort -u`) --
every "Bronze: X -> Y" clause has the exact same shape as the "science:
X -> Y" and "culture: X -> Y" clauses on the same or sibling lines (e.g.
"GAME DATA UPDATED Green science: 2 -> 5; Green Bronze: 0 -> 2"), and the
values move independently of whether that player has built/upgraded an
actual Bronze mine card that game.

Game 7523085, line 245: "Green builds 2 stages of Great Wall Green spends
5 resources; ; Wonder completed" (round 8, a real multi-stage build, but
NOT limited by the stage cap -- wonder_stage_cost(steps=2)=5, matching the
journal exactly). REPLAY_DEBUG shows resources=0 at the point of failure.
Five lines earlier:
  line 240: "GAME DATA UPDATED Green Bronze: 4 -> 9"
old=4 does not match the reconstruction's own resources (0) AT THAT EXACT
LINE (this is why the fix defers rather than force-applies -- same
self-deferring shape already established for culture corrections), but by

(matches "old"), so the deferred correction (+5) applies and covers the
5-resource cost exactly.

Third trace (7521689, "builds 4 stages of First Space Flight ... spends 16

============================================================
RULED OUT / LEFT OPEN (honest negative, not "seems like drift")
============================================================

The remaining 21 games in the bucket do NOT share the GAME DATA
UPDATED/Bronze mechanism (none of them carry a "GAME DATA UPDATED ...
Bronze:" line in their journal at all -- checked by grep across all 21).

Hand-traced one of them in full (7521689, Orange, round 16-17, leader Bill
Gates, "builds 4 stages of First Space Flight ... spends 16 resources"):
using the existing (already-instrumented) REPLAY_DEBUG_ALL=1
REPLAY_DEBUG_TECHS=1 output, the reconstruction's own resources fall
short of the journal's own "(now M)" running total starting at the round-16
End Turn (delta -4), growing to -8 by round 17's End Turn -- BEFORE the
WonderStep line is ever reached, i.e. this is a downstream symptom of an
earlier economy divergence, not a WonderStep-specific bug (same shape the
existing code comments already warn about for this whole bucket family).

Traced the exact mechanism: `economy::gain_resources`/`gain_food`
(economy.rs) cap production by `blue_available(p)`, computed via
`tokens_for(value, denoms)` -- a DENOMINATION/VALUE-based token count
(minimum tokens to represent a given total value, "making change"). This
is the CORRECT model for the general "gain food or resources" rule from
card effects (CoL p.11: "move one or more blue tokens... resulting total
must be exactly the amount... if not enough tokens, gain the nearest lower
achievable value"). But CoL p.6's End-of-Turn "Resource Production" step
is worded differently: "For each WORKER on your mine technology cards,
move ONE blue token from the blue bank to that card... if not enough
tokens, move all you can, beginning with those of the highest level." That
is a WORKER-COUNT-based token cost (one token per producing worker,
regardless of that worker's own per-level value), not a VALUE-based token
cost. For a player whose only resource-track cards are all denomination-1
(e.g. un-upgraded Bronze) the two models coincide, but for
`Special::ResourcesPerLabEqualToLevel` (Bill Gates: "each of your labs
ALSO produces resources equal to its level") a single worker on a level-3
lab contributes 3 to `s.resources` under today's model at a cost of 3
value-based tokens, when the CoL-p.6-worded rule (if it even applies to a
leader-ability bonus stacked onto a lab at all, which is itself unverified
-- Bill Gates' bonus is not literally "a mine technology card") would cost
at most 1.

Traced the arithmetic through by hand (pre-corruption resources=7,
corr=2 -- matches the journal's own "CORRUPTION! Orange loses 2
resources" exactly, ruling out the corruption FORMULA itself) and even a
fully-uncapped model (7 - 2 + 10 = 15) still falls 2 short of the
journal's own final total of 17, so simply removing the cap is not a
complete fix either -- there is a second, unidentified discrepancy beyond
the token-cost model. This is the SAME "blue_total/blue_used, not the
corruption formula" lead a PRIOR pass already flagged and explicitly left
open (docs/REPLAY.md, "Seventeenth pass" section, game 7522625,
"NOT yet checked: whether blue_total's starting value of 16 is even the
right constant per player count, and whether some OTHER effect should be
adding to it by this point... ran low on context before finishing this
trace").

NOT attempted in this pass: rewriting `economy::end_of_turn`'s resource/
food production to be worker-count-based (rather than value-based) for
the plain mine/farm case, and/or exempting non-mine/farm production
sources (Bill Gates, DoubleBestMine, SciencePerBestLabOrLibraryLevel-style
bonuses) from the blue-bank cap entirely. Both are plausible partial fixes
by the CoL p.6 text quoted above, but:
  (a) this touches the CORE production loop every single game runs through
      every single turn (`economy::end_of_turn`), so a wrong or partial
      fix risks corpus-wide regressions, not just missing a further win;
  (b) my own hand-trace above did NOT fully reconcile the numbers even
      after the most obvious partial fix (uncapping non-mine/farm bonus
      production) -- a second, still-unidentified gap remains;
  (c) this is NOT a WonderStep-specific mechanism -- it is a general
      economy/corruption discrepancy that would resurface across many
      IllegalMove buckets (Build/Upgrade/Develop, per the existing
      "Build/Upgrade/WonderStep 'resources short by 1-2' cluster" comments
      already in apply.rs and corpus.rs), so it deserves its own dedicated
      pass with a full budget, not a bolt-on inside this one.
