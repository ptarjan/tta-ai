THE REAL DISCRIMINATOR: AGE TRANSITION BETWEEN DECLARE AND RESOLVE
---------------------------------------------------------------------
Checked declare-age vs resolve-age (journal's own `Line::age` column) for
every war above:

  7523045      declare III -> resolve IV   (broken: needs Napoleon excluded)
  7522509      declare III -> resolve IV   (broken)
  7523473      declare III -> resolve IV   (broken)
  7523127      declare III -> resolve IV   (broken)
  7522590 war1 declare III -> resolve III  (CORRECT: Napoleon included)
  7522590 war2 declare III -> resolve IV   (broken)
  7521763 war1 declare III -> resolve III  (CORRECT, spot-checked)
  7521459 war1 declare III -> resolve III  (CORRECT, spot-checked)
  7521459 war2 declare III -> resolve III  (CORRECT, spot-checked)

7/7 clean split: every war that resolves in a DIFFERENT age than it was
declared in is broken; every war that resolves in the SAME age is correct.
Napoleon Bonaparte is an Age II leader (card_table.rs ~1822,
`age: Age::II`). `game::antiquate` (game.rs:597-630) discards a player's
leader when `leader.get().age as u8 < ended as u8` where `ended` is the
age that just finished -- i.e. an Age II leader is legitimately discarded
the moment Age III ends (transitioning III->IV), matching CoL §12.2 (only
technologies/wonders/colonies/tactics/declared-wars survive antiquation;
leaders and pacts do not). So in the 5 broken games, Napoleon Bonaparte
really was gone from Purple's/Orange's civilization by the time their War
over Culture resolved in Age IV -- BGA's own "Attacker's strength" number
correctly has NO Napoleon bonus. `game::start_turn`'s own doc comment
(game.rs:772-773) already anticipates exactly this: "Replenishing first
matters -- it is what can end an age, and an age change can antiquate a
card out of the very tableau the war is about to be scored against."

CONFIRMED DIRECTLY: added a temporary eprintln! of `state.age_civil` at
the top of `combat::resolve_war_outcome` (reverted) and re-ran game
7523045: at the exact instant `resolve_war_outcome` computes the
attacker's strength, `state.age_civil == III`, even though the journal
tags that same resolution line "IV 17". So THIS REPLAYER's reconstructed
age genuinely lags the real BGA game's age at the moment the war
resolves -- `antiquate` never got a chance to discard Napoleon before
`state_stats` read his still-present leader special.

WHY: `combat::resolve_war_outcome` fires SYNCHRONOUSLY inside
`game::advance_turn` -> `game::start_turn`, itself triggered as a side
effect of applying the DEFENDER's own last "End turn" journal line for
the OLD age (via the normal `Move::EndTurn` dispatch, not journal-driven).
`game::replenish`'s own natural, deck-empty-triggered `advance_age` is
what SHOULD flip `state.age_civil` to IV before `resolve_war_outcome`
runs, exactly like the real BGA deck did -- but this reconstruction's own
`civil_deck` is well-documented (module doc on
`game::force_civil_age_at_least`, `replay_common.rs`'s
`catch_up_civil_age`) to lag the true deck's depletion by up to several
turns, because civil ROW slots are grounded card-by-card from observed
"takes ... in hand" lines rather than drawn through `civil_deck`
sequentially. The corrective mechanism, `replay_common::catch_up_civil_age`
(called once per journal line, forcing `state.age_civil` UP TO that
line's own stated age) is DELIBERATELY gated off "WinWar" confirmation
lines -- see `is_trustworthy_age_line`/`is_pure_confirmation_line` and the
existing test
`is_trustworthy_age_line_call_site_gate_ignores_a_winwar_confirmation_but_still_advances_on_the_next_real_decision`
(replay_common.rs ~8728), which explicitly asserts "a WinWar confirmation
line must not force the age" (to avoid double-firing CoL §12.2.4's
"-2 yellow_bank" deduction off an untrustworthy line -- a DIFFERENT,
already-fixed bug this same machinery guards against). So by the time the
loop reaches the WinWar line and would normally catch the age up, the war
has ALREADY resolved (synchronously, one line earlier) using the stale
age -- and the catch-up that finally happens on the FOLLOWING real
decision line is too late to matter for this war.

WHY NO FIX LANDED
--------------------
The true fix needs the reconstruction's `state.age_civil` to be correct
BEFORE the synchronous `advance_turn` cascade that resolves a pending war,
specifically when that cascade is itself triggered by processing an
EARLIER (still-old-age-tagged) journal line -- i.e. it needs work at or
before the defender's own preceding "End turn" line, not at the WinWar
line itself. `replay_common.rs`'s age-catchup logic is dense, already
carries a long history of narrowly-scoped fixes for adjacent symptoms
(HandFull, IllegalMove:Pop, food-consumption-off-by-one at age boundaries,
premature §12.2.4 deductions -- see the module's own doc comments and the
~10 existing tests pinning `catch_up_civil_age`'s exact gating), and a
naive "also catch up before resolving a pending war" change risks
reintroducing the yellow_bank-double-deduction bug the WinWar exclusion
test guards against, or the mid-turn-consumption bug the
`pending`/`queue`-emptiness guard exists for. Getting this right needs
either (a) a way to catch up `state.age_civil` for ANTIQUATION purposes
specifically (leader/wonder discard) without re-running the §12.2.4
yellow-bank deduction a second time, decoupling the two effects
`advance_age` currently bundles, or (b) forcing the age-catchup to happen
one line earlier than it currently does specifically when the NEXT line
is a WinWar confirmation tagged a later age than the current line. Both
are real, scoped, plausible fixes -- but each touches exactly the
kind of extremely delicate, thoroughly-tested sequencing code the task
brief warns against destabilizing without full corpus validation, and I
did not have the remaining budget to implement + prove either one safe
across all 687 completed games (only 5 of which are even affected by this
exact symptom; a wrong version could easily cost more elsewhere via the
yellow-bank or consumption-timing regressions the existing tests guard
against). Per the task's own allowance ("A measured negative is
acceptable. Do not manufacture a fix on well-tested combat code"), I am
reporting this as a confirmed-but-unfixed root cause rather than risking a
speculative patch to `replay_common.rs`.
