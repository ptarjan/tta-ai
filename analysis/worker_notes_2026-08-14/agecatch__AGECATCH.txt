THE FIX
-------
Per the diagnosing worker's own suggested shape: decouple ANTIQUATION
(leader/wonder/pact discard) from the rest of what an age transition does
(§12.2.4's "-2 yellow_bank" deduction, civil_deck rebuild, `age_civil`
itself), and let the replayer run JUST the antiquation half early, at
exactly the moment it detects the synchronous cascade is about to use a
stale age -- while leaving everything else on the EXACT same deferred
schedule the ~10 existing `catch_up_civil_age`/`is_trustworthy_age_line`
tests already pin.

1. `rust/src/game.rs`: split `antiquate(state, ended)` into two private
   halves -- `antiquate_hands` (unchanged, still called by `antiquate`) and
   `antiquate_leader_wonder_and_pacts` (also still called by `antiquate`,
   same order as before, so `antiquate`'s own external behaviour, and every
   existing test of it via `advance_age`/`force_civil_age_at_least`, is
   byte-for-byte unchanged). Hands were deliberately kept OUT of the new
   early-antiquation path: they are what the discard-phase hand-size
   machinery (`interact::discard_options`, `prescan_discard_phase_oracle`,
   `apply_one`'s `Discard` arm -- explicitly off-limits, a different worker
   owns that path right now) reasons about, and running their antiquation
   ahead of the deferred, fully-timed `advance_age` call risked shifting a
   discard-phase decision that split has no business touching. Leader/
   wonder/pacts have no such entanglement -- `on_leave_play`'s token
   bookkeeping is the only side effect, and it is idempotent the same way
   the rest of `antiquate` already is (a card already gone when the LATER,
   deferred, full `antiquate` call reaches the same `(state, ended)` pair is
   simply not found, so that call is a no-op for it).

   Added `pub(crate) fn antiquate_leader_wonder_pacts_up_to(state, target)`:
   loops `antiquate_leader_wonder_and_pacts(state, ended)` for every age
   from `state.age_civil` up to (not including) `target`, WITHOUT ever
   bumping `state.age_civil`, touching `civil_deck`, or running the §12.2.4
   deduction.

2. `rust/src/replay_common.rs`: added `upcoming_confirmed_winwar_age(journal,
   i, card_index)` -- scans forward from line `i`, skipping ONLY
   `is_end_of_turn_bridge_line` lines (`Bookkeeping`, or `EndTurn`/`Discard`
   action classes -- exactly the untrusted-for-catchup classes
   `is_trustworthy_age_line` already excludes, minus `WinWar` itself, which
   is what this function is looking FOR), and returns the first `WinWar`
   line's own age if one is found before any real decision line. Wired into
   `replay_game`'s main loop right after the existing
   `is_trustworthy_age_line`-gated `catch_up_civil_age` call: when
   `upcoming_confirmed_winwar_age` returns `Some(age)`,
   `game::antiquate_leader_wonder_pacts_up_to(&mut r.state, age)` runs
   immediately, before this line's own `try_apply` (and therefore before
   whatever synchronous cascade that `try_apply` might trigger).

THE DISCRIMINATOR I HAD TO WIDEN (this is the part worth reading closely)
--------------------------------------------------------------------------
My first version of `upcoming_confirmed_winwar_age` mirrored
`is_trustworthy_age_line`'s own WinWar-exclusion reasoning defensively: it
additionally required the line AFTER the `WinWar` confirmation to not be
tagged an OLDER age, matching the exact shape documented as unsafe on real
game `7523079` (a `WinWar` line's timestamp collides with, and exports one
line before, a DIFFERENT player's own still-old-age `End turn` trailer;
trusting it there ran the cross-player §12.2.4 deduction a turn early).

That extra check made the isolated cluster-game check pass for only 3 of the
5 diagnosed games (7522509, 7523473, 7522590) -- 7523045 and 7523127 stayed
broken. Traced why: both have the IDENTICAL "older age immediately after
WinWar" shape as `7523079` (confirmed by reading the raw journal -- game
`7523045` line 335 `"Purple wins War over Culture"` tagged IV is immediately
followed by line 336, Orange's own still-Age-III `EndTurn`/discard trailer,
all three lines sharing one timestamp, `01:29:32`), yet they are GENUINE
transitions, not collisions -- the previous worker's own instrumentation
already proved this shape's `WinWar` age tag is real ground truth.

The two shapes are NOT mechanically distinguishable by "what tag trails the
WinWar line" alone -- what differs is what the TRUSTING code then DOES.
`is_trustworthy_age_line`'s caller (the untouched, pre-existing
`catch_up_civil_age` call) forces `state.age_civil` itself, `civil_deck`'s
rebuild, AND §12.2.4's CROSS-PLAYER "-2 yellow_bank" deduction -- real,
shared, wide-blast-radius state a same-timestamp tie can genuinely corrupt
for an unrelated bystander (`7523079`'s Purple). My new function's only
caller, by contrast, calls ONLY `antiquate_leader_wonder_pacts_up_to`, which
touches ONLY the specific player who owns the too-old leader/wonder/pact
being removed -- no `age_civil`, no `civil_deck`, no cross-player
`yellow_bank` deduction. There is no shared state left for the tie to
corrupt. So I dropped the "no regression after WinWar" check entirely (see
`upcoming_confirmed_winwar_age`'s own doc in replay_common.rs for the full
argument, cross-referencing both real games). After dropping it, all 5
cluster games matched exactly, and the FULL 687-game guard sweep still
showed zero regressions (see bar below) -- the corpus itself is the actual
proof this widening was safe, not just the local reasoning.
