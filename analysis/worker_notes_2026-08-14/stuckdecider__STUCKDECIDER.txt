ROOT CAUSE
-----------
`corpus::build_card_index` (corpus.rs ~118-134) maps every BGO-printed bare
card name to a CardId via `.entry(name).or_insert(id)`, walking `CARDS` in
array order -- so an ambiguous family name that BGO always prints WITHOUT
its age suffix (Aggression cards: "Raid", "Enslave", "Infiltrate", ...;
Territory cards likewise, out of scope here) ALWAYS resolves to that
family's FIRST (oldest-age) table entry, no matter which age was actually
in play. This is already known and already partially fixed for ONE family
(Plunder, via `resolve_plunder_age`, replay_common.rs ~3612-3630, matched
against the card's own printed "up to N resource and/or food" cap) -- but
every OTHER Aggression family (Raid, Enslave, Infiltrate, Annex, Armed
Intervention, Spy, ...) had no equivalent correction, so
`ActionClass::PlayAggression`'s dispatch (apply_one, replay_common.rs, the
"ActionClass::PlayAggression =>" arm) was consuming a systematically wrong
card identity whenever a multi-age family's OLDER-age default (cheaper MA
cost) did not match the age actually printed on the journal line.

Concretely, game 7523354 line 233: BGO's own text is Raid's Age II wording
("...2 urban buildings: one of Age II or older and one of Age I or
older...", 2 MA -- confirmed against RULES_SPEC.md 5.5's own table: Raid I
"destroy a level 0-1 building" 1 MA, Raid II "up to a level 0-1 and a level
0-2 building" 2 MA, Raid III 3 MA), but `card_index["Raid"]` always resolves
to `"Aggression: Raid (I)"` (1 MA). `combat::start_aggression` (combat.rs
~260-266) deducts `card.get().military_action_cost` -- the WRONG card's
field -- so it only spends 1 of Purple's military actions instead of the
true 2, leaving `military_actions` (the live per-turn remaining budget,
`PlayerState.military_actions`) 1 too HIGH for the rest of the turn. This
inflated value feeds two downstream computations:
  1. `economy::draw_military_step`'s `military_actions_unused` -> one extra
     end-of-turn military card drawn beyond what the journal shows;
  2. `interact::discard_excess_military`'s `limit = military_actions +
     military_hand_limit` -- inflated by 1, so a hand that genuinely
     exceeds the TRUE limit by 1 (per journal, which announces a real
     discard) computes NO excess in this binary's own reconstruction --
     eventually, several rounds later, landing exactly on this bucket's
     shape: `state.current` has already legally advanced past the player
     the journal's next line names, with nothing pending to explain the gap.

A DIAGNOSTIC RED HERRING (worth an hour of anyone's future time to avoid
repeating): `prescan_military_hand_ledger` (replay_common.rs ~4200-4270,
purely a JOURNAL-TEXT reconstruction used only for the `SimulatorBug`
classification, never consulted by the real replay logic) does NOT model
Rule Spec section 12.2 antiquation -- "on an age ending, all players discard
antiquated cards from HANDS (civil and military)" (RULES_SPEC.md line
297-299, confirmed against CoL p.3 / RB p.21). `game::antiquate` (game.rs
~595-621) DOES correctly implement this for the real simulator, discarding
hand_military cards whose age is older than the age that just ended. This
session spent a long time hand-tracing game 7523354 believing a spuriously
"vanishing" Aggression: Raid (I) card (round 13, between lines 217 and 218)
was itself the bug, before discovering it was CORRECT antiquation (Age II
ending, Raid I correctly discarded) that the ledger's own text-scan simply
never accounts for -- so `SimulatorBug`'s classification ("ledger agrees
with journal; forward simulator's own hand_military is wrong") is
BACKWARDS whenever antiquation participates: the ledger is the one that's
wrong, not the simulator. This did NOT block finding the real bug (the
antiquation trace is what led, by elimination, back to the actually-wrong
Raid MA-cost deduction one round earlier) but a future worker chasing
`SimulatorBug`-tagged games should verify against `game::antiquate`
BEFORE assuming the simulator itself is at fault. Fixing the ledger to
model antiquation would only fix diagnostic LABELS -- it is not used by
the real replay path and would not by itself resolve any StuckPending.

THE FIX (committed, replay_common.rs)
---------------------------------------
New function `resolve_aggression_age(card, raw_text) -> CardId`
(replay_common.rs, right after `resolve_plunder_age`), wired into
`ActionClass::PlayAggression`'s dispatch in `apply_one` immediately after
the existing `resolve_plunder_age` call:
    let card = resolve_plunder_age(card, raw_text);
    let card = resolve_aggression_age(card, raw_text);
Parses the journal's own trailing "uses N military action" clause (reusing
the existing `civil_and_military_uses` helper, already used elsewhere for a
civil-action-total cross-check) and re-resolves `card` to the UNIQUE
family_siblings() member whose OWN printed `military_action_cost` matches
N. A safe no-op (returns `card` unchanged) for: Plunder (all 3 ages tie at
1 MA -- explicitly excluded so it never fights `resolve_plunder_age`'s own,
already-correct, cap-based resolution), a missing/unparseable clause, or a
tie/zero-match on cost (never worse than the pre-correction guess).

Diagnostic/hand-verified BEFORE landing: `Special::DestroyUrbanBuildings`
already correctly loops per age within a SINGLE special variant
(`combat::finish_aggression`, "for &age in ages { enqueue Raid{...} }") --
the prior session's note that Raid II/III's "special list needs 2
DestroyUrbanBuildings entries, not 1" is WRONG / already-fixed independent
of this session; do not re-do that work. Similarly, the prior session
flagged the "half of DOUBLE cost" resource-gain formula as suspect --
VERIFIED CORRECT per RULES_SPEC.md line 353 ("half the resources needed to
build it (rounded up)" -- explicitly PER destroyed building, not summed
first; the code's `printed.div_ceil(2)` per building in
`interact.rs`'s `ChoiceKind::Raid` handling already matches this exactly).
Do not "fix" this rounding -- it is already right.
