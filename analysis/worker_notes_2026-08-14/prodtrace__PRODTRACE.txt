[2] THE ACTUAL ROOT CAUSE: A NON-WORKER WONDER BONUS STARVED BY ORDERING
===========================================================================
Re-ran the game with `REPLAY_DEBUG_ALL=1` and the existing `DEBUG blue_used`/
`DEBUG end_of_turn pre-corruption` instrumentation (both already in the
codebase, no patch needed to see this). The pre-corruption line ALREADY
prints `s.resources` (the engine's own `effects::compute`-derived total
resource income for this round, entirely independent of the token bank) next
to the actual tracked bank state:

  round 17: idx=3 resources=31 blue_total=18 blue_used=16 corr=4 s.resources=14

`s.resources=14` is HELD CONSTANT across rounds 13-18 (traced every
`DEBUG end_of_turn pre-corruption` line for idx=3: 8,8,8,14,14,14,14,14,14 --
the jump from 8 to 14 happens at EXACTLY round 13, the same round as the
Iron-to-Oil upgrade). But `worker_capped_production(&techs, Mine, MAX)`
("mine_full", the pure worker-count-based production ceiling) is only 9 at
round 17 (Iron: 2 workers x 2 = 4, Oil: 1 worker x 5 = 5). The gap
(`bonus_resources = s.resources - mine_full` = 14 - 9 = 5) is computed and
fed to `gain_resources` in `end_of_turn`'s existing "3e. resource
production" step (economy.rs, was lines 1059-1067) -- so the code already
KNOWS about this 5-value gap every round; the question was only why it
wasn't landing.

Traced WHY the gap is exactly 5, and why it jumped from 2 (pre-round-13) to
5 (round 13 on): Grey's own completed wonder Transcontinental Railroad
(built round 10, journal line 336-339) carries `Special::DoubleBestMine`
(card_table.rs:1375). Its resolution (effects.rs:1014-1019):

    DoubleBestMine => {
        if let Some(b) = best_staffed(&p.techs, |k| k == CardType::Mine) {
            stats.resources += b.get().production.resources as i32;
        }
    }

-- i.e. the single best-staffed Mine card's own printed value is added ONCE
MORE, flat, NOT scaled by worker count and NOT tied to any specific worker.
Before round 13 the best mine was Iron (denom 2) -> +2. From round 13 on
(after the Iron-to-Oil upgrade) the best mine is Oil (denom 5) -> +5. This
is exactly the CoL-legal "the best mine produces double" wonder power, and
it is computed CORRECTLY by `effects::compute`/`state_stats` (verified by
grepping card_table.rs and effects.rs directly, not inferred) -- so this is
NOT a computation bug. The gap is real, rules-correct income the true game
received every round Grey had this wonder in play.

THE ACTUAL BUG: `end_of_turn`'s resource-production step ran, in this order:
  1. `credit_production(Mine, blue_available(p), ...)` -- the MANDATORY
     one-token-per-producing-worker placement (never in question, "you
     produce wherever your yellow tokens are").
  2. THEN `gain_resources(p, bonus_resources)` for the wonder's flat bonus,
     using whatever `blue_available(p)` is LEFT.

Both draw from the exact same shrinking `blue_available` pool within the
SAME round. At round 17, `blue_available` before this step was 3 (18 total,
15 already used). Step 1 (credit_production) consumed all 3 physical tokens
placing Iron/Oil's 3 workers (2 Iron + 1 Oil, value 9 -- this alone happens
to equal mine_full here, so credit_production itself is NOT capped this
round). By the time step 2 ran, `blue_available(p)` was already 0, so
`gain_resources(p, 5)` returned 0 and the ENTIRE 5-value wonder bonus was
silently and permanently dropped -- not partially placed, not deferred, just
gone. Confirmed exactly matching the previously-traced symptom (resources
ending the round at 36 instead of 39, later flagged by RESOURCE_DETAIL as
"round=17 actor=Grey delta=-3", and eventually surfacing as an illegal Build
2-3 rounds later per TOKENBANK3's own trace).

This is a DIFFERENT and more precise finding than "credit_production's
forced placement, accumulated over history, is structurally unresolvable"
(TOKENBANK3/TOKENCOUNT/TOKENGAIN's shared conclusion): the forced per-worker
placement itself is fine and matches the journal's own worker history
exactly (see [1]). The loss is entirely in a SEPARATE, non-worker income
stream (a wonder's flat per-turn bonus) that the code already models
correctly in value but starves in PLACEMENT ORDER whenever the round's token
budget is tight -- which becomes likelier precisely when a player has
consolidated workers onto high-value cards (exactly the "upgrade" pattern
the task asked to watch for): the higher the best mine's denomination, the
BIGGER `DoubleBestMine`'s bonus, and the more of the round's scarce token
budget it needs, while it is served LAST.

===========================================================================
[3] THE FIX
===========================================================================
Reordered both `end_of_turn` production steps (food/farm and
resources/mine, economy.rs) to credit the non-worker bonus
(`bonus_food`/`bonus_resources` -- leader/wonder/government flat bonuses,
e.g. `DoubleBestMine`, `BestTheaterDoubleCulture`'s sibling, etc.) BEFORE
the mandatory per-worker `credit_production` call, not after. This does NOT
touch `credit_production`'s own mandatory one-token-per-worker-per-card
placement rule at all (never weakened, still fully forced, still capped at
`blue_available`) -- it only changes which of the two DIFFERENT income
categories gets first claim on a round's shared, scarce token budget when
both want tokens the same round and the budget cannot cover both. Full diff
(prodtrace.patch, 2 hunks, both in `economy.rs`'s `end_of_turn`):

  - compute `bonus_food`/`bonus_resources` and call `gain_food`/
    `gain_resources` FIRST (using `blue_available(p)` as it stood before
    this step touched anything);
  - THEN call `credit_production` for the capped, forced per-worker
    placement, using whatever `blue_available(p)` remains.

VERDICT
===========================================================================
The task's own named hypothesis -- a worker-relocation/upgrade mishandling
that leaves workers "piling up on low-value farms" -- is RULED OUT for
game 7521459: `do_upgrade`/`do_build` correctly reproduce the journal's
exact Bronze -> Iron -> Oil worker history, 1-for-1, with no inference
involved. The REAL cause is a same-round ordering bug in `end_of_turn`
(economy.rs): a legitimate, correctly-VALUED non-worker income source (here,
Transcontinental Railroad's `DoubleBestMine` wonder power -- the best
staffed mine's value added once more, flat) competes with the mandatory
per-worker `credit_production` placement for the same shrinking
`blue_available` token pool within a single round, and the old code served
the forced/worker-tied claim first, unconditionally starving and silently
dropping the flexible/bonus claim whenever the pool ran out -- which is more
likely to happen precisely when a player has consolidated (upgraded) onto
high-value production cards, since that is exactly when `DoubleBestMine`'s
own bonus is largest. Reordering to serve the bonus claim first (2 small
hunks in economy.rs, prodtrace.patch) fixes all 3 of the task's named
regressions (7521459, 7522402, 7522796) with ZERO regressions against the
734-game guard set and the same 5 pre-existing wins retained: 736/709 ->
739/712 completed/exact, RESOURCE_ORACLE 114 -> 111 diverging games. Tests
1451/1451, clippy clean. This is a clean, evidenced, MEASURED win ready to
land.
