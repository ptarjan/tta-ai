STEP 3: the two confirmed, fully-proven mechanisms fixed this pass
============================================================

3.1 -- ENGINE/REPLAYER BUG: an all-food Trade-Routes-Agreement payment on
a Build/Upgrade/WonderStep line was silently NOT converted, so the
reconstruction charged the (untouched) resource pool instead.

File: rust/src/replay_common.rs only.

`total_paid_for_build(text)` correctly reads ONLY the resource-shaped
clauses ("spends N resources" / "loses N military resource") -- it MUST
keep doing exactly that, because its other caller
(`resolve_named_card_by_effect`) solves for a resource DISCOUNT and would
be fed a wrong number if food were folded in. But every downstream caller
that wants "how much did this whole line pay" was composing that with
`.map(|base| base + spent_food_after_resource(text))`, which stays `None`
whenever the ENTIRE payment was food (no resource clause at all) --
indistinguishable from `total_paid_for_build`'s OWN `None` case, a
genuinely free build/upgrade/wonder-stage (its own doc-tested example:
`total_paid_for_build("Purple builds 1 stage of Pyramids")` == `None`).
`convert_trade_food_shortfall`'s gate then silently no-opped, and the
caller's own `Move::Build`/`Move::WonderStep`/`Move::Upgrade` charged the
move's true cost straight out of `p.resources` -- resources the real
player never touched, permanently missing from the reconstruction for the
rest of the game. This is the corpus's dominant "resources short by 1"
Build-bucket signature.

Fix: a new `stated_build_payment(text)` (right above
`convert_trade_food_shortfall`) that tells the three shapes apart --
resource-only, ALL-food (still a real payment, `Some(food)`), and
genuinely free (still `None`) -- used both by `convert_trade_food_
shortfall`'s own gate and by the ordinary Build arm's separate cost-
mismatch pre-check (same bug, same fix, one function).

Tests (RED confirmed by reverting `stated_build_payment` to the old bare
`.map()` composition, then restored):
  - `stated_build_payment_tells_all_food_apart_from_genuinely_free`
  - `convert_trade_food_shortfall_covers_a_build_paid_entirely_in_food`

3.2 -- ENGINE/REPLAYER BUG: Raid II/III's two-or-three eligibility
brackets resolved by blind FIFO order instead of respecting their NESTED
(not independent) eligibility.

File: rust/src/replay_common.rs only (`resolve_intervening`'s
`ChoiceKind::Raid` arm).

`interact.rs`'s `QueueItem::Raid` gates each bracket's own candidate list
on `id.level() <= max_lv` -- RULES_SPEC.md §5.5's "destroy up to a level
0-1 AND a level 0-2 building" (Raid II) / three brackets for Raid III.
This is a NESTED constraint: a low-level casualty is legal for EITHER
bracket, a high-level one ONLY for the wide one. The journal's own
`"Raid casualties ..."` summary line lists casualties by name, not by
which bracket picked which (confirmed: game `7522513`'s "1 Alchemy; 1
Organized Religion" is plain alphabetical order, and Organized Religion,
level II, is not even a legal option for the level-0-1 bracket at all --
it could only ever have been the wide bracket's pick). The old consumer
took whichever FIFO entry was at the FRONT if it matched the CURRENT
bracket's options, with no lookahead -- for this game it handed the wide
bracket "Alchemy" (FIFO front, journal-alphabetical), stranding
"Organized Religion" with no home once the narrow bracket opened next
(not among its options), silently declining it (`Stop`) and leaving
Green one destroyed-building's worth of `workers_free` short for the rest
of the game.

Fix: among the CONTIGUOUS run of FIFO entries that match the CURRENT
bracket's own options (a non-match ends the run -- the same boundary the
existing "discard leading orphans" cleanup already trusted, preserved
unchanged), prefer the HIGHEST-level one (fewest alternative homes),
leaving lower-level/more-flexible entries in the FIFO for whichever
bracket opens next. Existing orphan-cleanup and single-entry tests
unaffected (verified both still pass unmodified).

Test (RED confirmed by reverting the arm to the old front-only loop, then
restored):
  - `resolve_intervening_prefers_the_highest_level_raid_casualty_for_a_wide_bracket_leaving_a_lower_level_one_for_the_narrow_bracket_that_opens_next`
