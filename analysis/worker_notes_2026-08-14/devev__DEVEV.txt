===========================================================================

game.rs `new_game` (around line 433-441):

    // §1.6: no military DECK in Age A -- the ten Age A military cards are
    // shuffled and the top `num_players + 2` become the starting current
    // events. The rest are simply not in the game.
    let mut age_a = build_deck(Age::A, false, n);
    shuffle_cards(rng, age_a.as_mut_slice());

This matches RULES_SPEC exactly: build_deck(Age::A, false, n) returns
exactly these 10 cards; n+2 of them get seeded as `state.current_events`.

Consumption is NOT at setup -- it happens progressively, one card per
`Move::PrepareEvent` for the whole rest of the game. apply.rs
`h_prepare_event` (line 1506):

    fn h_prepare_event(state: &mut GameState, idx: u8, card: CardId) {
        state.players[idx as usize].hand_military.remove_first(card);
        state.players[idx as usize].culture += card.level() as u16;

        state.seeded_by[card.0 as usize] = idx;
        events::reveal_current_event(state);   // <-- pops top of
        end_politics(state, idx, PoliticalAction::Played);   //     current_events and
    }                                                          //     resolves it

`events::reveal_current_event` -> `resolve_event` applies the popped
card's `Special::AllPlayers(EventBlock{...})` for real -- production
deltas, free builds, card draws, etc.

===========================================================================
3. WHY cardblame STILL SHOWS ZERO -- THE REAL MECHANISM
===========================================================================

cardblame's two attribution sets:
  - narrow (`cards_in_play`): end-of-game tableau snapshot. Event cards
    never sit in a tableau (cardblame's own module doc says so explicitly)
    -- narrow zero exposure for this whole family is EXPECTED and correct
    by cardblame's own design, not a bug.
  - widened (`ever_cards_in_play`, replay_common.rs ~5734): union of (1)
    narrow, (2) every `CardId` `move_card_args(mv)` names for every Move
    applied, (3) each player's `colonies`, (4) each player's final
    `wonder`/`government`.

The gap is in source (2). `move_card_args` (replay_common.rs line 5665):

    PrepareEvent { card } => [Some(card), None],

`card` here is the card field on `Move::PrepareEvent` -- i.e. the card
being PREPARED (moved from hand to `future_events`). It is NEVER the card
that gets revealed and resolved by the SAME move's internal call to
`events::reveal_current_event`. Those are structurally two different
`CardId`s within one `h_prepare_event` call. The revealed/resolved
"Development of X" card's id is applied purely inside `resolve_event`'s
state mutations -- it is never the argument of ANY `Move` variant, so no
per-Move attribution scheme (which is what `move_card_args` is) can ever
see it. It also isn't a colony, wonder, or government, so sources (3)/(4)
don't catch it either -- unlike those cases (which the module doc says
were separately special-cased after cardblame's own first real run turned
up exactly this kind of gap), there is currently no fifth source in
`game_ever_cards_in_play` for "cards resolved via `current_events`/
`future_events` reveal."

So all 10 "Development of X" cards fall through every one of cardblame's
four widened sources, and none sit in a tableau for the narrow set --
hence zero-exposure in BOTH sets, for every one of the 10, exactly as
observed, DESPITE being dealt and resolved with real effects in ~45% of
games each (the family average: (players+2)/10 fraction of the 10-card
pool seeded per game, times how many of the seeded ones get popped before
the game ends).

===========================================================================
4. RELATIONSHIP TO THE TASK'S OPTION (a)
===========================================================================

The task's option (a) framed this as "resolved during new_game's initial
deal, before the journal's first line." That specific claim is FALSE: the
corpus lines above show these events resolving at round 3, round 6, round
9, etc, well into real games, each with an actor and a "Current event:"
clause. What IS true, and what makes this the same VERDICT as (a) ("the
engine is correct, the diagnostic simply cannot see it"), is that these
cards are never the SUBJECT of any player Move -- they're a passive
side-effect of resolving a DIFFERENT card's PrepareEvent move -- and
cardblame's widened-set construction is Move-argument-shaped. That is a
structural blind spot in cardblame, not in the engine. The engine's
`new_game` seeding, `h_prepare_event`, and `resolve_event` all behave
exactly as RULES_SPEC.md and BGA's own material describe.
