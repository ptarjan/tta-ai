ROOT CAUSE
========================================================================
Game 7523357, journal line 503-506:
    503: "Purple plays Plunder against Grey Your rival loses a total of up to 7 resource
         and/or food (your choice). You gain that many resource and food.; ; Purple uses
         1 military action"
    504: "concedes defeat"   (Grey, bookkeeping, unrelated)
    505: "Purple produces 7 resources; Grey spends 7 resources"   <- the real PlunderSplit
         resolution, parses cleanly via `parse_plunder_split_line` into (Purple, food=0,
         resources=7)
    506: "Purple increases population Purple spends 4 food"  <- replay STOPS here,
         StuckPending("PlunderSplit choice open for player 1 ...")

`ActionClass::PlayAggression`'s handler (`replay_common.rs::apply_one`, ~line 6834) resolved
"Plunder" from the raw journal text to a `CardId` via `corpus::build_card_index`'s bare-name
lookup -- WITHOUT any age-family correction. Added a temp debug print and confirmed:

    TMPDEBUG PlayAggression raw_card=Aggression: Plunder (I) age_civil=III age_military=III
        hand_military=["Loss of Sovereignty", "Impact of Population", "Impact of Agriculture"]
    TMPDEBUG offer_plunder_split attacker=1 defender=3 printed=3 defender_resources=7
        defender_food=9

Plunder prints "up to N resource and/or food" once per age (3/5/7 for I/II/III,
`TakeFromOpponentBlock.food_and_or_resources` in `card_table.rs`). The journal's OWN text at
line 503 says "up to 7" (the Age III copy) and `state.age_military` was already III at that
point -- but `build_card_index`'s arbitrary same-name pick resolved to the Age I copy (value 3)
instead, because nothing corrected it. `combat::finish_aggression` then called
`interact::offer_plunder_split(state, attacker, defender, 3)` (not 7), which capped the
`PlunderSplit` choice's options at total=3 (`{0/3, 1/2, 2/1, 3/0}`) -- none of which can ever
match the journal's real (food=0, resources=7) resolution. The `plunder_splits` FIFO entry for
this attacker sits there forever, unconsumable, and the replay deadlocks on the very next line
that reaches `resolve_intervening` with this pending still open (506).

This has NOTHING to do with the `PlunderSplit`/split-choice machinery itself, which is correct
-- `parse_plunder_split_line`, `prescan_plunder_splits`, and the FIFO-drain-and-validate consumer
in `resolve_intervening` all worked exactly as designed. The bug is purely in resolving WHICH
`CardId` "Plunder" refers to before the effect even fires -- the choice was offered against the
wrong card's printed number.

Precedent: `ActionClass::TakeCard` (same file, ~line 6288) already has this exact class of bug
fixed for the NINE same-name civil-row-and-friends families, via
`best_age_sibling(card, r.state.age_civil)`. Aggression cards are a military-deck family with
the identical "same bare name, one copy per age, no age tag in the journal text" shape --
`best_age_sibling`'s own doc comment describes exactly this pattern. `PlayAggression` had no
equivalent correction at all.

HAND-VERIFIED A SECOND AND THIRD GAME (both from the 75-ID bucket) before writing the fix -- see
below (this file's "SECOND/THIRD GAME" section) -- both hit the exact same missing-correction
mechanism, on Raid and Plunder respectively, confirming this is not a one-off.

WHY: a real card-identity / DiscardSolver collateral-damage mechanism
------------------------------------------------------------------------
Tried THREE scopes this session, in order, each rebuilt+re-verified against the SAME 366-row
check index:

1. `best_age_sibling(card, r.state.age_military)`, applied to EVERY `ActionClass::
   PlayAggression` card (Plunder, Raid, Enslave, Spy, Annex, Infiltrate, ...) -- 21 regressions.
2. Same scope (every Aggression card), bound changed to `r.state.age_civil` (provably identical
   to `parse_age(line.age)` on every trustworthy line, so guaranteed consistent with an identical
   correction added to `prescan_future_military_needs`) -- STILL 21 regressions, the EXACT SAME
   21 IDs. Ruling out: this is not an age_civil-vs-age_military drift bug; the two bounds were
   never the actual cause.
3. Narrowed to ONLY `card.get().base_name == "Aggression: Plunder"` (both in `apply_one`'s
   `PlayAggression` arm and in `prescan_future_military_needs`, matching gates) -- 8 regressions
   remain (down from 21, i.e. real progress, but not zero).

Root mechanism (confirmed via `REPLAY_DEBUG` trace diff on game `7521683`, one of the 21/8
regressions): `apply_one`'s corrected `card` is fed straight into `Replayer::
consume_named_military_card` -> `ground_for_consumption`, which does:
    if hand.contains(card) { return; }
    let victim = hand.iter().find(|id| !needed_later.contains(id));  // first match, ORDER-sensitive
    hand.remove_first(victim); hand.push(card);
`hand_military` here is largely SIMULATED filler `CardId`s (BGO never reveals a hidden hand's
true contents), and `needed_later` comes from `discard_solver::DiscardSolver`'s own
`FutureNeed`-driven protection set. Changing WHICH exact `CardId` a `"plays <Aggression>"` line
resolves to (even when `prescan_future_military_needs` is kept perfectly consistent with it, as
in attempt 2 above) still changes what `ground_for_consumption` treats as already-in-hand vs.
needing a swap-in, which can flip which SIMULATED card an EARLIER, entirely unrelated hand-limit
discard picks as its victim (`ground_for_consumption`'s victim search is a first-match over
insertion order, not a stable identity-independent choice). That earlier discard drift then
compounds forward through the turn-by-turn simulated hand until a real divergence surfaces (in
`7521683`: `StuckPending: decider 0 != expected actor 1` at journal line 242, many lines after
the actual Aggression play at line 212 -- confirmed BOTH scopes 1 and 2 diverge from baseline at
the EXACT SAME line, ruling out the age-bound choice as the variable that matters).

This is a genuine, deeper structural coupling between "correcting a played card's identity" and
"the discard solver's simulated-hand bookkeeping" that this session did not have budget to fix
properly. It is NOT specific to Plunder or to this bucket -- any correction to `apply_one`'s
card resolution for a card class the discard solver also tracks via `FutureNeed` risks the same
class of collateral regression.
