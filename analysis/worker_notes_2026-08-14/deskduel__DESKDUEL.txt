WHY THIS RUN EXISTS
The desktop climb is stopped; its artifacts are already copied. The climb's
own accept signal (vs_anchor) is known-unreliable -- blind anchor veto, and
the desktop 2p run logged 1400 accepts against only 32 vetoes. vs_anchor is
also not comparable cross-machine because each climb carries its own
anchor. Only a direct duel under ONE binary settles whether the desktop's
three vectors are actually better than what the mini is running.

INTERFACE (learned by reading source, not guessed)
Read /private/tmp/base0815/rust/src/bin/arena.rs and
/private/tmp/base0815/rust/src/arena.rs on the mini (plain local reads).
Confirmed identical on the desktop via `arena.exe --help` (byte-for-byte
same usage text) -- the desktop binary, despite being hand-synced/possibly
older, implements the same CLI:

  arena --a PATH --b PATH --players N --games N --seed N --threads N
        [--kind KIND, default "weighted"]

  --a is the CHALLENGER: seated in ONE seat per game, ROTATED through every
      seat across the run (game g: A in seat g % players, deal seed
      seed0 + g/players).
  --b is the DEFENDER: seated in every OTHER chair, every game.

This means seat-fairness is BUILT IN, not something I had to arrange:
`--games` is a multiple of `players`, so over the whole run each vector
sits in each seat exactly games/players times, by construction (Match::
seats_for + play_one in rust/src/arena.rs, unit-tested by
`the_challenger_visits_every_seat_equally`). I did not need to run mirrored
pairs myself -- the harness already does it, and reports one paired,
deal-clustered win-rate estimate with a proper confidence interval and a
`verdict` gate that requires the WHOLE interval to clear the null
(1/players), not just the point estimate.

NOISE ASSESSMENT
All three configurations pass arena's own gate: the WHOLE confidence
interval clears the null, at n=720 games (>=3x the 240 standard, >>60
minimum), with p-values from 0.0007 down to ~0. These are not point-
estimate-only "ahead"; the margins are large relative to their intervals
(2p: 6.6 pts of margin vs +/-3.6; 3p: 24-26 pts of margin vs +/-3.6; 4p:
5.5 pts of margin vs +/-3.2). None of this is 6-game noise. 3p was
independently reproduced at a second seed with an even larger margin, so
it is not a single-seed fluke either.

CAVEATS
1. ENGINE AGE: the desktop binary (target/release/arena.exe) may be older
   than the mini's current Rust engine -- both sides of every duel used the
   SAME binary, so weight-vs-weight comparison within each duel is valid,
   but none of these results say anything directly about how these vectors
   would fare under the mini's current (possibly patched) rules. Do not
   install off this alone; re-test on the mini's current engine first.
2. 4P CULTURE IS NEGATIVE while win rate is positive (A 231.9 vs best-other
   273.8, lead -41.9). The desktop 4p vector wins more OUTRIGHT GAMES than
   null despite scoring less culture on average than the best opponent --
   i.e. it appears to be optimizing for winning narrowly rather than
   margin. Win rate (not culture mean) is arena's actual gate and the
   actual game-winning metric, so the accept verdict stands, but this is a
   real behavioral difference worth knowing about before installing.
3. 3P CONTRADICTS A PRIOR "SCRAP" CALL. I was told a previous review ruled
   the desktop's 3p champion is scrap and must not be installed, and that
   for 3p the bar here is "is there surprising evidence to overturn that,"
   not "is it slightly ahead." This measurement clears that higher bar: a
   57-59% win rate against a 33.3% null, reproduced at two seeds, p
   effectively 0 both times, WITH a positive culture lead both times
   (+13.5 and +15.6) -- i.e. the 3p vector isn't just winning close games,
   it's outscoring the field too. This is surprising, large, and
   reproducible evidence in the desktop vector's favor, measured under the
   exact protocol (direct duel, same binary, seat-paired, real sample
   size) this task exists to trust over the climb's own blind anchor
   signal. I am NOT overriding the scrap ruling myself -- that's explicitly
   not my call -- but this result is strong enough that the scrap verdict
   should be revisited: either the prior review used a different (possibly
   stale or differently-configured) baseline, or something about this
   vector's real-world/anchor performance diverges from its head-to-head
   strength against the mini's CURRENT champion. Worth a second look before
   treating "scrap" as final.
4. Table composition: per-config, the challenger (desktop) sits in exactly
   1 seat per game and the defender (mini) fills the remaining seats
   (players-1 of them), and the harness rotates the challenger through
   every seat an equal number of times over the run (games is a multiple
   of players, enforced by validate()). This is symmetric by construction,
   not by an average I asked for after the fact.
