DEEP-DIVE 1: 7523162, "Impact of Population" (root-caused, NOT fixed)
=======================================================================

Symptom: engine=[173,205,228,236] index=[171,205,228,236] (sorted per-game
score lists). culture_drifted_in_play=false -- the running culture total
tracked every BGO checkpoint all game; the bug is purely in final-state
worker/happiness accounting the culture checkpoint can't see.

Mapped the sorted arrays back to seats via the index.tsv `results` column:
the diverging entry is GREEN (PLAYER, 171 actual vs our 173). Green's
"Impact of Population" journal line: "Green scores 12 culture"; this binary
computes 14 (content-worker count off by exactly 1: (17-10)*2=14 vs
(16-10)*2=12, `culture_per_content_worker_above_10 == 2` on that card,
`card_table.rs` "Impact of Population" entry) -- this is the exact
"off by one discontent worker's culture" shape the task description named.

Traced backwards with temporary instrumentation (added, verified, then
reverted -- not in the patch) on `economy::increase_population`,
`economy::lose_population`, and `apply::grant_yellow`. Root cause: BGO's
journal line 597 --

  "Grey plays event ... II / Emigration; Each civilization loses half of
   its discontent workers, rounded up (return them to your yellow bank).;
   Green loses 1 population"

-- fires during GREY's Age-IV political phase. `events.rs`'s
`decrease_population_by_half_discontent_workers_rounded_up` handler (the
Emigration mechanic) computes `n = ceil(economy::discontent(Green) / 2)`
for EVERY active player, including Green, at the moment this event
resolves. At that exact moment this binary's own `state.age_civil` is
STILL "III" for the reconstruction (it lags the real Age-III->IV civil-deck
transition, which happened for real sometime earlier in actual play but
which this journal-driven reconstruction only ever catches up to lazily,
via `game::force_civil_age_at_least`/`replay_common.rs::catch_up_civil_age`
-- see that pair's own extensive doc comments, `game.rs` ~line 705 and
`replay_common.rs` ~line 5235). Because the Age-III->IV transition removes
2 unborn population from every player's yellow_bank (RULES_SPEC §12.2.4,
`game::advance_age`, `game.rs:556`), Green's yellow_bank is 2 higher in
this binary's reconstruction than in the true game at the instant
Emigration's math runs -- `economy::discontent` reads `happy_required(5)=5,
happy=5 -> discontent=0` here (verified via temporary
`SCOREDIV_EMI_DEBUG`/`SCOREDIV_POP_DEBUG` prints), so `n=0` and the
Emigration LosePop never fires for Green in this reconstruction, even
though BGO's own journal says it did (n=1). That missing 1-population loss
is exactly 1 content worker's worth of "Impact of Population" culture (2
points) at game end.

Why this isn't caught earlier: `replay_common.rs::is_trustworthy_age_line`
(shared with `is_pure_confirmation_line`, by explicit design -- see that
function's own "hidden twin" doc note) deliberately does NOT force the age
catch-up off a `PlayEvent`-classed line's own age tag, because
`PlayEvent`/`WinAuction`/`Colonize`/`WinWar` lines are documented,
evidenced cases of BGO exporting a summary/confirmation line either before
the real action that causes it, or with a timestamp that collides with an
unrelated OTHER player's still-in-progress older-age trailing line (see
that predicate's own doc, and the landed `WinWar` fix citing real game
`7523079`). So the age (and its yellow_bank deduction) genuinely isn't
caught up yet by the time Emigration's own math runs on this line.

ATTEMPTED FIX (reverted, unsafe): removed `PlayEvent` from the untrusted-age
set in `is_trustworthy_age_line` (kept `WinAuction`/`Colonize`/`WinWar`
untrusted, since those have direct documented evidence; `PlayEvent` did
not, on inspection of its own doc -- it was swept into the shared exclusion
list defensively, not because of a documented age-timing collision).
Rebuilt, ran the full regression check: introduced a REAL regression,
`7523021`, which changed from a 582/582 completed game to a NEW
`StuckPending: decider # != expected actor #, phase Actions, no pending`
failure at "Orange discards 1 card" (line 241) -- i.e. forcing the age
catch-up earlier changed some other player's hand-limit/antiquation timing
enough to desynchronize a later decider check. This is the exact class of
bug `is_pure_confirmation_line`'s "hidden twin" doc warns about: trusting a
`PlayEvent` line's age tag is not safe in general, even though it clearly
IS safe for 7523162 specifically. Reverted the edit; confirmed the tree is
back to a clean `git diff` against 628c0dd before moving on.

WHAT'S NEEDED: a fix scoped much more narrowly than "trust all PlayEvent
lines" -- e.g. only force the catch-up when the PlayEvent line's own actor
IS `state.current` (i.e. it's unambiguously that player's own live turn,
not a same-timestamp confirmation collision with someone else's still-open
turn) AND `state.pending`/`state.queue` are both empty (the existing guard
`catch_up_civil_age` already applies). That's a testable, narrower
predicate than blanket-trusting the class, but it needs its own regression
sweep against all 582 completed games before landing -- not done this pass,
ran out of budget after the one blanket attempt regressed.

TOOLING NOTE
=============
Every trace in this pass used the SAME technique: add a
`std::env::var("SCOREDIV_..._DEBUG").is_ok()`-gated `eprintln!` right next
to the suspect computation (following this codebase's own established
pattern, e.g. `SCOREDIV_EVENT_DEBUG` already existed for the Population/
Happiness blocks in `events.rs` before this pass), filter `index.tsv` down
to a single game ID with `head -1 index.tsv > /tmp/one.tsv; grep
"^$ID\t" index.tsv >> /tmp/one.tsv`, rebuild `--profile difftest`, and run
`replaystats /tmp/one.tsv journals/`. Always revert the instrumentation
(`git checkout -- <file>`) once the trace is captured, before moving to the
next hypothesis -- keeps `git diff 628c0dd HEAD` meaningful at every point
and made the final "confirm clean tree, zero regressions" check trivial.
