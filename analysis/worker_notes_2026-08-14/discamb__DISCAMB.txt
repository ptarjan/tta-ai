STEP 2 -- WHICH RENDERING IS RIGHT, AND WHY (checked 7 instances, not just
the traced game)
================================================================================
Cheap check done FIRST, per task instructions: is this a "header counts only
military cards, resolution line counts all cards" units bug? NO -- ruled out.
Manually inspected the raw journal context around 6 more diff=1/announced>0
instances (7521911 rd10, 7522830 rd15, 7523390 rd15, 7523262 rd16, 7523176
rd10, 7521683 rd4) plus the already-traced 7523376 rd9. All seven show the
IDENTICAL shape: a single "Discard Phase N military card(s) must be
discarded" line immediately followed (within the SAME actor's own turn
block, no intervening event) by a single "<Color> discards N+1 cards"
resolution line -- e.g. 7521683 rd4 Orange: "Discard Phase 1 military card
must be discarded" then "Orange discards 2 cards", nothing else attributable
in between. No sign of a units mismatch (military-only vs all-card-types) --
TTA's base game has no other hand-limit mechanic that would bundle a
non-military card into this same resolution line, and the resolution line's
own text ("discards N cards", not "N military cards and M other cards")
gives no indication of a mixed count either.

Verdict: the RESOLUTION line ("<Color> discards N cards") is the reliable
number; the ANNOUNCEMENT modal under-counts by a small, always-positive
margin. This matches decisive prior evidence already in the codebase's own
module doc comment (`replay_common.rs` ~4270-4281): on game `7522614` (one
of the 29 games that replays clean through `game_over`), the resolution
line's count was independently corroborated end-to-end while THIS BINARY's
own reconstruction was what was wrong -- i.e. the resolution line has
already been proven trustworthy against ground truth once; this pass adds
seven more same-shape instances all pointing the same direction, with a
uniform sign across the whole 268-entry population.

I could not determine the RULE that makes the announcement modal
under-count (matches decider's own earlier finding for 7523376: no
candidate mechanism -- Robespierre, Republic revolution, Patriotism -- has
a documented rule that forces an extra hand-limit-independent discard).
Given the sign is 100% consistent and the resolution line is independently
corroborated on a clean game, this pass proceeds on the resolution line's
authority without needing the exact upstream BGO mechanism.

STEP 3 -- THE FIX (see discamb.patch for the exact diff)
================================================================================
Narrow, evidence-scoped, and deliberately NOT a re-run of the closed
universal experiment:

- New prescan `prescan_discard_disagreement_shortfall` builds a THIRD map,
  `Replayer::discard_target: HashMap<(u8, String), u32>`, populated ONLY
  when, for a given (actor, round): exactly one resolution line exists,
  the announcement was non-zero, and the resolution line's count exceeds
  the announcement's. Value stored is the resolution line's own count (the
  ground truth target), not a bare delta -- kept honest against whatever the
  live engine actually manages to discard on its own, rather than assuming
  the live engine's natural count equals `announced`.
- `apply_one`'s `ActionClass::Discard` arm calls the existing (unmodified)
  `resolve_discard(actor)`, then, if `discard_target` has an entry for this
  (actor, round) and fewer cards were actually removed than the target,
  calls a new `Replayer::force_extra_discards(actor, n)` to make up EXACTLY
  the observed gap.
- `force_extra_discards` picks each extra victim via `interact::
  discard_options` (called read-only, its own ordering/logic is completely
  untouched -- HARD CONSTRAINT respected) wrapped through the EXISTING
  `interact::push_choice` + `Replayer::resolve_one_discard_choice` +
  `discard_solver` pipeline, the SAME machinery an ordinary discard already
  uses -- no new "which card" heuristic invented, no bypass of the discard
  solver's own journal-hint logic.
- This is deliberately NOT the closed universal experiment: that one forced
  the journal's count for EVERY discard action regardless of whether the
  two journal renderings agreed (measured 456 regressions : 1 win). This
  fix only ever engages on the self-flagged 268-entry ambiguous subset;
  every other discard in the corpus (agreement, or no announcement at all)
  is completely untouched -- `discard_target` is empty for them, so the new
  code in `apply_one`'s Discard arm is a pure no-op.

MEASUREMENT BUG FOUND MID-PASS, FIXED, RE-MEASURED
================================================================================
First implementation measured "how many cards resolve_discard actually
removed" as `hand_military.len()` before minus after the call. WRONG: on
game `7521072` round 6 (Orange), the debug trace showed
`before=5 after=7` -- the hand GREW across the call. Reason:
`resolve_discard`'s `Move::Choose` can resume the REST of
`economy::end_of_turn` in the very same call, including that turn's own
military draw ("End turn ... Orange draws 3 military cards" is logged
BEFORE the "discards" line but mechanically resolves AFTER the discard
choice, as part of the same suspended continuation) -- confirmed via
`REPLAY_DEBUG_ALL=1` trace (`DEBUG discard_excess_military` /
`DEBUG discard:` lines). `before.saturating_sub(after)` floors at 0
whenever this happens, so the shortfall computed as `target - 0` instead of
`target - 1`, forcing ONE EXTRA discard beyond what was warranted --
directly caused 44 of the first pass's regressions (evicting real cards a
later action needed).

Fixed by replacing the hand-size delta with a discard-DECISION counter:
new `Replayer::discards_resolved_since_reset: u32`, incremented inside
`resolve_one_discard_choice` (the one place both the natural path and
`force_extra_discards` funnel through), reset to 0 at the top of
`apply_one`'s `ActionClass::Discard` arm before calling `resolve_discard`.
Immune to whatever else the same continuation does (draws, production,
etc.) since only actual `DiscardMilitary` choice resolutions increment it.

discard_options`' ordering as load-bearing for -- the fix does not touch
that ordering, but even a correctly-counted forced discard can still pick
the "wrong" (real-game-inconsistent) card when the count crosses genuine
identity ambiguity.

mechanism further. Do not re-attempt the discard-count self-disagreement
