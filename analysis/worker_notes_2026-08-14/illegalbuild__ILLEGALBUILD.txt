ROOT CAUSE FOUND AND FIXED
-----------------------------
`h_play_leader` (rust/src/apply.rs), the leader-REPLACEMENT path.

A leader carrying a flat `civil_actions`/`military_actions` bonus (e.g. Joan
of Arc: +1 MA; the doc comment on `on_leave_play` already named "Julius
Caesar, Napoleon, ..." as other carriers) who is replaced MID-TURN, after
some of that bonus has already been spent, was having the ALREADY-SPENT
portion clawed back out of the remaining pool a second time, not just the
unclaimed portion. Mechanism: `h_play_leader` called the generic
`on_leave_play(old)`, which does a PLAIN decrement of
`p.civil_actions`/`p.military_actions` by the old leader's flat bonus,
clamped at 0 -- with no memory of how much of that bonus had already been
spent this turn.

Traced end-to-end on BGO human game 7522520, round 11 (added a temporary
REPLAY_DEBUG_ALL trace of every applied move's civil_actions/
military_actions -- this is the technique to reuse if re-tracing):
  - Grey is Theocracy (3 printed MA, confirmed against
    sources/bga_throughtheages_material.inc.php's own Theocracy row:
    'CA' => 4, 'MA' => 3) with leader Joan of Arc (+1 MA per
    data/cards_wonders_leaders.json), so 4 MA total this turn.
  - `Grey adopts existing tactics I / Medieval Army` = `Move::CopyTactic`
    (confirmed 2 MA against sources/ubg_subsequent-rounds.txt's own
    "Copying A Tactic" section: "Pay 2 military actions ... Note: Copying a
    tactic costs you 2 military actions, even if it is one you originally
    played.") -- MA 4 -> 2 remaining. This matched the engine's own applied
    trace exactly: `DEBUG applied mv=CopyTactic{...} -> military_actions=2`.
  - `Grey takes Isaac Newton in hand` (1 CA) then `Grey elects Isaac Newton
    Joan of Arc dies` = `Move::PlayLeader`. THE BUG: the applied-move trace
    showed `military_actions` drop from 2 to 1 on this move alone --
    PlayLeader should touch CIVIL actions only (RULES_SPEC item 7: "Play a
    leader -- 1 CA"), never military.
  - `Grey builds Knights` (1 MA) -> military_actions 1 -> 0. `Grey builds
    Warriors` then needed 1 more MA and had 0: rejected as illegal, even
    though the human demonstrably built both units in the real game.
  - The true total spent this turn was CopyTactic(2) + Knights(1) +
    Warriors(1) = 4, exactly the ORIGINAL total (3 Theocracy + 1 Joan)
    before she left play -- i.e. the correct rule is that Joan's bonus,
    once already reflected in this turn's pool, stays spendable for the
    REST of the turn even after she is replaced. Only a NEWLY GAINED bonus
    (the replacement's OWN effect, or any other card entering play
    mid-turn) should retroactively top up the live counter -- which
    `on_enter_play`'s existing, correct `+=` logic already does; there was
    no symmetric "already spent doesn't get clawed back" protection on the
    LEAVING side.
  - This is exactly the shape `set_government` (same file) ALREADY handles
    correctly for the analogous revolution case, via `carry_over_action_
    pool(old_total, new_total, spent, old_remaining)`: when the total goes
    DOWN, the decrease is absorbed against what's ALREADY BEEN SPENT first
    (`old_remaining - max(decrease - spent, 0)`), so a decrease that is
    smaller than what was already spent leaves the remaining pool
    untouched. `h_play_leader` had its own bespoke, and for MA entirely
    missing, logic instead of reusing this existing, tested, correct
    formula.

THE FIX
-------
File: rust/src/apply.rs, function `h_play_leader`. Snapshots `old_total_c`/
`old_total_m`/`spent_c`/`spent_m`/`old_remaining_c`/`old_remaining_m` (the
same shape `set_government` reads) BEFORE the old leader leaves play, lets
`on_leave_play`/`on_enter_play` run as before (their own CA/MA arithmetic in
between is now dead work, harmless since it gets overwritten), then
overwrites BOTH `p.civil_actions` and `p.military_actions` via
`carry_over_action_pool(old_total, new_total, spent, old_remaining)`,
folding the existing "+1 CA refund for replacing a leader" (RULES_SPEC item
7's separate clause) in as a final `.min(carried_c + 1)` step so the
previously-passing CA refund tests are unaffected.

Commit (in the clone, on top of 9f6104d): 4e29a4c "Fix leader replacement to
carry over already-spent action pool, not claw it back".

   worker to `workers_free`, and that this explained the 31-game
   `workers_free==0` sub-cause (game 7523355 has a colonize with a
   sacrificed Warrior right before its Build failure). WRONG: read
   `interact.rs::colonize_step`'s own comment first -- "§11.4: the token

   implemented. Colonize sacrifice is a dead end for `workers_free==0`.

2. Assumed "GAME DATA UPDATED Orange Bronze: 0 -> 2" (game 7521932 only,
   the ONLY game in the whole corpus with this phrase -- confirmed via
   `grep -l "GAME DATA UPDATED" journals/*.tsv`) was a parser gap silently
   dropping a real worker/resource event. It is NOT unparsed -- `corpus.rs`
   deliberately classifies it as `Bookkeeping` ("an admin correction BGO
   occasionally injects"). This game's title contains "Packs de ressources"
   (a tournament house-rule variant name); most likely a non-standard rule
   this corpus's model was never meant to cover. Left alone -- 1 game, not
   worth chasing further; flagged as an accepted gap, not re-investigated
   beyond this.

3. Added a `trailing_now_resources` REPLAY_DEBUG diagnostic (mirroring the
   pre-existing `trailing_now_science` one) to check whether the `res_short`
   sub-cause (41 games) was ONE systemic under-production bug. First pass
   (828 drift hits across 41 games, every one strongly negative) looked like
   a slam dunk -- but this was almost entirely the SAME diagnostic artifact
   analysis/worker_notes_2026-08-13/replayfin__REMAINING.txt already warned
   about for the science check: comparing state right at the "End turn"
   dispatch point is a FALSE positive whenever that turn is discard-blocked
   (`economy::end_of_turn` returns before running production). Gated the
   check on `!matches!(r.state.pending.top(), Some(Pending::Choice(c)) if
   c.kind == ChoiceKind::DiscardMilitary)` (same pattern the culture-oracle
   checkpoint already uses) and the count dropped from 828 to 28. The
   remaining real drift is SMALL (1-3 resources per game, occasionally +2)
   and does not look like one shared cause -- some correlate with
   "CORRUPTION!" journal lines (§6.2), suggesting a `corruption`/
   `blue_available` accounting edge case, but this was NOT confirmed or
   fixed this session. The diagnostic itself (properly gated) is left in
   the tree as it mirrors an accepted existing pattern and may help whoever
   picks up `res_short` next -- see `trailing_now_resources`'s doc comment.

   Orange ... Raid produces 7 resources") end to end suspecting a
   Raid-resolution resource-crediting bug. Confirmed `parse_raid_casualties_
