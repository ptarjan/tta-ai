THE BUG
-------
`Replayer::ground_auction_winner_hand` (rust/src/replay_common.rs) grounds
the bonus cards a journal-named auction winner is about to sacrifice into
their reconstructed `hand_military`, ahead of `drain_colonize`'s own
`Move::SendBonus` which removes the identical card identity for real a
little later. To pay for each phantom push it evicts one filler card of
unknown identity -- unless every card currently in hand is either (a) still
needed by this same sacrifice (multi-copy case) or (b) already proven by
`DiscardSolver::needed_after` to be played by name later. In that no-victim
case, the old code just pushed anyway: `Move::SendBonus`'s later removal
still fires, so the push+removal net to ZERO instead of the real -1 a
genuine sacrifice leaves behind, and no debt was recorded anywhere -- a
PERMANENT phantom card sitting in the reconstructed hand for the rest of the
game.

THE FIX
-------
Exactly mirrors commit c579b25 ("Record a military-hand deficit when
consumption has no filler to evict"), which fixed the IDENTICAL shape in
`ground_for_consumption` (the shared primitive behind PlayTactic, DeclareWar,
PlayAggression, ProposePact, defense spends, and ColumbusColonize). That
commit's own doc explicitly named `ground_auction_winner_hand` as having
"the identical missing-fallback shape... left to the colonize lane" -- this
session picked that up.

The fix: in the no-victim branch, increment `self.military_hand_deficit
[actor as usize]` instead of silently pushing with no compensation.
`repay_military_hand_deficit` (already written, already used by the
`ground_for_consumption` and `resolve_political_decision`/`PrepareEvent`
sibling fixes) settles the debt automatically the next time that actor's
hand_military genuinely grows (a real draw), popping one filler card as
repayment instead of letting growth stack a phantom extra card on top.

No new mechanism invented. Same field, same repayment path, same "never
evict a card `needed_later` protects" rule already used by every other
filler-pop site in the file.

TEST

New unit test in the existing `#[cfg(test)] mod tests` block, right after
the sibling test `sacrificing_a_grounded_auction_bonus_card_shrinks_the_
hand_by_one_not_zero` (which pins the ORDINARY case, where a filler exists):

    sacrificing_a_grounded_auction_bonus_card_with_no_disposable_filler_
    records_a_deficit_that_a_later_draw_repays

Sets up an auction winner (seat 1) sacrificing a Warriors unit + a
colonization bonus card, but starts their hand_military COMPLETELY EMPTY
(the simplest possible "nothing to evict" case -- no need to manufacture
`needed_later` protection). Confirms:
  1. `ground_auction_winner_hand()` pushes the phantom bonus card (0 -> 1)
     and records `military_hand_deficit[1] == 1`.
  2. `drain_colonize()` sacrifices it for real, netting back to 0 -- same
     net-zero as before the fix (the deficit is what's new, not this net).
  3. A later genuine 2-card draw + `repay_military_hand_deficit(1, 2)`
     leaves the hand at 1 card (not 2) and the deficit at 0 -- the debt is
     repaid, not stacked.

ROOT-CAUSING THE ONE REGRESSION (game 7523376)
-----------------------------------------------
Did NOT hand-wave this. Isolated the game to its own single-row index.tsv
(/tmp/gawh_single_index.tsv) and rebuilt `replaystats` with and without just
the behavioral hunk (doc/test left in place either way):

    unfixed:  "1 games sampled, 1 completed to state.game_over"
    fixed:    "1 games sampled, 0 completed to state.game_over"

Both deterministic across repeated runs (byte-identical completed-ID sets
each time) -- not a flake.

With REPLAY_DEBUG=1 on the fixed build: `GAWH_NO_VICTIM actor=0 line=142`
fires once, early. The recorded debt for actor 0 is later repaid by
`repay_military_hand_deficit` popping one extra filler card from actor 0's
own hand_military at their next real end-of-turn draw -- correct behavior,
that's the whole point of the fix. But `interact::max_force` (the §11.2 bid
ceiling, `pending_moves`'s `Pending::Auction` arm) is a function of the
BIDDER'S OWN hand via `bonus_pool`/`unit_pool`. Popping that one extra
filler card shrinks actor 0's `bonus_pool` by exactly one bonus-type card by
the time the NEXT auction opens, which perturbs the auction's own internal
`active`/`pos` bidder-rotation bookkeeping (the derived ceiling changes which
`Move::Bid`s are legal, which can change how `ground_bid_ceiling` forces
groundings elsewhere in this file). The eventual symptom: the journal's next
`Bid` line is issued by actor 1, but the reconstructed `Pending::Auction`'s
own `player` field (updated by `_auction_move`'s `del active[pos]` rotation
in the Python original) still names actor 0 as the expected decider ->
`StuckPending("decider 1 != expected actor 0, phase Actions, no pending")`
at journal line 265.

CRITICAL CROSS-CHECK: this exact error string --
"StuckPending: decider # != expected actor #, phase Actions, no pending" --
is not new or unique to this fix. It is an existing, ~100+-game bucket two
OTHER workers in this same session independently spent their whole budget
chasing without a full fix:
    analysis/worker_notes_2026-08-14/decider__DECIDER.txt (102 games at an
        older base, root-caused ONE sub-cause -- wrong Aggression-card
        age-sibling resolution -- explicitly did NOT find the true origin of
        the rest within budget)
    analysis/worker_notes_2026-08-14/stuckdecider__STUCKDECIDER.txt (122
        games, implemented a fix for the Aggression age-sibling cause, but
        that fix itself has 3 unresolved regressions of its own -- not
        landed, handed to a future session)

So 7523376's regression is this same still-not-fully-understood systemic
class, not a new bug this session introduced. Before this fix, 7523376
happened to sit on the lucky side of it (an inflated, uncorrected hand size
for actor 0 happened to keep `max_force`/the auction rotation on the path
the journal took); after this fix, the hand size is CORRECT and the game
falls into the same bucket every other affected game already sits in. I did
not attempt to fix the decider-mismatch class itself -- out of scope for
this task, and two other sessions already spent their whole budgets on it
without landing a full fix.
