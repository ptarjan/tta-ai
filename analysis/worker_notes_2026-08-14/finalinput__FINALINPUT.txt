7522866 -- THE SHARED STATE ERROR
====================================
Three "Impact of ..." final-scoring award formulas all disagreed with the
journal on the SAME seat (seat0/Orange) in the same game:
  Impact of Population   journal 12, engine 10 (delta -2)
  Impact of Competition  journal  7, engine  6 (delta -1)
  Impact of Variety      journal 16, engine 14 (delta -2)

All three formulas (`events.rs::scoring_culture`) read `p.techs` /
`p.workers_free` directly (culture_per_content_worker_above_10,
culture_per_level_of_military_units_and_arenas,
culture_per_distinct_type_of_unit_urban_building_and_special_tech) -- three
different linear combinations of the SAME underlying "how many workers on
which unit cards does Orange have" fact. Adding a debug dump
(`SCOREDIV_POPULATION`, already landed by `scorediv5`) showed Orange's
reconstructed state: 15 total workers (14 on tech cards + 1 free), 0
Swordsmen fielded. The journal-consistent value needed is 16 total workers,
with exactly 1 Swordsmen (a level-1 Infantry unit) -- a SINGLE missing
worker on a SINGLE unit card explains all three deltas simultaneously:
  Population:  (16-10)*2=12 vs (15-10)*2=10   -- delta matches -2
  Competition: +1 level*1 worker*multiplier(1) -- delta matches -1
  Variety:     +1 newly-distinct unit KIND (Infantry, not otherwise present)
               * multiplier(2) -- delta matches -2

Hand-tallying Orange's own "builds"/"colonizes ... Sacrificed Units"
journal lines for Swordsmen (3 built, 1 free-Warrior->Swordsmen upgrade,
3 sacrificed across three colonizations) gives a net of exactly 1 Swordsmen
remaining -- confirming the journal's OWN army history, not just the
arithmetic, wants that worker present.

ROOT CAUSE (structural, in the replayer's own bookkeeping, not engine
state -- `rust/src/replay_common.rs`): a colonize-sacrifice reconstruction
queue (`Replayer::colonize_sacrifices`, one `ColonizeSacrifice` per
"<Color> colonizes a <Territory> Sacrificed Units:; ..." journal line, in
journal order) desyncs against the ACTUAL sequence of `Pending::Colonize`
opens during replay.

`apply_one`'s `ActionClass::Colonize` dispatch arm (the confirmation line's
own "pure validation checkpoint") had a special case, landed by a PRIOR
session chasing game 7522152: pop this territory's own queue entry right
here whenever `Pending::Colonize` reads "not open" at this exact dispatch
moment, because `interact::colonize`'s own `colonize_auto` can walk a
force ALL the way to completion with no branching step (a small unit pool,
no bonus cards), entirely inside the earlier `Bid`/`BidPass` line that won
the auction -- so by the time the confirmation line is reached,
`drain_colonize` (the only OTHER place that pops this queue) never got a
chance to see it, and would otherwise leak the entry forever, misattributing
every LATER colonize in the game to the wrong queue front.

The bug: "`Pending::Colonize` not open right now" is ALSO exactly what "the
auction for THIS territory has not resolved yet" looks like. Traced on
7522866's own "Orange colonizes a Developed Territory" line (age II,
journal line 270): at the moment this confirmation line's own dispatch ran,
`state.pending.top()` was `Some(Pending::Auction(_))` -- NOT gone because
`colonize_auto` already finished it, but because the auction itself had not
yet resolved. (`resolve_intervening`'s own forced-`BidPass` block --
"BGO's UI auto-passes a decider with no click to log" -- is what actually
settles this specific auction and calls `interact::colonize`, and it only
runs ahead of a NON-confirmation line, so it had not run yet either, for
the same reason `drain_colonize` had not.) The old check popped the
"Developed Territory" entry anyway (its front-of-queue lineno matched the
current line). Moments later, once the auction genuinely resolved (during
`resolve_intervening`'s prep for the NEXT journal line), the real
`Pending::Colonize` opened and needed the entry that had already been
stolen. `drain_colonize`, later, found the FOLLOWING territory's entry
("Inhabited Territory") at the front instead, force-fed its clauses
(`Unit(Knights)` first) against the wrong, still-open pending, failed the
legal-move check, and fell back to `approximate_colonize` -- which greedily
picks the engine's first-offered move rather than the journal's real
sacrifice list, for BOTH this colonize and the next one. That is exactly
where Orange's Swordsmen worker went missing.

Confirmed exact mechanism with temporary instrumentation (removed before
landing): `COLONIZE_FALLBACK_DUMP=1` showed
`reason=illegal-move actor=0 line=435 clause=Some(Unit(Knights))` fired
while resolving what should have been the "Developed Territory" pending,
and a temporary per-call trace showed the queue's own front already equal
to "Inhabited Territory" (435) before "Developed Territory" (270) had ever
been popped by anyone.


THE FIX
=========
Two changes, both purely in replayer bookkeeping (`rust/src/
replay_common.rs`), neither touches engine state or weakens any check:

1. `apply_one`'s `ActionClass::Colonize` arm (~line 8859): the existing
   "pop only when not open" check now ALSO requires
   `card.is_some_and(|c| state.players[actor].colonies.contains(c))` --
   i.e. this exact territory card is ALREADY a completed colony. That is
   true if and only if `interact::gain_colony` (the only place that ever
   pushes onto `p.colonies`) has actually run for it -- true in the
   original 7522152 shape (fully-forced, already done), false in the new
   7522866 shape (auction not even resolved yet). This keeps the pre-
   existing `a_fully_forced_colonize_pops_its_own_queue_entry_...` test
   passing (it drives a colonize via a direct `interact::colonize` call,
   bypassing move application entirely, so it needs this confirmation-line
   path to still work).

2. `Replayer::apply_move` (~line 1067), the SINGLE chokepoint every `Move`
   in the whole replayer goes through (`try_apply`, `drain_colonize`,
   `resolve_intervening`'s forced pass, all of it): whenever the move is
   `Move::Bid`/`Move::BidPass` -- the only moves that can ever settle an
   auction (`interact::auction_move`'s own match panics on anything else)
   -- snapshot the TOTAL colony count across all seats before and after.
   If it grew by one, some colonize completed (fully auto-resolved) inside
   this exact move, and `colonize_sacrifices`' own front entry is popped
   right here, at the true moment of completion -- not inferred later,
   possibly after the one confirmation-line dispatch that could have
   caught it has already come and gone. This is the general fix: it
   handles BOTH the original 7522152 shape and the new 7522866 shape
   uniformly, and needs no territory-age or actor-identity guessing (a
   colony-count DELTA is age-blind and name-blind by construction; only
   one `Pending::Colonize` can ever be resolving at a time, so a growth of
   exactly one can only be the queue's own front entry).

Both checks are kept (not just #2) because the existing regression test for
7522152 exercises `interact::colonize` directly, bypassing `apply_move`
entirely -- #1 is what makes that test (and the real, rare case a caller
uses the same shape) still correct.
