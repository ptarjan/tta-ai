1. THE FIX
===========================================================================
`Replayer::ground_for_consumption` (`rust/src/replay_common.rs`, private,
the general "ensure `card` is in `actor`'s hand, evicting one filler card
of unknown identity first" primitive behind `consume_named_military_card`
-- the sanctioned way `PlayTactic`/`DeclareWar`/`PlayAggression`/
`ProposePact`/defense-card-spend ground and play a NAMED military card in
one atomic step, plus `ColumbusColonize`'s own direct call) had the EXACT
"net-zero wash" bug `resolve_political_decision`'s own `PrepareEvent`
handling was explicitly fixed for (see that function's own doc, and
`docs/REPLAY.md`'s "Discard-phase hand-size oracle" section) -- but never
got the matching fix:

    if let Some(&victim) = hand.as_slice().iter().find(|id| !needed_later.contains(id.get().base_name)) {
        hand.remove_first(victim);
    }
    hand.push(card);                     // <-- pushed UNCONDITIONALLY

When every card currently in `actor`'s hand is already PROVEN by
`DiscardSolver::needed_after` to be played by name at some later line (a
"fully-protected, not merely empty" hand -- the same edge case
`resolve_political_decision`'s own comment names for real repro game
`7522634` round 3), there is no disposable filler to evict, and the old
code just pushed the needed card anyway with NO compensating eviction. The
very next thing `consume_named_military_card` does is apply the consuming
`Move` (`PlayTactic`/etc.), which removes that SAME card identity from
hand again -- so the whole call nets to ZERO instead of the real -1 a
played card leaves behind. Unlike `PrepareEvent`'s own wash, which at
least records a `military_hand_deficit` entry a later real draw can repay,
this one recorded NOTHING -- a PERMANENT phantom card, not a temporary
window.

FIX: give `ground_for_consumption` the identical `military_hand_deficit`
fallback `resolve_political_decision` already uses, so every no-filler
wash in the file shares one repayment path:

    if let Some(victim) = victim {
        self.state.players[actor as usize].hand_military.remove_first(victim);
    } else {
        self.military_hand_deficit[actor as usize] += 1;
    }
    self.state.players[actor as usize].hand_military.push(card);

Scope note: this is a SHARED primitive. Its callers are mostly squarely
mine (PlayTactic/DeclareWar/PlayAggression/ProposePact/defense, all via
`consume_named_military_card`), but `ColumbusColonize` also calls
`ground_for_consumption` DIRECTLY (not through the wrapper, per that
function's own doc -- "an unavoidable `resolve_intervening` step sits
between the ground and the consuming `Move::ColumbusColonize`"). Columbus's
colonize-without-sacrifice ability is colonize-ADJACENT but is NOT
`approximate_colonize` or "the colonize handler in apply.rs" the other
worker's brief named -- I judged it in scope as a shared low-level
primitive fix, not a colonize-sacrifice-fidelity change, and it can only
ever make Columbus's own hand accounting MORE correct (adds a
never-previously-tracked deficit), never touches `parse_sacrifice_clauses`,
`drain_colonize`, or `approximate_colonize`. Flagging LOUDLY per the task's
own instruction in case this needs reconciling with the colonize worker's
own patch (their clone: /private/tmp/colofix, seen running concurrently).
`ground_auction_winner_hand` has the IDENTICAL missing-fallback shape
(`replay_common.rs` ~2183-2236, found by a sub-agent during this pass) but
is squarely colonize-sacrifice territory (grounds bonus cards ahead of a
`Move::SendBonus`) -- NOT touched, named here as a concrete next step for
whoever owns that lane.

UNIT TEST: `consuming_a_named_military_card_with_no_disposable_filler_
records_a_deficit_that_a_later_draw_repays` (`replay_common.rs`, next to

3. HYPOTHESES INVESTIGATED AND RULED OUT (so the next pass does not re-walk them)
===========================================================================
Per-game cross-tab was built (temp instrumentation: dumped every game in
the +1-delta bucket with its `colonize_approximated` flag and its
`HandLedgerVerdict`/last-ledger-event classification; added, used,
reverted before the final patch). Of 482 dumped +1-delta games, 453 (94%)
have `colonize_approximated=false` -- confirming, as the task's own brief
expected, that the vast majority of this bucket is independent of the
OTHER worker's colonize-approximation-fallback lane. Breakdown of those
453 by last-ledger-event: PrepareEvent 167 (37%, by far the largest),
Draw 116, Discard 93, ConsumingPlay 65 (the bucket THIS fix targets),
DefenseConsume 3.

(a) RULED OUT: `military_hand_deficit` repayment leak. Hypothesis: maybe
    `resolve_political_decision`'s existing `PrepareEvent` deficit fix
    itself frequently fails to repay (its own repayment loop can ALSO hit
    "no disposable filler" and just leaves the debt owed, per that
    function's own doc). Measured directly: at the moment
    `check_discard_phase_oracle` first records a divergence, printed
    `self.military_hand_deficit[actor]` corpus-wide -- nonzero in only
    4/1481 checkpoints. The existing fix is NOT leaking; it is, as its own
    doc claims, "usually self-correcting." The large PrepareEvent-tagged
    bucket above is therefore best read as a PROXIMITY artifact (whichever
    ledger-tracked action most recently preceded the checkpoint), not a
    causal one -- consistent with `drift__DRIFT.txt`'s own warning that
    "the true first divergence is routinely several rounds earlier."

(b) RULED OUT (by code reading, not full corpus trace): the
    `drift__DRIFT.txt` deep-dive's own named next suspect for game
    `7523791` -- "does sacrificing TWO DIFFERENT-VALUE Colonization bonus
    cards (`+1` and `+2`) in the same colonize actually remove BOTH from
    `hand_military`?" Read `interact.rs`'s `colonize_step` `Move::
    SendBonus` arm in full: each commit does `c.bpool.remove_first(card)`,
    `c.bonuses.push(card)`, AND `hand_military.remove_first(card)` --
    keyed by the SPECIFIC `CardId` each clause parses to (a `+1` bonus
    card and a `+2` bonus card are different table entries with different
    identities, so there is no aliasing between them). `drain_colonize`'s
    own `owed` computation is a proper multiset difference against
    `c.bonuses`, so two distinct clauses each get their own `Move::
    SendBonus` call and each removes its own card. This mechanism reads as
    CORRECT for the multi-different-value case; I could not reproduce the
    drift note's suspicion from the code, though I did not walk a full
    corpus trace to be 100% certain no OTHER games hit an edge case here.
    NOTE: `7523791` itself has `colonize_approximated=false` and its
    `HandLedgerVerdict` is `UnmodelledEvent: PrepareEvent` (ledger's own
    text-scan ALSO disagrees with the journal here, so this is not even a
    "SimulatorBug" case) -- this specific game's true root cause remains
    unpinned by anyone as of this pass.
