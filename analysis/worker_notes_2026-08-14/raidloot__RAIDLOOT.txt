BEST EVIDENCE -- the LIVE BGO JOURNAL prints the card's full effect text
verbatim every time it is played, and it settles this beyond any doubt
(game 7521462 line 489, also 7522967 line 730, etc.):
  "Orange plays Raid against Purple Destroy up to 2 of your rival's urban
  buildings: one of age III or older and one of age II or older. You gain
  resources equal to half their TOTAL COST, rounded up."
"Half their TOTAL cost, rounded up" is explicit and unambiguous: sum the
printed costs of every building this raid destroys, then round up ONCE.
RULES_SPEC.md item 6's own summary prose ("half the build cost PER
DESTROYED BUILDING, rounded up (a cost-3 building yields 2 resources)") is
written against the Raid-I single-building example; it never actually
resolves the 2-building case, and where it generalizes to "per building" it
is simply wrong for Raid II/III -- superseded here by the game's own
printed text.

BOTH CLAIMED DEFECTS, VERIFIED
--------------------------------

DEFECT 1 (rounding): REAL. Confirmed against multiple real BGO games where
the SAME card was destroyed twice in one raid (so per-casualty cost was
identical on both sides, isolating the rounding question):
  - game 7523072 line 154: "Raid casualties 1 Philosophy; 1 Philosophy;
    Orange produces 3 resources" (Philosophy costs 3). Total-then-round:
    ceil(6/2)=3 -- MATCHES. Per-card-then-sum (old code):
    ceil(3/2)+ceil(3/2)=4 -- WRONG.
  - Organized Religion x2 (cost 7 each), 3 real games e.g. "...Orange
    produces 7 resources": total-then-round ceil(14/2)=7 MATCHES; per-card
    ceil(7/2)*2=8 WRONG.
  - Theology x2 (cost 5 each), 2 real games, "...produces 5 resources":
    total-then-round ceil(10/2)=5 MATCHES; per-card ceil(5/2)*2=6 WRONG.
  Even-total pairs (Alchemy x2 cost 6, Scientific Method x2 cost 8, Drama x2
  cost 4) don't distinguish the two formulas (both give the same answer when
  each individual cost is already even), which is presumably why this
  survived undetected for two-of-a-kind cases with even printed costs.

DEFECT 2 (silent no-op on a duplicate destroy): NOT REPRODUCIBLE as
literally described. I read `QueueItem::Raid`'s handler (interact.rs, was
lines 1089-1121, now ~1108-1141): each age-tier bracket's candidate list is
recomputed FRESH from `state.players[victim].techs.iter()` filtered on
`slot.workers > 0` at the moment THAT bracket is dequeued -- which is always
AFTER the previous bracket's choice has fully resolved and mutated state
(the engine drains `state.queue` strictly in order, blocking on any
`Pending::Choice` until a `Move::Choose` arrives). A card already destroyed
to `workers == 0` by an earlier bracket is therefore never re-offered to a
later bracket, so `techs.get_mut(id)` can never legitimately return
`workers == 0` for an option a player was validly offered. `TechSlot.workers`
also does double duty as "how many copies of this card the player owns with
a worker on it" (never removed from the tableau on destroy, just
decremented -- confirmed via `Tableau::remove` not being called from either
`ChoiceKind::Raid` or `ChoiceKind::DestroyOwn`), so the real "two casualties,
same card name" case (proven common in the corpus above) is naturally
handled: workers=2 lets both brackets independently succeed. I could not
construct a legal path that hits the `if !ok { return; }` guard with a
validly-offered option. Left UNCHANGED except that it now also flushes any
ALREADY-accumulated loot from an earlier bracket before returning (see
below) -- a robustness improvement, not a functional behavior change, since
I could not prove this branch reachable.

*** apply.rs, costs.rs, effects.rs, legal.rs ARE in this diff ***
Per the hard constraint about the missing commit f2dff03 (which also
touches these same four files): my only change to each is the single
mechanical `raid_loot_pending: 0,` line inside that file's OWN
`blank_player()` test helper, to keep it compiling against the new

The coordinator should be able to hand-apply this one line to each
regardless of how f2dff03 reshapes the rest of the file, but flagging it
explicitly as instructed.

Design note: I first considered NOT persisting anything in `PlayerState`,
but `QueueItem::Raid`'s two brackets are enqueued BOTH AT ONCE, upfront, by
`combat::finish_aggression`, before either bracket's choice is answered --
so the second bracket's `QueueItem` cannot be given the first bracket's
actual outcome at construction time. Some form of state that outlives one
`resolve_choice` call and survives across the intervening player decision
was unavoidable; a small persistent per-player field, always fully drained
(`std::mem::take`) the moment the raid's last bracket resolves, was the
least invasive option that keeps `economy::gain_resources` itself
untouched (called with a different amount, never a different formula).

RED-CONFIRMATION
------------------
New test in rust/src/interact.rs (`interact::tests` module):
  raid_ii_rounds_the_combined_printed_cost_of_both_casualties_once_not_each_casualty_separately
Gives a defender 2 copies of Philosophy (printed cost 3, Age A -- eligible
for both Raid II brackets), runs a full "Aggression: Raid (II)" through
`start_defense`, destroys both copies across the two brackets, and asserts
the attacker ends with exactly 3 resources (matching real game 7523072),
plus an intermediate assertion that resources are still 0 after the FIRST
bracket alone (loot must not be granted until the raid's last bracket
settles).

I confirmed RED by temporarily reverting JUST the `if loot { ... }` body in
`ChoiceKind::Raid` back to the original per-bracket `gain_resources(...,
printed.div_ceil(2))` call (backed up the fixed files first, restored them
after). Re-running the test against that reverted code failed exactly as
expected:
  thread '...raid_ii_rounds...' panicked at src/interact.rs:2302:9:
  assertion `left == right` failed: loot is not granted until the LAST bracket settles
    left: 2
   right: 0
i.e. the OLD code granted `ceil(3/2)=2` resources immediately after the
FIRST bracket alone, instead of waiting for the total. Restored the fix;
re-ran green (see below).

  7522967: a REAL regression, but a consequence of correctness, not a new
  bug in my code. This game has TWO Raid uses. The second (line 730, round

  Religion; 1 Organized Religion; Green produces 7 resources" -- printed

  "ledger agrees with journal; forward simulator's own hand_military is

  hand_military count before either version reaches the Raid at line 730.
  baseline's build simply happens to still limp to completion after that
  (1/1 completed, exact-match not reached), while my fix -- which now
  grants Green exactly 1 resource LESS than baseline's inflated total at
  line 730-732 -- pushes Green's tableau state (via the pre-existing
  divergence) into an "IllegalMove: Build" at line 740 ("Green builds Tanks
  Green spends 7 resources") that baseline's OVER-crediting happened to
  paper over. In short: fixing the Raid rounding bug removed an accidental
  compensating error that was propping up this one already-broken game.
  I did not attempt to fix the pre-existing hand_military SimulatorBug --
  it is a separate, already-tracked defect, well outside this task's scope

  The 3 WINS are clean, direct confirmations of the fix: 7522520 (Multimedia
