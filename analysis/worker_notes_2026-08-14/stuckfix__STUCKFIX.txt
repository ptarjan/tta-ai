WHAT I CHANGED ON TOP OF THE ORIGINAL PATCH
---------------------------------------------
The original stuckdecider patch (commit 9c210f6, `resolve_aggression_age`
in replay_common.rs) was correct as written and did NOT need any changes
to itself. What it exposed needed fixing elsewhere:

Root cause of the false regressions: correctly resolving Raid II/III (2/3
MA, TWO printed age brackets each: card_table.rs's `Special::
DestroyUrbanBuildings(&[Age::II, Age::I])` for Raid II, `&[Age::III,
Age::II]` for Raid III) means `combat::finish_aggression` now genuinely
enqueues TWO separate `QueueItem::Raid` destroy choices per Raid II/III
play, instead of the old code's always-wrong-but-single-bracket Raid I.
Each bracket's "destroy UP TO N urban buildings" (RULES_SPEC.md line
82/98) is an OPTIONAL choice -- a human attacker can leave an eligible
building standing. But `interact.rs`'s `QueueItem::Raid` handling (around
line 1076, pre-patch) built the candidate list and called `push_choice(...,
auto: true)` with NO way to decline. `push_choice`'s own `auto`+`len()==1`
rule (interact.rs ~line 171) force-resolves a lone remaining candidate
IMMEDIATELY, with no `Pending::Choice` ever created -- so the replay's own
journal-aware `ChoiceKind::Raid` handler in `replay_common.rs`'s
`resolve_intervening` (the one that checks the prescanned `raid_destroys`
queue against what the journal's "Raid casualties ..." lines actually
report) never got a chance to see that the human declined the second
bracket. Net effect: whenever the FIRST bracket happened to leave exactly
one eligible building standing for the SECOND bracket, this binary
force-destroyed it even though the real player left it alone and the
journal has no record of it -- confirmed on game `7522647` (Orange's own
starting `Philosophy` lab, force-destroyed by Raid II's second bracket at
journal line 171/round 12, only surfacing as a failure 4 lines later at
line 221 when Orange tries to `Upgrade Philosophy` and this binary's own
`workers(Philosophy)` is wrongly already 0).

Fix (commit 2796ab9, two files):
1. `rust/src/interact.rs`, `QueueItem::Raid` handling (~line 1076): after
   building the candidate `opts` list, append `ChoiceOption::Word(Keyword::
   Stop)` -- but ONLY when `!no_loot`. `no_loot` is the one field the two
   real call sites already differ on: `combat::finish_aggression`'s real
   Raid-card enqueue passes `no_loot: false` (all 3 Raid tiers); `events.rs`
   `destroy_one_urban_building_of_each_opponent` (Terrorism) passes
   `no_loot: true` and is MANDATORY, not "up to" -- so it must never get a
   Stop option. Appending Stop naturally defeats `push_choice`'s
   `len()==1` auto-resolve for a lone-candidate Raid bracket (list becomes
   len 2: the candidate + Stop), so `auto: true` on the `push_choice` call
   itself did not need to change.
2. `rust/src/interact.rs`, `resolve_choice`'s `ChoiceKind::Raid` arm
   (~line 447): if `opt` is `Word(Stop)`, return without destroying/looting
   (declined).
3. `rust/src/replay_common.rs`, `ChoiceKind::Raid` handling inside
   `resolve_intervening` (~line 1479): now precomputes `stop_idx` (the
   position of the `Stop` option, if this choice offers one). The loop
   still prefers a `raid_destroys` front-entry match (pop and take it) same
   as before; if the front entry does NOT match this choice's own options,
   it now takes `Stop` (if offered) WITHOUT touching the queue -- the front
   entry, if any, belongs to a later Raid/Terrorism event. Only when `Stop`
   is not offered (Terrorism) does a mismatch fall back to the OLD "skip
   past an earlier already-auto-resolved single-option Raid/Terrorism and
   keep looking" behaviour, preserved unchanged for that case.
4. `rust/src/replay_common.rs`, `resolve_aggression_age`'s doc comment
   updated to describe and cross-reference this mechanism instead of
   excluding Raid (an earlier, abandoned attempt at this session literally
   excluded `"Aggression: Raid"` from the function to sidestep the bug --
   DO NOT reintroduce that; it was measured at 0 wins / 0 regressions, a
   dead end, and is not part of the committed patch).

Bots: `bots/book.rs`'s `ChoiceKind::Raid { .. } | ChoiceKind::Annex { .. }`
arm (~line 1378) only ever calls `best.consider(i, v)` for `ChoiceOption::
Card` entries -- a `Word(Stop)` option is silently never considered, so
`Best`'s default (`i:0`, unset) still resolves to whichever real candidate
scored highest, i.e. the bot's behaviour is UNCHANGED (it never declines,
same as before this session -- previously it never got the choice not to).
Checked the `Best::new()`/`consider()` default-index-0 fallback explicitly
(interact.rs ~1254-1272) for the n==0-candidates-only-Stop-left case too:
still correct (only Stop exists, only Stop can be at index 0). `weighted`/
`neural` bots do not pattern-match `ChoiceKind` at all (grepped; only
`book.rs` does) -- they must route through generic legal-move enumeration,
so they are structurally unaffected by a new option appearing in `c.
options`. NOT independently verified by running self-play/training after
this change -- see "WHAT I DID NOT FINISH".
