============================================================
INSTRUMENTATION: TIE_CENSUS
============================================================

Added a permanent (not temporary/reverted) diagnostic env var, TIE_CENSUS,
wired the same way SCOREDIV_DUMP_COMPLETED/REPLAY_DUMP_BUCKET already are
(one flag in `debugflags.rs`, checked at each call site, no behavior change
when unset). When set, every superlative-target selection in
`events::apply_single_target`/`events::conditional_target`/
`events::resolve_count_targets` prints one stderr row:

  TIE_ROW game=<id> line=<journal lineno> card=<name> kind=<selection key>
    stat=<Strength|Culture> order=[<colors, clockwise from revealer>]
    values=[<that stat's value for each color in order>]
    selected=[<colors the engine actually picked>]

Deliberately dumps RAW inputs (every live seat's stat value, in the
UNMODIFIED clockwise-from-revealer order -- never whatever protected/
reversed order a caller actually ranked with) rather than a precomputed
verdict, so a script can replay ANY candidate tie-break rule against the same
census without a recompile -- this is what let six candidate rules get
scored in one afternoon instead of six edit-compile-sweep cycles.
`apply_single_target` rows are gated on the card's own block being non-empty
(`EventBlock::EMPTY` is a proven no-op -- every card triggers all four
singular keys unconditionally per `resolve_event`'s own doc, so without this
gate every ordinary card with no `strongestPlayer`/etc. clause at all would
contribute four meaningless rows).

New `tie_context` module: a diagnostic-only thread-local `(game id, journal
line, card name)` label. `events.rs` has no journal/game-id of its own to
thread through every targeting function's signature, so this is a small,
explicitly-documented thread-local (replay is single-game, single-threaded
per process) rather than a signature change to a dozen call sites. Set from:
  - `replay_common::replay_game`'s own `meta.id` (once per game).
  - `resolve_political_decision`'s own `prep.lineno`, right before the
    `apply::apply(Move::PrepareEvent)` call that synchronously resolves the
    revealed event inside `apply::h_prepare_event` -> `events::
    reveal_current_event`. NOT `self.current_lineno`: that field tracks the
    OUTER per-journal-line loop, but `resolve_political_decision` is called
    from the political-phase machinery, which can run before or after that
    line's own journal row is reached -- using `current_lineno` here silently
    mislabeled every row with the WRONG journal line (caught by a systematic
    "journal line has no 'Current event:' clause at all" failure during
    validation: 0/281 clean Barbarians resolutions on the first sweep,
    fixed by switching to `prep.lineno`, which `event_plan::solve` derives
    directly from the SAME journal row BGO itself logs the reveal+resolution
    text on).

Guard: `cargo test --profile fasttest --lib` 1420 passed (baseline 1419, +1
for `tie_context`'s own round-trip test), 0 failed. `cargo clippy
--all-targets`: 0 warnings/errors.

CENSUS METHODOLOGY
============================================================

Full-corpus sweep (`TIE_CENSUS=1 ./target/difftest/replaystats
sources/bgo/index.tsv /tmp/bgo-journals/journals`) over all 1011 games
produced 4719 TIE_ROW lines. Breakdown by selection key:

    1321  single:Strength:best=false:favor_current=false   (WeakestPlayer)
    1301  single:Strength:best=true:favor_current=true      (StrongestPlayer)
     291  strongest_count:1
     281  barbarians_outcome
     281  barbarians_culture
     276  strongest_count:2
     210  weakest_count:1
     180  single:Culture:best=true:favor_current=true        (PlayerWithMostCulture)
     150  weakest_count:2
     147  single:Culture:best=false:favor_current=true        (PlayerWithLeastCulture)
     146  barbarians_strength:among=1
     135  barbarians_strength:among=2

Cross-referenced against the journal's own "Current event:" outcome clause(s)
for each row's (game, line). Following weakest__WEAKEST.txt's own established
(and re-validated) rule: ONLY journal lines whose "Current event:" DESCRIPTION
is a single '.'-terminated sentence are trusted -- a card with a combined
multi-effect description (e.g. Refugees: "The strongest scores... The
weakest... loses...") has multiple outcome clauses with no sound way to pair
them back to a specific effect from the text alone (that file's own "Border
Conflict" counter-example still applies; not re-litigated here). Barbarians,
Reign-of-Terror-style singular keys, and all four count-based cards
(Foray/Cold War/Raiders/Crime Wave) all happen to have single-sentence
descriptions in the base game, so this filter costs little coverage for this
question specifically. For the two count-based keys (cutoff > 1), ground
truth is the SET of colour names mentioned anywhere in the outcome clause(s)
(robust to Foray/Raiders' extra "X choses first" clause and to Cold War/Crime
Wave's clean two-clause shape), compared as a set against the engine's own
`selected` set.

"Tied at cutoff" definition: sorting all live players by the ranked stat,
the value at the last SELECTED rank equals the value at the first EXCLUDED
rank (e.g. for weakest-2, ranks[1] == ranks[2]). For Barbarians specifically,
"tied" covers EITHER a culture tie at the top (2+ players share the max
culture, so WHO is "the civilization with the most culture" is itself
ambiguous) OR a strength tie at the weakest-N cutoff boundary -- either one
makes the final population-loss decision tie-break-sensitive.

BARBARIANS CENSUS -- the primary question
============================================================

  total clean Barbarians resolutions: 281
    culture tied at top:        15
    strength tied at cutoff:    64
    either tied:                73
    neither tied (clean untied):208

Six candidate rules scored on the SAME 281-row census (culture_reverse /
strength_reverse mean "protect the current player from a bad culture-pick /
weakest-cutoff tie by reversing `order` before ranking", exactly
`protect_current_from_bad_tie`'s own existing mechanism, just tested on both
ranking steps independently):

  RULE                                                          overall  untied   tied
  --------------------------------------------------------------------------------------
  CURRENT (favor-current culture, protect-current strength)     99.3%    99.5%    98.6%
  reverse culture tie too (coordinator's hypothesis)             94.7%    99.5%    80.8%
  favor current on BOTH (no protection anywhere)                 83.3%    99.5%    37.0%
  protect on both, but culture direction inverted (control)      81.5%    99.5%    30.1%
  exclude current player entirely from both selections           47.7%    44.7%    56.2%
  nobody selected whenever strength tie sits at the cutoff        88.3%    99.5%    56.2%

  Exact counts:
  CURRENT:                    279/281   untied 207/208   tied 72/73
  reverse-culture-too:        266/281   untied 207/208   tied 59/73
  favor-both:                 234/281   untied 207/208   tied 27/73
  protect-both-wrong-dir:     229/281   untied 207/208   tied 22/73
  exclude-current:            134/281   untied  93/208   tied 41/73
  no-select-on-strength-tie:  248/281   untied 207/208   tied 41/73

CONCLUSION: the shipped rule wins outright, and by a wide margin on the tied
subset specifically (98.6% vs the next-best candidate's 80.8%). The
coordinator's specific hypothesis -- "conditional_target's culture ranking
(line 1005) uses unreversed `order`, favoring the current player INTO a
culture tie that then feeds a penalty, the same inversion already fixed for
the strength cutoff 4 lines later" -- is a reasonable-sounding prior (the
overall Barbarians effect IS a penalty), but the 1011-game corpus does not
bear it out: reversing the culture step breaks 14 more of the 73 tied games
than it fixes (72 -> 59 correct). BGA's real tie-break asymmetry (favor
current on WHO has the most culture, protect current on WHO counts as
weakest) does not reduce to "penalty outcome -> protect current on every
ranked step feeding it". Not changed.

`resolve_count_targets`'s `strongestPlayers` path (events.rs:1054, plain
unreversed `order`) was also checked directly against the card table, not
just reasoned about: `Special::StrongestPlayers` is printed by exactly two
base-game cards (`card_table.rs` line 3275 Foray, line 3636 Cold War), and
BOTH pair it with `Special::Gain` only -- neither ever prints `Lose`. So
there is no base-game card where this path's direction is exercisable as a
penalty; the current unreversed order is correct for every card that exists
today. (`WeakestPlayers` is printed by exactly Raiders and Crime Wave, both
`Lose`-only, already correctly reversed -- matches that function's own doc
comment, re-confirmed rather than assumed.) The "drive direction off
gain/lose structurally instead of auditing per-key" idea (coordinator's point
3) is safe in principle but there is currently no failing case to motivate
restructuring working, tested code around -- left alone.

Every tied Barbarians resolution (game/line/order/culture/strength/among/
engine-pick/journal-victim) is in /tmp/tie_rows.txt's full census and the
raw script output; the SINGLE remaining mismatch under the current rule is
game 7521544 line 339 -- the exact game buildbk__BUILDBK.txt traced by hand
(engine picks Purple, journal says "No effect"). Culture is UNTIED there
(Purple=25 outright highest); the anomaly is entirely in the 3-way
strength=11 tie among Purple/Orange/Green (current player). No candidate
rule tested reproduces BGO's "No effect" outcome for this specific game
without breaking other games elsewhere in the census -- consistent with
weakest__WEAKEST.txt's own ~1.2% "genuinely unexplained BGA divergence, no
available oracle" rate for strength-tie selections generally. Left as the
same already-documented, unfixable-without-a-BGA-source anomaly.
