0. TWO BUGS, NOT ONE
===========================================================================
Went in expecting a single "ground the named unit" reconstruction repair
(`Replayer::approximate_colonize`, `rust/src/replay_common.rs:2312` in the
brief's line numbering). Found and fixed TWO independent defects, both
required to move the needle without regressing:

  A. `parse_sacrifice_clauses` (`rust/src/replay_common.rs`, ~line 5030) --
     a genuine PARSING BUG, not a hidden-information gap. Its unit-clause
     match arm was `[unit] => sacrificed_unit_card(unit, ...)`, a
     single-word slice pattern. Every base-game unit name IS one word
     ("Warrior"/"Cannon"/"Knights"/"Swordsmen"/...) except ONE: "Modern
     Infantry" (age IV, the only two-word unit in the card table). A
     "1 Modern Infantry" clause split into `["Modern", "Infantry"]`, missed
     the `[unit]` arm, and fell into the same `_ => None` catch-all this
     function's own doc says is for SKIPPING non-card bookkeeping clauses
     ("Colonization bonus: +N", "Total force: N") -- i.e. a real sacrificed
     unit was silently indistinguishable from "nothing was sacrificed here
     at all". Confirmed on real game `7522267` (line 321): journal says
     "1 Cannon; 1 Warrior; 1 Modern Infantry", parse only produced
     `[Unit(Cannon), Unit(Warriors)]`.

     Fix: replace the single-word arm with a catch-all that joins ALL
     remaining words with a space before the lookup (`words =>
     sacrificed_unit_card(&words.join(" "), card_index)`). Handles every
     unit name, one word or several, without special-casing "Modern
     Infantry" by string. The two earlier, more specific match arms
     ("Colonization card +N", "Military card +1") still take priority since
     Rust matches top-to-bottom.

  B. `Replayer::drain_colonize`'s fallback (`approximate_colonize`,
     `rust/src/replay_common.rs:2312` per the brief) -- the actual named
     defect. When the journal's next owed clause is `SacrificeClause::
     Unit(card)` and `card` is not currently in `Pending::Colonize::pool`
     (this binary's own reconstructed army snapshot), the old code gave up
     immediately and let `approximate_colonize` grab whatever `legal_moves`
     offers first -- typically MORE, WEAKER substitute units, exactly as the
     brief described.

     Fix: new `Replayer::ground_army_unit_for_consumption` (mirrors the
     existing `ground_for_consumption` hidden-hand repair, extended from
     `hand_military` to the ARMY). Before falling back, SWAP one worker off
     whichever OTHER unit the pool already has onto the named card instead
     -- net army size unchanged, only WHICH unit types this binary believes
     make up the army gets corrected. Never steals a unit `owed` still needs
     for a LATER clause of the same sacrifice (same caution the existing
     `ground_auction_winner_hand` already uses for bonus cards).

1. THE GRANT-WITHOUT-A-VICTIM VARIANT THAT WAS TRIED AND REJECTED
===========================================================================
First attempt mirrored `ground_for_consumption` EXACTLY, including its
"always push, victim-removal is best-effort" shape: when no swap victim was
available, grant the named unit anyway (grow army size by one) rather than
leave `drain_colonize` stuck. Measured:
  - Fixed the then-only regression (game `7522267`, via mechanism A above
    actually, not this).
  - Introduced a NEW regression: game `7522866`, 4p. Granting a Knights
    worker with no compensating removal pushed a player's `p.techs` worker
    total past what an UNRELATED, otherwise-correct later
    `ChoiceKind::LosePop` "destroy something" choice expected -- that
    choice's own candidate-matching logic (`replay_common.rs:1426`,
    `lose_pop_destroys` queue) could no longer find the journal's real
    "destroys" line among its options, and the whole replay stalled
    ("LosePop choice open for player 0 but no journal-observed destroy line
    left to resolve it with"). Net effect measured: -1 completing game vs.
    baseline, 0 wins -- a regression the brief's hard rule ("never make the
    replayer skip/coerce/forgive... to manufacture a completion") reads as
    exactly the wrong direction: it would have been trading one kind of
    fidelity gap for another, invisible one (worker-count/population
    mismatch instead of wrong-unit-sacrificed).

Reverted to the strict SWAP-ONLY version: if no non-owed victim exists in
the pool, `ground_army_unit_for_consumption` is a no-op and
`drain_colonize` falls through to the pre-existing `approximate_colonize`
fallback UNCHANGED -- strictly no worse than baseline for that one clause.
Combined with fix A (which independently unblocked several of the
`illegal-move` fallback fires that swap-only alone could not reach), this
is the version that landed with zero regressions.
