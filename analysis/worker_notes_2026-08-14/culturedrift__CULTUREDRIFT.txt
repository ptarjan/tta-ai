=== ROOT CAUSE FOUND AND FIXED ===

File: rust/src/effects.rs, `apply_special`'s `CulturePerHappyFromTemplesTheatersWonders`
arm (Michelangelo's leader ability).

Traced via game 7521066 (Purple, round 12): the debug trace
(`REPLAY_DEBUG=1 ./target/difftest/replay ... 7521066`) showed:
  "DEBUG end-turn culture drift: actor=1 journal says (now 39), this binary
   computes 38 (delta -1) at line 304"
and this delta -1 persisted UNCHANGED at every subsequent Purple end-turn
checkpoint for the rest of the game (lines 334, 366, 408, 441: always exactly
-1) — a signature of a one-time miscount at the turn Purple completed Kremlin,
not a compounding per-turn bug.

Purple held Michelangelo (elected round 7, confirmed still in play — round
10's "Orange plays Infiltrate against Purple" destroyed Purple's unfinished
Transcontinental Railroad WONDER, not the leader). Purple completed Kremlin
on round 12. Kremlin's printed effects (`rust/src/card_table.rs`) include
`happy: -1` — a genuine printed UNHAPPY face, not merely the absence of a
happy face; Kremlin is the only base-game wonder with negative printed happy.

The buggy code:
    let mut happy = happy_from(&p.techs, |k| matches!(k, CardType::Temple | CardType::Theater));
    for &w in p.completed_wonders.as_slice() {
        if p.flipped_wonders.contains(w) { continue; }
        happy += w.get().effects.happy as i32;   // <-- BUG: raw signed value
        if p.homer_wonder == w { happy += 1; }
    }
    ...
    stats.culture += v as i32 * happy.max(0);

Michelangelo's printed text is "1 culture per HAPPY FACE from temples,
theaters and wonders" — an unhappy face is not a happy face, so it should
contribute ZERO to this count, never a negative number that cancels a happy
face contributed by some OTHER source in the same sum. FAQ v1.5 p.9 (already
in sources/faq_v15.pdf) independently confirms this per-source count is its
own thing, exempt from the whole-civilization 0..8 happiness clamp ("the
maximum per-turn Culture benefit of Michelangelo can be greater than eight")
— i.e. it is a face COUNT, not a net-happiness SUM. The two sibling helpers
`happy_source_count` and `temple_theater_wonder_happy_source_count`
(same file) already gate on `card.effects.happy > 0` for exactly this
reason; this arm was the one place that summed the raw signed value instead.

THE FIX: clamp each wonder's contribution to non-negative before adding it:
    happy += w.get().effects.happy.max(0) as i32;

This is NOT the wonder-loop `continue`-before-own-effects family of bugs the
task brief flagged (Homer / happy_source_count / temple_theater_wonder_
happy_source_count / Michelangelo's arm) — I checked all four call sites and
the Homer-unconditional-check-before-`continue`, and the `effects.happy > 0`
gating in both `happy_source_count` and `temple_theater_wonder_happy_source_
count`, are ALL ALREADY CORRECT at 13019ca (fixed in prior commits ed3ccc9,
8513ae0, a149802 — visible in `git log --oneline -- rust/src/effects.rs`).
The bug that remained was specifically the un-clamped sum inside
Michelangelo's own `CulturePerHappyFromTemplesTheatersWonders` arm.
