BUCKET

StuckPending sub-bucket: "auction decider # owes a real bid/pass decision (#
legal moves) but the upcoming line (Pass) is neither, and more than BidPass is

============================================================================
ROOT CAUSE
============================================================================
`rust/src/interact.rs::start_auction` (colonization auction, RULES_SPEC
11.1/11.2) filtered the auction's `active` bidder list down to players whose
own `max_force(...) > 0` BEFORE the auction ever opened. RULES_SPEC 11.1 says
the auction is "open to all players", and the real BGO journals confirm two
DIFFERENT observed behaviours the old filter conflated into one wrong rule:

  1. Game 7523791, journal line 200: Green colonizes a Vast Territory the
     round before (line 175, sacrificing 3 Warriors), which drops Green's own
     `max_force` to exactly 0 by the time the NEXT territory ("Developed
     Territory") is revealed by Green themself at line 199. The journal's
     very next line is a real, explicit "Green passes" (line 200) -- BGO
     still asked the zero-force REVEALER for a real bid/pass decision, ahead
     of Grey/Orange/Purple's own bids (lines 201-205). Confirmed via a
     temporary `eprintln!` in `start_auction`: `max_force=0` for player 2
     (Green) at that exact call. Old code excluded Green from `active`
     entirely, so the computed first decider was Grey (index 3) instead of
     Green (index 2) -- exactly the `decider 3 owes a real bid/pass decision`
     StuckPending this bucket's example message shows.

  2. Games 7521683 (journal lines 230-233) and 7523256 (journal lines
     235-238): a NON-revealer with `max_force == 0` at the moment a territory
     is revealed is NEVER asked at all -- the revealer's own bid wins
     immediately with no intervening "X passes" logged for the zero-force
     player. Confirmed the same way (temporary `eprintln!`): in both games,
     `player=0, max_force=0` appears in `start_auction`'s per-player dump for
     an auction whose revealer is player 1, and the journal shows Purple
     (the revealer) bidding and winning outright with zero lines from the
     zero-force player anywhere near it.

So the real BGO rule the fix now encodes: EVERY non-resigned player is a
potential bidder (open to all), EXCEPT a non-revealer whose own `max_force`
is 0 is skipped over and never asked; the REVEALER is always asked, even at
`max_force == 0`, as long as at least one player anywhere can actually bid.
If literally nobody (revealer included) can ever bid, no auction opens at all
-- unchanged from before, still pinned by the pre-existing
`an_auction_nobody_can_enter_is_not_started` test.

I found this by first trying the SIMPLER hypothesis (always include everyone,
full stop) -- that fixed 7523791 but broke 2 previously-completing games
(7521683, 7523256) on the first full-corpus check, which is what surfaced the
revealer/non-revealer distinction. Recording this because a from-scratch
re-derivation should NOT stop at the first game that looks fixed; the
regression check is what caught the incomplete theory.

WHAT WAS CHANGED
============================================================================
File: rust/src/interact.rs, function `start_auction` (~line 1313-1345).

Old:
    pub fn start_auction(state: &mut GameState, card: CardId, revealer: u8) -> bool {
        let (order, n) = order_from(state, revealer);
        let mut active = [0u8; MAX_PLAYERS];
        let mut k = 0;
        for &i in &order[..n] {
            if max_force(state, &state.players[i as usize]) > 0 {
                active[k] = i;
                k += 1;
            }
        }
        if k == 0 {
            state.past_events.push(card);
            return false;
        }
        state.pending.push(Pending::Auction(crate::state::Auction::new(card, &active[..k])));
        true
    }

New (same shape, two changes: the "anybody at all" check is now separate
from the per-player inclusion test, and the inclusion test OR's in
`i == revealer`):
    pub fn start_auction(state: &mut GameState, card: CardId, revealer: u8) -> bool {
        let (order, n) = order_from(state, revealer);
        let any_bidder = order[..n].iter().any(|&i| max_force(state, &state.players[i as usize]) > 0);
        if !any_bidder {
            state.past_events.push(card);
            return false;
        }
        let mut active = [0u8; MAX_PLAYERS];
        let mut k = 0;
        for &i in &order[..n] {
            if i == revealer || max_force(state, &state.players[i as usize]) > 0 {
                active[k] = i;
                k += 1;
            }
        }
        state.pending.push(Pending::Auction(crate::state::Auction::new(card, &active[..k])));
        true
    }

Also added, incidentally: `rust/tests/suite/common/mod.rs`'s `blocked_on`
had a pre-existing `_ => None` wildcard match arm over `Move` (present at
base 3fc32b5, NOT introduced by this session) that fails
`cargo clippy --all-targets -- -D warnings`'s `wildcard_enum_match_arm` lint,
unrelated to the auction bug. Fixed it the same way every other exhaustive
`Move` match in this codebase is written (spelled out every variant, one
extra `None`-mapped arm block) so the required clippy gate can pass at all;
this is a one-line-conceptually, mechanical change with no behavior change
(every variant besides `Resign` already mapped to `None` via the wildcard;
now they do so explicitly).

Also added: `rust/src/bin/replaystats.rs` got a `SCOREDIV_DUMP_COMPLETED`
env-gated dump of completed game IDs (`println!("SCOREDIV_COMPLETED_ID {}",
meta.id)`), per the coordinator's centrally-specified regression-guard
method (`/private/tmp/GUARD_METHOD.txt`) -- this is shared infrastructure
other bucket workers also need, not auction-specific logic.
