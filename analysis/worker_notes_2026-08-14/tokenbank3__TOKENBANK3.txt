Isolated via a one-row index.tsv (header + 7521459's row) and re-ran with

  round 16 end: "CORRUPTION! Grey loses 2 resources; ... (now 31)"  (resources=31)

            -- NO Raid, NO non-production gain event anywhere in this

  => true production this turn = 39 - (31-4) = 12.

Engine's own instrumented trace for actor idx=3 (Grey), round 17:
  end_of_turn pre-corruption: resources=31 blue_total=18 blue_used=16 corr=4
  [corruption debits 4 resources by removing 2 tokens of denom 2 each,
   lowest-available-first: mine_tokens 8->6, resources 31->27 -- CORRECT,
   matches the journal's stated "-4" corruption exactly]
  [food production step credits 2 new denom-3 food tokens: food_tokens 8->10]
  [food consumption (step 3d) pays food, dropping a token: food_tokens 10->9]
  [resource production step (3e) via credit_production/production_pairs:
   blue_used going in = food_tokens(9) + mine_tokens(6) = 15;
   blue_total = 18 => free = 3 => AT MOST 3 new tokens can be credited
   regardless of how many mine workers Grey actually has]
  mine_tokens 6->9 (3 new tokens), resources 27->36 (+9, NOT +12)
  end_of_turn POST: resources=36  (journal says 39; delta -3, matches
  RESOURCE_DETAIL's own report exactly: "lineno=637 round=17 actor=Grey
  journal_now=39 reconstructed=36 delta=-3")

ROOT CAUSE (as best traced with remaining budget): `credit_production`
correctly places one new token per producing worker at that worker's own
denomination (per the owner's ruling, not in question), but it is bounded
by `free = blue_total - blue_used` -- the player's OWN accumulated blue
token bank capacity, which this game's engine-reconstructed history says
is already 15/18 full at this point. If Grey in fact has 4 producing mine
workers this turn (matching the true +12 gain), the engine's own
`blue_used` count of 15 leaves room for only 3, capping production one
worker short.

This is NOT assumption #3 (non-production gain placement) -- there is no
non-production gain anywhere in this turn's causal chain, and it is NOT
the Raid bug (already fixed, not present in this game's round-17 turn).
It looks structural: `blue_total` (max token capacity, driven by total
worker/population count, pre-existing and untouched by this patch) is a
hard ceiling: it is correct and shared with the true game. But `blue_used`
-- the COUNT of physical tokens the engine's own reconstructed history has
accumulated by round 17 -- can legitimately differ from the true game's
physical token count even while both represent the exact same resource
VALUE, because the exact card each worker's token landed on over 17 prior
rounds is underdetermined by the journal (it only ever states running
totals, never per-card breakdowns). The engine's own greedy choices inside
`gain`/`pay_resources`/`credit_production` (search-downward-for-max-amount
on gain, lowest-first-with-change on spend) are A plausible reconstruction
consistent with the rules, but not necessarily THE SAME token-count history
the real player actually had -- and when the two histories diverge in
COUNT (not value), the fixed `blue_total` ceiling can bind sooner in the
reconstruction than it did in the real game, silently capping production
and compounding into a resource deficit that only becomes visible many
turns later as an illegal Build.
