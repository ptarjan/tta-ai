spread_table_provenance — git-history provenance of the live
WeightKey::p95_candidate_spread table, per the request in 8d37ddf's wake
("verify that with git history alone"). Read-only; weights.rs untouched.
Method: git log -S on the FULL row line "WeightKey::<V> => [" (so a value
change is detected even when the line prefix is unchanged), restricted to
rust/src/bots/weighted/weights.rs.

RESULT: the claim is confirmed. The live table is a merge of exactly two
instruments, and git history shows it:

  1. bin/featspread — 35fb168 "Bound each weight by what its own feature
     is worth, not by one flat 60" (2026-08-24). Introduced the whole
     table for all 174 keys; commit message says the 486 constants come
     from bin/featspread.
  2. bin/creditspread — 523bfc2 "Land the measured credit-key clamp
     bounds" (2026-08-27, ~12h before this report). Rewrote EXACTLY the
     20 credit-class rows (19 *Credit + CardBoardLeader), all from all-zero
     triples, and nothing else in the table.

No other commit in the repo's history touches any of these 28 rows.

=== Part B: the 8 zero-live-but-nonzero-featspread keys ===

BestArena, BestFarm, BestLab, BestLibrary, BestMine, BestTemple,
BestTheater, RivalFreeCa. For every one of them, git log -S on the full
row line returns EXACTLY ONE commit: 35fb168, and the line has not been
edited since. So they were never zeroed; they were set to their current
values at table creation.

BUT — and this is the point that 8d37ddf's "zero in featspread" does NOT
imply — the values 35fb168 wrote are not featspread measurements. The
commit message itself says the keys featspread measures at zero spread
"keep the flat rail rather than an invented number", and the triples it
wrote for these 8 are clean small integers, not instrument output:

  key             35fb168 wrote                live today (unchanged)
  BestArena       [2.0, 3.0, 3.0]              [3.0, 0.0, 0.0]
  BestFarm        [2.0, 3.0, 3.0]              [0.0, 0.0, 3.0]
  BestLab         [2.0, 0.0, 3.0]              [0.0, 0.0, 2.0]
  BestLibrary     [2.0, 2.0, 3.0]              [3.0, 0.0, 0.0]
  BestMine        [0.0, 0.0, 3.0]              [0.0, 0.0, 2.0]
  BestTemple      [2.0, 0.0, 2.0]              [2.0, 0.0, 0.0]
  BestTheater     [0.0, 2.0, 3.0]              [3.0, 0.0, 0.0]
  RivalFreeCa     [1.0, 1.0, 1.0]              [0.0, 2.0, 4.0]

The per-count pattern — exactly one nonzero entry per row for the seven
Best* keys (and one nonzero for RivalFreeCa's 3p/4p) — matches the
per-count feature definitions: at 2p these features are defined for one
of the three board classes (the second player's), at 3p for one, at 4p
for one; the integer is the hand-authored "typical magnitude" the commit
used in place of a measurement. 8d37ddf's featspread run, which DOES
measure them (nonzero in featspread, zero in the live table), is the
instrument that would replace these integers with real numbers; that
landing has not happened yet.

So the honest split of the 8 is:
  * never measured by featspread in any committed table version —
    confirmed (one commit touched each row, and it wrote integers);
  * never zeroed either — they were authored nonzero at creation and
    remain so;
  * their live zeros are per-count feature-availability zeros (the
    feature does not exist at that count), not "thin sampling" zeros —
    consistent with 8d37ddf's 160-vs-40 finding that sampling is not the
    zero-maker.

=== The merge, precisely ===

  live table = 35fb168's featspread table
             + 523bfc2's creditspread overwrite of the 20 credit rows.

  19 credit rows:   creditspread values (nonzero; 4 intra-row zeros are
                    instrument-indefensible cells, documented in 523bfc2).
  1 credit row:     CardRateCredit, zero in BOTH instruments (unmeasurable
                    by construction at current champions).
  8 best/rival rows: hand-authored integers from 35fb168; featspread has
                    since measured them (8d37ddf) but no commit has landed
                    those numbers.
  the other 146 rows: 35fb168's featspread values, unchanged.

Caveat for anyone re-deriving this: a -S on the bare prefix
"WeightKey::<V> =>" (without the trailing "[") shows only 35fb168 for
every row, because 523bfc2 changed the VALUES on the same line prefix.
The full-line -S (prefix plus "[") is what isolates 523bfc2.
