TWO IMPRECISIONS
----------------
free_workers is NOT "floored at 0 by type". The emitted value is a SUM:

    features.rs:840
    f.set(WeightKey::FreeWorkers, f64::from(p.workers_free) + g(GainFeature::FreeWorkers));

`p.workers_free` is u8, but the gain term is f64 and is written at
rivals.rs:353 as `gains.add(GainFeature::FreeWorkers, scale * eff.population as f64)`.
Nothing in the type system floors that sum. The floor is a property of the
CARD DATA -- no `population` field is negative anywhere in base-2015 data, per
analysis/production_counterexample_audit_2026-08-27.txt -- not of the u8. The
distinction is not pedantry: a data-derived floor silently stops holding if a
card ever prints negative population, whereas a type-derived one cannot.

rival_culture_rate is NOT floored at 0 by any visible clamp. features.rs:654
seeds it `f64::from(ctx.rival_culture_rate)` and features.rs:673 maxes it with
`f64::from(base_culture) + pg.get(GainFeature::CultureRate)`. There is no
`.max(0.0)`. (The DIFFERENCE key at features.rs:1144 does carry `.max(0.0)` --
that is a different coordinate.) `cultureProduction` has two negative entries in
base-2015 card data, so a negative value is not structurally impossible; it is
merely unlikely as a max over rivals. Describe it as unclamped.

THE BIGGER FINDING: best_farm CANNOT RESPOND TO A FARM BUILD
-------------------------------------------------------------
`best.farm` is filled from `p.techs.iter()` with `let lv = id.level()`
(features.rs:191, :214), and `CardId::level()` is the card's AGE:

    cards.rs   /// Age as a number: A=0, I=1, II=2, III=3, IV=4.
               pub fn level(self) -> u8 { self.get().age as u8 }

Agriculture is `age: Age::A` (card_table.rs:185-188), so it maps to 0. Every
player starts with Agriculture and Bronze already in the tableau
(game.rs:120-121). Therefore:

  1. best_farm reads exactly 0.0 for a player holding only Agriculture -- the
     same value as a player with no farm tech at all. 0 aliases "no farm" and
     "Age-A farm". Same for best_mine and Bronze.

  2. best_farm moves ONLY on Develop of a higher-age farm tech (Irrigation,
     age: Age::I, card_table.rs:204-207). A Build places a worker on a tech
     already owned; it does not change which techs are owned, so it does not
     change `best.farm`. Move::Build cannot move this feature at all.

That materially corrects analysis/farm_never_built_2026-08-27.txt, which reads
best_farm@4p = +37.78 (now +39.899) as a positively-priced farm channel that
somehow still fails to buy farms. It never could. best_farm prices farm TECH
AGE, not farm capacity, and is constant across every Build candidate in a
decision set -- and a feature that is constant across the candidates contributes
nothing to their ranking, whatever its weight. The huge 4p value is late-game
signal, inert in the opener window openerprobe measures.

The 4p relative-pricing story survives but must be restated: the channels that
can actually respond to a farm Build are food_rate (+0.65 at 4p) and the worker/
production terms, against resource_rate (+4.54) on the mine side. best_farm is
not one of them, and neither is best_mine.

This also weakens best_farm and best_mine as sign_intent targets, for a reason
neither the report nor my own shortlist audit saw: whatever a citation says
about them, it cannot touch the opener farm defect, because the coordinate is
not live in that decision.
