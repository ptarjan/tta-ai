EIGHT-KEY PLAYTEST, 3 PLAYERS -- 2026-08-24
=============================================

PURPOSE
-------
Prior work (analysis/mine_take_interpolation_normalized_3p_2026-08-24.txt,
analysis/mine_take_sensitivity_3p_2026-08-24.txt) found that STATICALLY
rescoring the champion's own stored decision points -- moving eight
coordinates jointly toward the human-fitted vector's relative values --
raises the "Mine take ranks first" fraction from whatever the champion gets
to 0.2003. That is a measurement of RESCORING states the champion already
chose. It says nothing about what a bot actually carrying that vector would
do at the table, because the states it would reach playing forward are not
the same states the champion reached. This playtest is the missing half:
build the vector, run it, see whether it takes Mines and whether it wins.

STEP 1 -- BUILDING THE VECTOR
------------------------------
Source: /private/tmp/opencensus/champ3p.json (the live 3p champion).
Output: /private/tmp/eightkey3p.json (left in place per instructions).

Built with a Python script that loaded champ3p.json, changed exactly the
following eight `weights` entries, and wrote the result with the same JSON
shape:

  hand_potential    0.0
  science_gap       0.0
  workers_late      0.0
  hand_perishable   0.0
  take_cost_paid    5.703
  strength          2.363
  culture_rate      6.041
  workers           4.061

All eight keys existed in champ3p.json (none needed inventing).

Verified diff (programmatic key-by-key comparison of the parsed JSON, not a
textual diff, since the two files are not byte-identically formatted):

  culture_rate:     champ=60                    eightkey=6.041
  hand_perishable:  champ=-5.012077393973028     eightkey=0.0
  hand_potential:   champ=0.4614204766574898     eightkey=0.0
  science_gap:      champ=-0.4241406489545858    eightkey=0.0
  strength:         champ=53.4862665057653       eightkey=2.363
  take_cost_paid:   champ=-1.306388415998009     eightkey=5.703
  workers:          champ=21.25334586774819      eightkey=4.061
  workers_late:     champ=60                     eightkey=0.0

Exactly these 8 keys differ. No other `weights` entry and no top-level
field (gen/players/sigma/since_accept/vs_anchor/vs_anchor_half) changed.

DOMINANCE_REPAIR ROUND-TRIP CHECK
----------------------------------
`bots::weighted::eval::load_weights` (rust/src/bots/weighted/eval.rs) calls
`parse_weights`, which calls `dominance_repair` on every load. This check
was done by tracing the actual gate logic in eval.rs and weights.rs rather
than by executing a round trip through a binary: no binary in rust/src/bin
dumps a loaded-and-repaired vector back to JSON without doing a full
training/climb run (which was judged too heavy and too risky for a
verification step -- it writes champion-shaped files and needs a pool/
gauntlet configuration this task has no business touching). The trace is
exact and cites line numbers:

  - `NET_NONNEG_PHASE` (eval.rs:792) is EMPTY -- no effect on any key.
  - `card_board_credit_keys()` only gates CardBoardLeader/CardBoardBonus-
    family per-card keys -- none of our eight.
  - `DOMINATES` (eval.rs:853) = [(ResourceStock,BlueFree),
    (WonderPotential,WonderPromise)] -- none of our eight.
  - `WeightKey::sign_intent` (weights.rs ~1056-1300): HandPotential,
    WorkersLate, TakeCostPaid, Strength, CultureRate, and Workers are all
    classified `Free` (ungated, confirmed by direct match-arm reading).
    ScienceGap and HandPerishable are classified `NonPositive`, whose gate
    only fires when the stored value is `> 1e-12`; we set both to exactly
    0.0, which does not trip it (`out.set(k, 0.0)` only runs if the
    condition is true, and 0.0 is not greater than 1e-12).

CONCLUSION: none of the eight values are mutated by dominance_repair on
load. All eight survive the round trip exactly as written. This is a
negative finding for the "first-class finding" trap the task warned about
-- the round trip is clean, so the static sweep and this playtest are
looking at the same vector.

STEP 2 -- DOES IT FIX THE SYMPTOM? (behavcensus)
--------------------------------------------------
Binaries built fresh: `cargo build --release --bin behavcensus --bin
kindmatch` -> exit 0, and confirmed newer than source after the build.

Commands:
  ./target/release/behavcensus --games 200 --players 3 \
      --weights /private/tmp/eightkey3p.json --threads 5
  ./target/release/behavcensus --games 200 --players 3 \
      --weights /private/tmp/opencensus/champ3p.json --threads 5

(200 games x 3 players = 600 player-games each, matching n=600 in both
reports below.)

Tech acquisition, Mine row (per player-game, n=600):
                 seen   taken   built  staffed
  eightkey:      2.96   0.79    1.26   1.25
  champion:      3.00   0.00    1.00   1.00

  Mine TAKEN by age tier:
    eightkey:  A=0.000  I=0.292  II=0.235  III=0.260
    champion:  A=0.000  I=0.000  II=0.000  III=0.000

Tech acquisition, Farm row, for comparison:
                 seen   taken   built  staffed
  eightkey:      2.96   0.77    1.43   1.36
  champion:      3.00   0.24    1.06   1.05

YES -- the eight-key vector fixes the reported symptom cleanly. Champion
takes zero Mines across 600 player-games at every tier, as reported.
Eight-key takes 0.79 Mines per player-game, spread across tiers I/II/III
(none at tier A, which is expected -- age A is the starting Mine, always
already owned).

Worker allocation curve (farm workers / mine workers / bestMine by round):
  champion: farmW 2.00 (r1) -> 1.31-1.36 (r18-20), a gentle drain.
            bestMine NEVER lifts off 1.00 for the whole game (r1-r21).
            mineW plateaus around 2.9-3.05 workers from round 9 onward.
  eightkey: farmW 2.00 (r1) -> 0.51-0.54 (r16-20) -> 0.33 (r22, n=54).
            bestMine climbs 1.00 -> 1.37 by round 20.
            mineW climbs from 2.00 to 6.3-6.6 by rounds 14-18, roughly
            DOUBLE the champion's plateau.

Production curve (food):
  champion: declines slowly and never crashes: 2.00 (r2) -> 1.98 -> ... ->
            1.34 (r20).
  eightkey: declines much faster and further: 2.00 (r2) -> 1.94 (r4) ->
            0.77 (r12) -> 0.43 (r14) -> a shallow partial recovery to
            ~0.5-0.6 by r17-21.

SIDE EFFECT WORTH FLAGGING: eight-key does not just start taking Mines, it
overcorrects -- it pours roughly double the champion's worker allocation
into mining, drains farm workers harder than champion does, and as a
direct consequence its food production crashes MORE severely than the
champion's already-declining food curve. Fixing the Mine-blindness this way
trades it for a worse food problem.

STEP 3 -- DOES IT WIN? (kindmatch, the deciding step)
--------------------------------------------------------
Command 1 (eight-key as A, one seat; champion as B, two seats):
  ./target/release/kindmatch --a weighted --b weighted \
      --a-weights /private/tmp/eightkey3p.json \
      --b-weights /private/tmp/opencensus/champ3p.json \
      --games 240 --players 3 --threads 5

  games        240
  players      3
  A (rotates)  weighted [eightkey3p.json]
  B (rest)     weighted [champ3p.json]
  A win rate   0.00% +/- 0.00   (null 33.33%)   p = 1.0000
  verdict      reject -- weighted is WORSE than weighted

Command 2 (mirrored: champion as A, one seat; eight-key as B, two seats):
  ./target/release/kindmatch --a weighted --b weighted \
      --a-weights /private/tmp/opencensus/champ3p.json \
      --b-weights /private/tmp/eightkey3p.json \
      --games 240 --players 3 --threads 5

  games        240
  players      3
  A (rotates)  weighted [champ3p.json]
  B (rest)     weighted [eightkey3p.json]
  A win rate   98.75% +/- 1.85   (null 33.33%)   p = 0.0000
  verdict      accept -- weighted beats weighted (interval clear of the null)

At 3 players a `kindmatch` table seats ONE `a` against TWO `b`, so the null
share is 33.33%, not 50%. Both arrangements agree: whichever weight file is
`--b` (playing two of the three seats) is the champion here, and the
champion's win share is essentially the whole table (98.75-100% of the
"champion side's" wins) while the eight-key side wins essentially nothing
(0.00%). This is not a marginal loss -- it is a near-total wipeout.

BOTTOM LINE
-----------
The eight-key vector DOES fix the reported symptom -- it takes Mines
(0.79/game across every non-starting tier, vs the champion's flat 0.000)
and lifts bestMine off 1.00 for the first time. But it LOSES DECISIVELY:
0.00% win rate at 3p against the champion (null 33.33%), confirmed in the
mirrored arrangement (98.75% for the champion, null 33.33%), and confirmed
again at 2p and 4p. This is the predicted outcome from the repo's history:
it takes more Mines and still loses -- and loses far worse than a marginal
amount. The behaviour census also shows WHY it plausibly loses beyond just
"wrong Mine count": it overcorrects, driving roughly double the champion's
worker count into mining, draining farm workers harder, and crashing food
production more severely than the champion's own (already-declining) food
curve.

CAVEATS
-------
- This vector was selected by a greedy search maximising a rank-1 fraction
  on states the champion reached. Greedy search beats any fixed vector at
  the number it optimises, so a good static score predicted nothing about
  play, and this run is precisely the test of that -- and it failed the
  test.
- The eight values came from a human-fitted vector's relative emphases. The
  human corpus is a DIAGNOSTIC MIRROR. Fitting weights to humans has lost
  three times and is on the standing do-not-do list; this is a hypothesis
  test about eight champion coordinates being over-weighted, not an
  endorsement of fitting.
- The dominance_repair round-trip check above was done by static trace of
  eval.rs/weights.rs, not by executing an actual load-and-resave round trip
  through a binary -- no existing binary exposes that without running a
  full climb/training process. The trace is exact and cites line numbers,
  but this is a methodological caveat worth naming.
- The 2p/4p runs reuse the 3p-tuned eightkey3p.json outside its designed
  player count; they corroborate the 3p result but are not a fair test of
  "an eight-key vector properly built for 2p/4p."

DO NOT FIT WEIGHTS TO THE HUMAN NUMBERS.
