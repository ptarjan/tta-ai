Block-arm sign_intent audit
2026-08-27 -- read-only; no code edits.
================================================================

SCOPE
----------------------------------------------------------------
`pub const fn sign_intent(self) -> SignIntent` (weights.rs:1480-2114)
is a pure const match: 174 WeightKey variants (verified against the
`weight_key_table!` list, weights.rs:766-790 et seq -- 174 entries,
0 missing, 0 duplicated arms), each covered by exactly one arm.
The arms split into two shapes:

  * FLAT arms -- `A | B | C => Kind("reason")`, a single constant
    returned for every key named. 12 such arms cover 147 keys.
    Every grep-shaped sign audit so far classified only these.

  * BLOCK arms -- `A | B => { Kind(...) }`, a braced single-return
    block. 7 such arms cover the remaining 27 keys. No audit has
    ever classified them, because a grep for `=> NonNegative` /
    `=> NonPositive` / `=> Free` matches the flat arms only: the
    block arm's `=>` is followed by `{`, and the returned Kind is
    on a line of its own, separated from the key list by the brace.

The 27 (exactly as briefed; all 27 verified present in the 9
block arms, none in any flat arm):
FamineDeficit, Discontent, Uprising, CivilActions, StrengthDeficit,
WarImmune, AttackCostDoubled, Wonders, WonderPotential,
WonderPromise, UnitTechCredit, TechBoardCredit, ActionBoardCredit,
GovBoardCredit, WonderBoardCredit, BuildFreshCredit,
RestrictedResourceCredit, TerritoryCredit, AggressionBoardCredit,
WarBoardCredit, EventBoardCredit, TacticReachCredit, HandValue,
HandValueLate, CivilActionSurplus, TechRedundancyDiscount,
ResourceCommitmentTurns.

KEY FINDING (the one that matters)
----------------------------------------------------------------
ZERO of the 27 block arms can return Free on any path.

Every block arm returns exactly one SignIntent, unconditionally --
there is no `if`, no state read, no player-count branch, no
dispatch inside any of the nine blocks (they are `const fn`
arms; a `const` match arm cannot inspect runtime state at all).
The "computed intent" in the brief is the braced syntax, not a
conditional: the intent is computed per-arm and constant
per-key. The strongest form of the argument is the signature:
`pub const fn sign_intent(self)` takes ONLY `self`, and a const
fn may not call non-const fns -- so the function structurally
CANNOT read runtime state (no player count, no horizon, no game
position is even available to branch on), independent of whether
any block contains an `if`. The four `if` hits a grep of the
body turns up are all inside comments (:1629, :1725, :2018,
:2027); there are zero executable conditionals in the 174 arms,
braced or flat. So there is no key that is "silently unconstrained on
some path" -- every one of the 27 carries a fixed, permanent
gate at every load, every mutation, every player count. The
hole the block syntax creates is the OPPOSITE of the one feared:
the keys are GATED, but the gate was invisible to every audit
that only greps flat arms, so the 27 have never been re-checked
against measured champion weights the way the flat-arm keys
were (SIGNAUDIT.txt's per-key measurements all run over the
grep-reachable set).

Condition per key: constant at runtime, for all 27. Genuinely
varies: none.

BLOCK 5 -- weights.rs:1660-1662

BLOCK 6 -- weights.rs:1734-1736
  HandValue | HandValueLate => { NonNegative("hand_value's
      feature is always >= 0 (a convex blend of two such
      endpoints is too)") }
  * 2 keys. Returns NonNegative unconditionally for both.
  * Condition: constant -- and this is the one block whose
    reasoning is about a RUNTIME-DEPENDENT quantity: the
    coefficient `evaluate` actually applies at lateness L is the
    convex blend `start*(1-L) + end*L` of the two keys (the
    PHASECUT T1-D collapse, 1713-1733). The gate holds at every
    L in [0,1] iff BOTH endpoints are >= 0, which is exactly the
    per-key NonNegative on each. The net is runtime-conditional;
    the per-key intent is not. (Found net-negative in every
    champion snapshot carrying nonzero phase pairs -- as low as
    -27.48 under the old basis; the per-snapshot evidence is in
    the SIGNAUDIT worker notes, e.g.
    analysis/worker_notes_2026-08-13/basiscut__SIGNAUDIT.txt
    section 7. The old composite mechanism
    `eval::NET_NONNEG_PHASE` is now EMPTY -- the per-key gate
    subsumes it.)

BLOCK 7 -- weights.rs:2041-2046
  UnitTechCredit | TechBoardCredit | ActionBoardCredit |
  GovBoardCredit | WonderBoardCredit | BuildFreshCredit |
  TerritoryCredit | AggressionBoardCredit | WarBoardCredit |
  EventBoardCredit | TacticReachCredit => { NonNegative("scales
      a dedicated function's signed output; a negative scale
      inverts good and bad rather than repricing one card") }
  * 11 keys. Returns NonNegative unconditionally for all 11.
  * Condition: constant. (The "eleven proven multipliers",
    re-audited per key 2026-08-24 in
    analysis/multiplier_decisiveness_all_counts_2026-08-24.txt:
    each is `w.get(key) * <dedicated function's signed output>`
    with no other use site. The block carries two further
    constants-of-record: (a) for the eight dispatch-switch keys
    -- Unit/Tech/Action/Gov/WonderBoardCredit,
    Aggression/War/EventBoardCredit -- `0.0` is NOT a neutral
    value, it routes the card type to a different pricing
    implementation in `cards::card_potential_core` (2015-2040),
    so dominance_repair raising a violator to 0.0 changes code
    PATH, not just magnitude; GovBoardCredit is the one where
    the fallback is reached in production (the 4p champion's
    -0.1722 is repaired to exactly 0.0 on every load). (b)
    BuildFresh/Territory/TacticReach are plain inline scales
    where 0.0 is ordinary and safe.)

BLOCK 7b -- weights.rs:1813-1815
  WarImmune | AttackCostDoubled => { NonNegative("a protective
      flag that removes no option from its holder") }
  * 2 keys. Returns NonNegative unconditionally for both.
  * Condition: constant. (Protective flags: `WarImmune` exits combat
    legality on the DEFENDER's side, removing no option from its holder;
    `AttackCostDoubled` reads the DEFENDER's leader in
    `combat::start_aggression` -- it means "rivals pay double to attack
    me", not "my attacks cost double"; Gandhi's matching self-restriction
    is `NoAggression`, which sits in the flat NonNegative arm above. The
    one pact granting WarImmune also carries `cultureProduction: -2`, but
    that is priced by the culture coordinates and floored at 0 by the
    rulebook's rating limits, so the block's comment at 1804-1812 records
    why it does not reach this gate. The citation rests on the
    COEFFICIENT's meaning -- it scales a flag that can only remove
    options aimed AT the holder -- not on a monotone feature value.)

WHY THE 27 ARE STILL AUDIT-DUE (bookkeeping, but real)
----------------------------------------------------------------
Cross-reference first: analysis/missing_sign_intents_2026-08-27.txt
(a same-day whole-match parse) already classified all 174 arms
arm-by-arm (111 Free / 38 NonNegative / 25 NonPositive) and its
counts agree with this file's tally exactly. The decomposition is
checked against the FLAT census, not just the total: flat
NonNegative 16 + block 22 = 38; flat NonPositive 20 + block 5 =
25; Free 111 + block 0 = 111; flat keys 16+20+111 = 147 = 174 -
27. (No block key appears in that file's Free list.) Its "LIST (2): keys that fall through to Free = EMPTY"
confirms there is no wildcard arm. What that file did NOT do is
the block-structure distinction this audit draws: it read the
intent, not the arm SHAPE, so it could not state that 27 of the
174 sit in braced arms invisible to grep-shaped audits. And the
evidence base below still does not exist for the 27:

  1. SIGNAUDIT's measured-inversions findings (the per-snapshot
     "found X in N snapshots" measurements in
     analysis/worker_notes_2026-08-13/*__SIGNAUDIT.txt, section 7
     of each -- e.g. pop_cost, tactic_gain negative in 8/10
     snapshots, tactic_short positive in 6/10) all live in
     flat-arm keys. The 27 block-arm keys were never in that
     measured set, so if any of them has drifted the same way,
     nothing on record says so. The gate clamps it at load
     (dominance_repair) and at mutation (climb.rs's guard), so
     the drift cannot act -- but the per-snapshot evidence base
     simply does not exist for these 27.
  2. Block 6 (HandValue/HandValueLate) and Block 7 (the eleven
     multipliers) have the richest conditional reasoning of any
     arm in the file -- convex-blend netting and dispatch-
     switch semantics -- and that reasoning was written inside a
     brace that the greps skip. It has been read by humans, not
     by audits.
  3. The single-key blocks (TechRedundancyDiscount,
     ResourceCommitmentTurns) are formatting, not logic: they
     could be flat arms, and their presence in block form is
     what makes them invisible to the grep pattern.

Suggested follow-up (not done here -- read-only): run the
SIGNAUDIT snapshot scan (section 7 shape) over the 27, reporting
for each the measured weight vs its gate (violations should be
zero post-repair; pre-repair values are the audit datum),
exactly as the SIGNAUDIT worker notes did for the flat-arm keys.
