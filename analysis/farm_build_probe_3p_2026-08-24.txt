FARM BUILD PROBE, 3 players, 2026-08-24
========================================

QUESTION (task framing): at 3p the champion TAKES Farm cards (0.24/player-game,
tier III/Mechanized Agriculture 0.195 taken) and almost never BUILDS them (tier
III 0.018 built). Where does the card die between TAKE and BUILD, and why is
Move::Build illegal when it is illegal?

METHOD
------
Extended rust/src/bin/takeprobe.rs (the ONLY file modified) with a `--build`
mode that mirrors the existing Mine-TAKE probe's four-stage discipline, but
for `Move::Build` on the three non-starting Farm technologies:

  FARM_NAMES = ["Irrigation", "Selective Breeding", "Mechanized Agriculture"]

(Agriculture, age A, is the starting technology printed on the player board --
excluded for the same reason the Mine probe excludes Bronze.)

Key method decision, made by reading legal.rs directly rather than guessing:
`legal::action_moves`'s build loop only ever generates `Move::Build{card}` out
of `tableau_names_sorted(&p.techs)` -- i.e. off the player's DEVELOPED
technology tableau, never off `p.hand_civil`. A Farm card that has been Taken
but not yet Move::Develop'd is never offered a build move at all, by
construction of that loop. So this probe's SEEN stage is
`p.techs.has(id)` (the Farm tech is already developed) at a decision point
where `state.phase == Phase::Actions && state.pending.is_empty()` -- the exact
precondition site the real build loop reads from, mirroring the Mine-TAKE
probe's own SEEN definition ("sitting in card_row" is the precondition site
`action_moves`'s take loop reads from).

Four stages, same semantics as the Mine-TAKE probe:
  1. SEEN    -- Farm tech developed (`p.techs.has(id)`) at a decision point
                where a build is structurally possible.
  2. LEGAL   -- `Move::Build{card: id}` is present in `legal::legal_moves`'
                output for that exact card.
  3. SCORED  -- it survives into `candidate_features`'s own candidate set
                (structurally identical to LEGAL for a plain WeightedBot, per
                the Mine-TAKE probe's own doc comment; checked independently
                here too, not assumed).
  4. RANK    -- 1-based rank and score gap to the winner, via the same
                `candidate_features`/`dot` re-derivation of the argmax the
                Mine-TAKE probe uses (never trusts `WeightedBot::choose`
                directly; re-derives the same pick from the same feature
                vectors, confirmed identical by construction).

ILLEGALITY CLASSIFIER
----------------------
For every SEEN-but-not-LEGAL occurrence, `classify_build_illegal` replays
`legal.rs`'s own build-loop checks (legal.rs, the `p.workers_free > 0` gate
through the non-unit affordability/CA checks) IN THE SAME ORDER and with the
SAME short-circuit semantics the real `||` expression uses, so the bucket a
card lands in is the actual reason `legal_moves` rejected it:

  1. NoFreeWorker       -- `p.workers_free == 0`. This is the OUTER gate,
                            checked once per decision point, before ANY card
                            (Farm, Mine, urban or unit) is even considered --
                            if it fires, every build is illegal simultaneously,
                            not just Farm's.
  2. NoCostPrinted      -- `costs::build_cost_net` returned `None` (no
                            printed resource cost). Never fires for a Farm
                            card in practice (every farm tech prints a
                            nonzero resourceCost) -- kept for exhaustiveness.
  3. CannotPayResources -- resources on hand (plus any live Trade Routes
                            Agreement food-as-resource conversion) fall short
                            of net cost.
  4. NoCivilAction      -- no spare civil action and no live Civil-Life-style
                            CA-free grant.
  5. Other              -- residual bucket; a Farm card is never a unit and
                            never urban, so the unit/urban-limit branches of
                            the real loop are never replayed here and never
                            attributed to Farm. `Other` firing at all would
                            mean this probe's replay diverged from legal.rs
                            itself -- it did not (see RESULTS: always 0).

This is decisive in the same shape the task's method note describes: it
separates "the code cannot build a Farm" (false -- both vectors reach LEGAL,
SCORED and even rank-1 at points) from "this weight vector will not build a
Farm" (largely true for the champion specifically). Under the SAME engine,
SAME legal.rs, SAME cost path, a differently-weighted policy reaches a 13x
higher Farm-build legality rate and, when illegal, is rejected for
CannotPayResources about as often as for NoFreeWorker (50/45) rather than the
champion's heavily worker-skewed 88/12 split.

Read together with the illegality-reason breakdown, the finding is: the
champion's Farm-build defect is NOT a Farm-pricing problem (build_cost_net
never returns None for a Farm card; CannotPayResources is a real but minority
reason) and it is NOT a code-level illegality bug (both vectors clear LEGAL/
SCORED/rank-1 under the identical engine). It is a policy-shaped scarcity of
free workers under the champion vector specifically: the champion's play
(worker allocation across takes/develops/pops/upgrades over the course of a
game) leaves `p.workers_free == 0` at the overwhelming majority (88.3%) of the
decision points where a developed Farm tech sits unbuilt, in every round from
round 5 onward, not just late game. A different weight vector (human_weights)
playing the identical engine reaches a dramatically higher build-legality rate
with a much less worker-skewed reason mix. This points the defect upstream, at
whatever champion-vector behavior is consuming/never-freeing workers, rather
than at Farm's own build cost or at legal.rs's build-loop code.

CAVEATS
-------

1. SEEN is defined as "developed" (`p.techs.has(id)`), not "in hand"
   literally (`p.hand_civil`). This is a deliberate reading, not the task
   prompt's literal wording: `legal.rs`'s build loop only ever draws
   candidates from the developed tableau (`tableau_names_sorted(&p.techs)`),
   never from hand, so a Farm card sitting in hand but not yet Developed
   would never be offered a build move regardless of workers/resources/CA --
   grounding SEEN there (rather than in hand_civil) is what makes the
   illegality classifier's checks the actual reasons `legal_moves` rejects a
   candidate, instead of always reporting "not developed yet" for every
   hand-only occurrence. This probe does NOT separately measure the prior
   Take-to-Develop step; a Farm card that is Taken but never Developed is
   invisible to this probe entirely (never counted in SEEN at all), and that
   gap is not measured here.

2. The champion and human-vector self-play games are NOT the same
   trajectories -- each vector plays its own game, so the games differ in
   length, pacing, and how often/when a Farm tech gets developed at all. The
   champion's much lower SEEN count (2763 vs 23802 over the same 600 games)
   and complete absence of Irrigation from the champion's SEEN set are most
   simply read as "the champion's own play rarely reaches a state where a
   Farm tech is both developed and it's the champion's action-phase turn,"
   which is itself evidence for the same worker/economy story (a policy that
   starves free workers plausibly also under-invests in developing Farm techs
   in the first place) -- but this probe does not isolate that from other
   differences between the two vectors' games (game length, age reached,
   etc.), so treat the SEEN-count gap as suggestive, not a separately proven
   claim.

3. RANK/gap tables and the WeightKey contribution ranking are thin for the
   champion (n=52 scored occurrences across 600 games) -- individual key
   rankings there should not be treated as precise; they are included because
   the task asks for them when the funnel reaches SCORED, not because n=52 is
   a confident sample. The human-vector ranking (n=5988) is much better
   powered.

4. The illegality classifier replays legal.rs's checks; it does not call
   legal.rs itself, so a future change to the build loop's checks/order (or a
   new gate added there) would silently desync this classifier from the real
   legality path until this probe is updated to match. `Other` reading
   exactly 0 in both runs is the check that they agree today, not a guarantee
   they will keep agreeing after a legal.rs change.

5. Per this task's own instruction, this file reports what was measured and
   does not propose a weight change or code fix.
