--------------------------------------------------------------------------------
1. THE ANSWER (the ~38 "missing points" do not exist)
--------------------------------------------------------------------------------
The earlier job-J hand-arithmetic prediction of seat-1 best-take at -1.227
(margin +3.39) vs the measured ~-39 was chasing a phantom. The empirical dump
reproduces the measured margin to 1e-13 with NO residual -- there are no
missing points to find. The discrepancy in the hand-arithmetic version was a
bookkeeping error in which state the EndTurn candidate was scored against,
not a missing ~38 of feature mass.

KEY FACT that the hand arithmetic kept getting wrong, confirmed in the current
champion source (eval.rs rank_moves, guard at line 554 as of this session's
read; the guard moved with commit f13707f):

    if !matches!(mv, Move::EndTurn) {
        apply::apply(&mut trial, mv);
    }
    let mut val = evaluate(&trial, idx, w, Some(&ctx), None);
    if matches!(mv, Move::EndTurn) { val += end_bias; }

rank_moves does NOT apply EndTurn. It scores the UNMOVED root plus end_bias.
Only the Take candidate is applied (apply(root, Take)). Therefore the margin
decomposes as:

    margin = best_take - endturn
           = [ evaluate(apply(root, Take)) - evaluate(root) ] - end_bias
           = (sum of per-term take-minus-root deltas) - end_bias

CORRECTION (2026-08-28, from coordinator): the Phase-1 claim that rank_moves
APPLIES EndTurn (apply.rs:314 -> game::end_turn) was CORRECT against the code
as it then was. Commit f13707f changed rank_moves AND candidate_features to
skip apply for Move::EndTurn (mirroring choose's guard, which has existed
since 02086c6), and added a test pinning the SCORE, not the argmax. Phase 1
and Phase 2 of this job both read the correct code for their respective
trees; nothing was stale. Scoring EndTurn against the end-of-turn state
(production collected, pools refilled, turn advanced) -- worth ~+39 at the
first R1 decision -- is what the pre-fix instrument measured and what the
hand arithmetic was implicitly doing. With the unmoved-root convention the
gap is exactly 0.

3. THE THREE CALLOUT KEYS (as requested by the coordinator)
--------------------------------------------------------------------------------

(a) RowPlayableCount -- a GENUINE row feature; it does NOT cancel.
    Weight at gen 121002: +0.174230  (coordinator cited +0.244164 at an
    earlier gen read; the key is the same, the live value drifted).

      seat 0 turn=1 slot3:  feature_root=5.000000  feature_take=0.000000  w*delta=-0.871149
      seat 1 turn=2 slot5:  feature_root=8.000000  feature_take=0.000000  w*delta=-1.393838
      seat 0 turn=1 slot1:  feature_root=4.000000  feature_take=0.000000  w*delta=-0.696919
      seat 1 turn=2 slot7:  feature_root=7.000000  feature_take=0.000000  w*delta=-1.219608

    The trial value COLLAPSES TO 0 at every dumped decision point -- exactly
    the coordinator's expectation. A take removes the taken card from the row
    AND spends a civil action, so can_take_gated re-evaluates for every
    remaining slot at lower CaLeft. At seat 0 (CaLeft 1 -> 0) the gate rejects
    every remaining row card, driving the count to 0. The feature root value
    (4-8) is the number of row cards still takeable before the move; the take
    zeroes it. This is a real, positive-weight contribution that PENALIZES
    taking (w*delta is negative): the bot is charged for the row cards it can
    no longer play because it already spent its action. The corrected opener
    menu's claim that this key "cancels because the row does not change during
    a turn" is FALSE -- the take changes the row (removes a card) and changes
    CaLeft (spends an action).

(b) ScienceNeedRow -- set in the same features.rs block (line 820); it DOES
    cancel at these R1 decision points.
      Weight at gen 121002: -0.080186.
      feature_root=0.000000  feature_take=0.000000  w*delta=-0.000000   (all 4 points)
    Both root and trial are 0, so its delta is exactly 0.0. The "claimed to
    cancel" assertion is correct FOR ROUND 1 (no science row need yet), but
    note this is a 0==0 cancellation, not the 5==5-style cancellation the
    menu described.

(c) HandPotential -- NOT a feature. Feature delta is ALWAYS exactly 0.0.
      Weight at gen 121002: +1.198659.
      feature_root=0.000000  feature_take=0.000000  w*(take-root)=+0.000000   (all 4 points)
    Confirmed: HandPotential is a w.get-only hyperparameter
    (features.rs:858-860, registry.rs NOT_SET_BY_FEATURES, never written by
    compute). It is never a Features field, so its feature delta between root
    and take-trial is exactly 0.0 -- there is nothing to report as a feature
    contribution, and the takeprobe --sensitivity "backwards" run was scaling
    the multiplier, not a contribution.

    CAUTION / disambiguation: HandPotential DOES appear as a row in the
    per-term decomposition (e.g. seat 1 slot5: root=0.000000, take=+13.534283,
    delta +13.534283). That row is the EVAL-ONLY block contribution
    (weights.get(HandPotential) * cards::hand_potential(state,...)), NOT a
    feature delta. The eval-only block is real and moves (taking a card adds
    to the hand's potential), but the HandPotential *feature* is always 0. The
    two must not be conflated: the coordinator's correction holds for the
    feature; the eval-only block is a separate, legitimate contribution that
    does move.

4. TOP-5 PER-TERM CONTRIBUTIONS (by |delta|, seat 1 turn=2 slot5, the
   representative round-1 seat-1 decision; margin +16.166910)
--------------------------------------------------------------------------------
  1. HandPotential (eval-only block, NOT the feature)   +13.534283
  2. CivilActionSurplus                                  -3.097431
  3. RowPlayableCount                                     -1.393838
  4. TakeCostShare                                        +1.390152
  5. CivilActionGap                                       -0.904813
  (end_bias -5.005234 applied on top; sum of all deltas +11.161676,
   minus end_bias => +16.166910.)

Interpretation: the single largest driver of a round-1 take is the eval-only
HandPotential block (+13.5) -- the hand's unrealized card value rises when a
card is taken. The two next largest are the civil-action bookkeeping
(CivilActionSurplus -3.1, CivilActionGap -0.9): taking spends an action, which
is priced against the surplus/gap keys. RowPlayableCount (-1.4) is the
row-feature penalty for the take (see section 3a). TakeCostShare (+1.4) is the
share-of-cost credit for paying the take's resource cost.

Seat 0 (turn=1) is dominated by the same civil-action keys plus RowPlayableCount;
HandPotential's eval-only block is smaller there (e.g. +3.02 slot1, +0.048
slot3) because the hand is thinner at the start of the game.
